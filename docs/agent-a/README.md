# Agent-A 직접 화면과 초안 보존 규약

IAMCEO 의 Agent-A 직접 화면(`web/src/components/AgentAReview.tsx`)은 Agent-A 앱을 칸(iframe)에 넣지 않고,
IAMCEO 서버의 검토 길(`server/integrations/agent-a-review.ts`)이 Agent-A 의 검토 규약을 대신 부른다.
이 문서는 그 길이 **다른 창의 초안을 덮지 않으려고** Agent-A 쪽에 더한 규약과, 적용·되돌리기 조건을 적는다.

## 왜 Agent-A 를 바꿔야 했나

원래 Agent-A(c559881)의 초안 저장(`POST /api/draft`)은 초안을 통째로 바꾼다. 세대 번호(`draftGeneration`)는
초안을 지우거나 제출할 때만 오르고, 보통 저장에서는 그대로다. 그래서 '초안을 읽고 → 주석 하나를 더해 → 통째로 저장'하면,
읽은 뒤 다른 창(원래 Agent-A 화면·다른 프로세스)이 저장한 직접 편집·첨부·주석이 사라진다. 두 저장이 모두 200 이라 알 수도 없다.
IAMCEO 안에서 줄을 세워도(직렬 잠금) 다른 창은 막지 못한다. 독립 검토 F1 이 이 반례다.

IAMCEO 만으로는 고칠 수 없다: 조건을 걸 수 있는 쓰기도, 주석 하나만 더하는 쓰기도 원래 규약에 없다.

## Agent-A 에 더한 것(초안 규약 2)

`agent-a-draft-protocol-2.patch` (기준 c559881, `src/server/plannotator.js` 와 시험 1개). 원래 화면(Plannotator)은 고치지 않았고,
원래 화면이 쓰는 요청·응답 본문의 모양도 그대로다. 더한 것만 쓰는 쪽이 보호받는다.

| 더한 것 | 뜻 |
| --- | --- |
| `draft_revision` | 저장된 초안이 바뀔 때마다 오르는 판 번호(저장·지우기·문서별 초안·제출·주석 추가). 응답 머리 `X-ENOUV-Draft-Revision` 으로 준다. |
| `POST /api/draft` 의 `ifDraftRevision` | 보낸 판과 지금 판이 다르면 아무것도 바꾸지 않고 409 `draft_conflict`. 안 보내면 예전처럼 통째로 바꾼다(원래 화면). |
| `POST /api/feedback` 의 `ifDraftRevision` | 제출하려는 사이 초안이 바뀌었으면 제출하지 않는다. 같은 제출의 재전송은 판 검사보다 먼저 처음 결과를 돌려준다. |
| `POST /api/draft/annotations` | 주석 하나만 한 트랜잭션에서 더한다. 초안의 다른 칸은 건드리지 않는다. 같은 id·같은 내용은 처음 결과 확인, 같은 id·다른 내용은 409 `idempotency_conflict`, 지난 판의 검토는 409 `revision_conflict`, 제출한 검토는 409 `decided`. |
| 검토 세션의 `capabilities.draft_protocol = 2` | 이 규약을 아는 Agent-A 라는 표시. |

## IAMCEO 가 쓰는 방법

| 일 | 길 | 다른 창의 초안 |
| --- | --- | --- |
| 새 댓글·삭제 표시 | `GET /api/draft`(초안 판 머리로 규약 확인) → `POST /api/draft/annotations` | 통째 저장을 하지 않으므로 남는다 |
| 본문 직접 고치기(초안) | `GET /api/draft` → `POST /api/draft` + `ifDraftRevision`(화면이 고치기 시작할 때 본 판) | 그사이 바뀌었으면 거절하고 대표에게 보인다 |
| 검토 제출 | `GET /api/draft` → `POST /api/feedback` + `ifDraftRevision` | 그사이 바뀌었으면 제출하지 않는다 |
| 빠른 라벨(고른 글 · 그림 영역의 '좋아요') | 새 댓글과 같은 길. 주석에 원래 화면과 같은 표시(`isQuickLabel`·`quickLabelTip`)를 싣는다. 그림 영역은 `imageRegion` 도 함께 싣는다 | 통째 저장을 하지 않으므로 남는다 |
| 도식의 한 부분(또는 도식 전체)에 댓글 | `GET /api/draft` → 지금 본문의 그 도식에 묶이는지 확인 → `POST /api/draft` + `ifDraftRevision`(읽은 초안에 주석 하나만 더한다). 주석에 원래 화면과 같은 자리(`diagramAnchor`)를 싣고, 원문 칸에는 그 부분의 글을 둔다. 이미 받은 id 의 재전송·지난 판·닫힌 검토는 새 댓글과 같은 길(`POST /api/draft/annotations`)로 보내 Agent-A 가 확인하거나 거절한다 | 그사이 바뀌었으면 Agent-A 가 받지 않는다. 다시 읽어 처음부터 확인하므로 다른 창의 저장이 남는다 |
| 검토 전체에 붙이는 그림 | `GET /api/draft` → `POST /api/draft` + `ifDraftRevision`(붙인 그림 목록만 바꾼다) | 그사이 바뀌었으면 거절하고 다시 읽은 목록을 보인다 |
| 답글·완료·지우기·다시 요청·갈래 질문·수정안 저장·판·문서 관리 | 원래 규약 그대로(줄 하나만 바꾸는 쓰기) | 초안을 건드리지 않는다 |
| 문서 관리의 블록 일(검토 표시·보관·새 블록·순서·배치·목표와 제약) | 정본 명령(`review_block`·`archive_block`·`insert_block`·`reorder_blocks`·`set_layout`·`update_context`) | 초안을 건드리지 않는다 |
| 문서 대화 가르기·AI 권한 응답 | `POST /api/ai/fork` · `POST /api/ai/permission` | 초안을 건드리지 않는다 |

문서 관리의 블록 일도 직접 고치기와 같은 방식이다: 명령을 요청이 가리킨 판(블록 판·문맥 판·배치 판)으로만 만든다.
같은 요청을 다시 보내면 같은 명령이 되어 Agent-A 가 처음 결과를 돌려주고, 낡은 판을 가리킨 새 요청은 Agent-A 가 거절한다.
새 블록의 id 는 요청 id 로 정해 다시 보내도 블록이 하나만 생긴다.

IAMCEO 만으로 고친 것: 직접 고치기·되살리기의 재전송(F2). 명령을 요청이 가리킨 판으로만 만들어, 같은 요청을 다시 보내면
같은 명령이 되고 Agent-A 가 판 검사보다 먼저 보관한 처음 결과를 돌려준다. 지금 판으로 바꿔 다시 보내지 않는다.

판을 보내지 않은 요청(문맥 판·배치 판 생략)도 같다(R2). 처음 보낼 때만 지금 판을 싣고, 같은 요청 id 의 명령이 이미 실행됐으면
Agent-A 가 사건 기록(`events[].command_id`·`payload`)에 남긴 그때의 판을 다시 싣는다. 그사이 목표나 배치가 바뀌어도 같은 명령이 된다.
보낸 판은 바꾸지 않으므로 같은 요청 id 에 다른 내용·다른 판은 여전히 거절된다.

초안 조건 저장(본문 직접 고치기·검토 전체에 붙이는 그림)의 재전송(R1): 저장할 때 초안에 저장 기록
`iamceoSave: { v: 1, body: [key…], attachments: [key…], ids: { key: 요청 id 지문 } }` 를 함께 싣는다. `key` 는 그 요청(문서·검토·칸·화면이 본 초안 판·값·요청 id)의 지문이다.
`ids` 는 남아 있는 기록이 어느 요청 id 로 왔는지를 적는다(문서·검토·요청 id 의 지문. id 없이 온 요청의 기록에는 없다).
Agent-A 는 초안의 모르는 칸을 그대로 보관하므로(패치를 바꾸지 않았다) 저장이 들어갔으면 그 기록도 들어가 있다.
저장은 됐는데 응답만 잃은 같은 요청이 다시 오면, 초안 판이 이미 올라 있어도 이 요청의 기록과 그 칸의 값을 보고 다시 쓰지 않은 채 지금 초안을 돌려준다.

- 기록은 칸(본문·그림)마다 따로 둔다. 본문 저장 뒤에 그림 저장(또는 그 반대)이나 댓글이 끼어 초안 판이 더 올라도 앞 요청의 기록이 남는다.
  앞 판(a474537)은 기록을 한 자리 `{ v: 1, key }` 에만 두어 다른 칸의 저장이 앞 기록을 지웠고, 독립 재검토가 두 방향에서 409 를 재현했다.
  앞 판 모양의 기록은 기록이 없는 것으로 본다(대표 화면에 반영된 적이 없는 모양이다).
- 한 칸의 기록은 지금 그 칸의 값을 만든 요청들이다(최근 네 개). 값을 바꾸는 저장은 그 칸의 앞 기록을 버리고, 같은 값을 다시 쓰는 저장은 앞 기록을 잇는다.
- 요청 id(`opId`)는 화면이 저장마다 정해 보낸다. 같은 저장(같은 초안 판·같은 값)을 다시 누르면 같은 id 를 쓰고, 다른 화면은 다른 id 를 쓴다.
  HTTP 길(`POST …/review/draft`·`…/review/draft/attachments`)은 id 가 없으면 받지 않는다.
- 요청 id 는 처음 입력에 묶인다. 기록에 남은 id 가 다른 입력으로 오면, 초안 판이 지금 판과 맞아도 새 저장으로 받지 않는다
  (409 `AGENT_A_IDEMPOTENCY_CONFLICT`, 아무것도 쓰지 않는다). 앞 판(5f7f626)은 id 를 `key` 안에만 넣어 '이 id 를 이미 썼는가'를 알 수 없었고,
  독립 재확인이 같은 id·지금 초안 판·다른 본문이 새 저장(200, 초안 판 +1)이 되는 것을 재현했다.

초안 판이 이미 오른 뒤에 온 요청이 200(이미 저장됨)인지 409(`draft_conflict`)인지는 아래와 같다. 가짜와 실제 Agent-A 서버 코드에서 본 그대로다.

| 초안 판이 이미 오른 뒤에 온 요청 | 결과 |
| --- | --- |
| 같은 요청 id·같은 초안 판·같은 값이고 그 칸의 값이 그대로 | 200, 다시 쓰지 않는다. 그사이 다른 칸의 저장·댓글이 끼었어도 같다 |
| 요청 id 가 다른 같은 초안 판·같은 값(다른 화면) | 409 |
| 요청 id 없이 온 같은 초안 판·같은 값(HTTP 를 거치지 않고 이 클래스를 직접 부르는 쪽) | 200. 두 호출을 가린 것이 아니다(가릴 값이 없다) |
| 내 저장 뒤 그 칸의 값이 바뀜(기록을 실었든 아니든) | 409, 바뀐 값이 남는다 |
| 기록을 싣지 않고 초안을 통째로 저장한 쪽이 있음 | 409 |
| 기록까지 그대로 다시 실은 저장이 있고 그 칸의 값은 그대로 | 200. 그 저장이 바꾼 다른 칸(주석 등)은 남는다 |
| 기록의 `v` 가 다름, 칸의 기록이 배열이 아님, 앞 판 모양(`{ v: 1, key }`), 다른 문서·다른 검토에서 옮겨 온 기록 | 409 |
| 칸의 기록 배열에 틀린 항목이 섞임 | 틀린 항목은 걸러 낸다. 걸러 낸 뒤 앞 네 개 안에 이 요청의 `key` 가 있으면 200, 다섯째로 밀렸으면 409 |

초안 판이 지금 판과 맞는 요청은 새 저장이다. 다만 요청 id 가 기록에 남아 있으면 아래와 같다.

| 지금 초안 판에 맞춰 온 요청 | 결과 |
| --- | --- |
| 기록에 없는 요청 id(새 id) | 200, 새로 저장한다 |
| 기록에 남은 요청 id 에 다른 값, 또는 같은 값(초안 판이 처음과 다르므로 다른 입력) | 409 `AGENT_A_IDEMPOTENCY_CONFLICT`, 쓰지 않는다. 다른 칸·주석·그림·초안 판이 그대로다 |
| 기록에 남은 요청 id 를 다른 칸(본문 ↔ 그림)에 보냄 | 409, 위와 같다 |
| 기록에서 빠진 요청 id(그 칸의 값이 바뀜·최근 네 건 밖), 요청 id 없는 호출, 다른 문서·다른 검토에서 쓴 요청 id | 200, 새로 저장한다 |
| 다른 쪽이 `ids` 를 빼거나 틀린 모양으로 다시 실은 기록에 남은 요청 id | 200, 새로 저장한다(그 기록은 요청 id 가 없는 기록으로 본다. 처음 입력의 재전송 확인은 그대로 된다) |

- 그러므로 '다른 화면의 저장은 늘 충돌'이 아니다. 첫 표의 셋째·여섯째 줄은 200 이다. 어느 줄에서도 재전송은 초안을 다시 쓰지 않고 초안 판을 올리지 않는다.
- id 없는 호출의 같은 값을 같은 요청으로 보는 것(첫 표의 셋째 줄)은 구현의 한계를 적은 것이다. 대표가 정한 정책이 아니다.
- 요청 id 를 묶는 범위도 구현의 한계다: 이 문서·이 검토의 기록에 남아 있는 동안만이다(칸마다 최근 네 건, 그 칸의 값이 바뀌면 앞 기록을 버린다).
  모든 요청 id 를 따로 보관하지 않으므로 기록에서 빠진 id 는 새 요청으로 받는다. 화면은 저장마다 새 id 를 쓰고, 화면을 새로 열면 앞 id 를 기억하지 않는다.
  이 범위와 같은 id 를 다른 칸에 보낼 때의 거절은 대표가 정한 정책이 아니다.
- 200 으로 돌려주는 것은 처음 응답의 사본이 아니라 지금 초안이다(그사이 바뀐 다른 칸·주석 수·초안 판이 들어 있다).
- 원래 Agent-A 화면이 초안을 저장할 때 이 기록을 싣는지는 확인하지 못했다(보존한 소스 사본에 화면 부품이 없다). 싣지 않으면 그 뒤의 재전송은 409 이고 저장된 내용은 남는다.
- 화면이 받는 초안(`AgentAReviewDraft`)과 검토 제출 글에는 기록을 싣지 않는다.

## 서버 조합

| IAMCEO | Agent-A | 결과 |
| --- | --- | --- |
| 이 가지 | 초안 규약 2(패치 적용) | 모든 기능 |
| 이 가지 | 원래 c559881 | 새 댓글(도식 부분 댓글 포함)·삭제 표시·빠른 라벨·본문 고치기·검토 첨부·검토 제출을 **거절**한다(`AGENT_A_UNSUPPORTED`, 화면에 까닭을 보인다). 읽기·답글·수정안·판·문서 관리(블록 일 포함)·문서에 묻기(가르기·권한 응답 포함)는 된다. 통째 저장으로 조용히 넘어가지 않는다. |
| 예전 가지(칸 방식) | 초안 규약 2 | 원래 화면이 그대로 돈다(더한 것은 안 쓴다) |

지금 켜 둔 체험 Agent-A(4417)는 원래 c559881 이다. 이 가지를 그 Agent-A 에 붙이면 둘째 줄이 된다.

## 적용과 되돌리기

1. 적용: Agent-A 소스에 `git apply docs/agent-a/agent-a-draft-protocol-2.patch` → Agent-A 다시 시작. DB 구조는 바뀌지 않는다
   (검토 세션 기록에 `draft_revision` 칸이 생길 뿐이고, 없는 옛 세션은 0 으로 읽는다).
2. 되돌리기: 패치를 빼고 Agent-A 를 다시 시작한다. 저장된 `draft_revision` 칸은 원래 코드가 읽지 않아 그대로 두어도 된다.
   그 뒤 IAMCEO 는 둘째 줄(쓰기 거절)로 돈다. 이미 저장된 댓글·초안·판은 그대로다.
3. 코드를 되돌려도 예전 방식으로 이미 덮인 초안은 돌아오지 않는다. 그 복구는 Agent-A 의 백업으로만 한다.

## 도식(Mermaid)을 그리는 방법

도식 글은 직원·AI 가 쓴 믿을 수 없는 글이다. 그리는 부품(Mermaid 12.2.0, 약 5MB)은 도식 글의 이름표를 HTML 로 다루는 길이 있어,
화면 문서에서 돌리면 도식 글이 그 문서의 DOM 에 닿는다(화면의 보안 정책이 스크립트는 막지만, 그 한 줄에만 기대지 않는다).

- 화면은 부품을 직접 싣지 않는다. 도식이 든 문서를 열 때만 보이지 않는 칸(iframe) 하나에 `/vendor/diagram-frame` 을 연다.
- 그 문서는 `sandbox allow-scripts` 로 열려 출처가 없다(화면의 DOM·저장소·쿠키·접속 코드에 닿지 못한다). 보안 정책은 이 서버의
  스크립트 두 개(`/vendor/mermaid.min.js`, `/vendor/diagram-frame.js`)만 허락하고 그림·글꼴·연결·다른 칸은 모두 막는다.
- 화면은 도식 글을 메시지로 보내고 SVG 글만 돌려받아 `<img>`(blob 주소)로 보인다. 그림으로 열린 SVG 는 스크립트가 돌지 않고
  바깥 주소를 부르지 못한다. 문법이 틀렸거나 부품을 받지 못하면 도식 원문을 글로 보인다.
- 부품 파일은 `server/vendor-mermaid.ts` 가 파일로 싣는다(컴파일한 실행 파일에도 들어간다). 패키지가 없으면 404 이고 원문을 보인다.
- 알려진 환경 조건(2026-11-17 확인, 제품 코드는 바꾸지 않았다): 서버를 macOS 격리 실행(`sandbox-exec`)에서 띄우고 그 규칙이 바깥 통신을
  막으면(`deny network-outbound`, 예외는 `remote ip "localhost:*"` 뿐) 이 부품 파일의 GET 만 끊긴다(HEAD 는 200, GET 은 연결이 끊기고
  화면은 도식 원문을 글로 보인다). 서버는 이 파일을 파일 응답(`Bun.file`)으로 보내는데, 커널이 그 큰 파일 전송을 바깥 통신으로 보고 막는다
  (커널 기록 `deny(1) network-outbound local:*:<포트>`). 같은 규칙에서 작은 파일과 메모리·스트림 응답은 온전히 간다. 격리 없이 띄우면 온전히 간다.

### 도식의 한 부분에 댓글

원래 Agent-A 화면은 도식의 노드·선·묶음을 눌러 그 부분에, 빈 자리를 눌러 도식 전체에 댓글을 단다. 이 화면도 같게 한다.

- 화면은 도식을 그림(`<img>`)으로만 보이므로 그림 안의 요소를 누를 수 없다. 그리는 칸이 그림과 함께 **누를 수 있는 부분의 이름·글·자리**
  (그림 전체를 1 로 본 비율)를 돌려주고, 화면은 그 자리에 투명한 단추를 겹쳐 놓는다. 격리(출처 없는 칸·보안 정책·`<img>` 로만 보이기)는 그대로다.
  돌려받은 부분 목록도 믿지 않는다: 종류·이름·숫자의 모양을 검사하고 글 400자·부분 300개·누를 자리 24개까지만 받는다(`cleanParts`).
- 자리는 주석의 `diagramAnchor`(`v`·`family`·`kind`·`id` 또는 `from`·`to`·`label`·`sourceLine`)에 싣는다. 원래 화면과 같은 모양이라
  두 화면이 서로의 도식 댓글을 같은 부분에 보인다. 자리는 도식 글의 이름이고 좌표가 아니다(다시 그리면 좌표는 달라진다).
  `sourceLine` 은 그 부분이 적힌 문서 줄 `[첫 줄, 끝 줄]`(1부터)이다.
- 이름을 읽는 규칙(Mermaid 12.2.0 이 그린 요소의 id)은 갈래마다 다르다: 흐름도(노드·선·묶음) · 상태도 · 클래스도 · 관계도 · 요구도는
  요소 id 에서, 순서도는 참여자 이름과 메시지·메모·틀의 차례 번호(`msg-1`·`note-1`·`frame-1`)에서 읽는다. 그 밖의 도식(원그래프 등)은 도식 전체에만 단다.
- 다시 열었을 때 부분을 찾는 차례: 이름(선은 양 끝)이 같은 부분 → 글이 같은 하나뿐인 노드 → 못 찾음(표시 없이 댓글 목록에만 남는다).
- 이미 있는 댓글을 어느 도식에 표시할지는 원래 화면의 규칙을 따른다(새 댓글의 검사와는 다른 일이다).
  - Graphviz 댓글은 Mermaid 도식에 붙지 않는다: Graphviz 댓글의 `B` 는 Mermaid 흐름도의 `B` 가 아니다. 그런 댓글은 지우거나 숨기지 않고
    번호 표시 없이 댓글 목록에만 남긴다.
  - Mermaid 안의 갈래(`family`)는 견주지 않는다(원래 소스 `core/diagram-anchor.ts` 의 `sameTarget`: "The family is not compared").
    본문의 도식을 흐름도에서 상태도로 바꿔도 같은 이름의 부분이 있으면 옛 댓글이 다시 붙는다. 순서도의 차례 이름(`msg-2`)처럼
    이름의 문법이 다른 갈래의 댓글은 그 이름의 부분이 없어 붙지 않는다.
  - `sourceLine` 이 가리키는 도식에 그 부분이 있으면 그 도식이다. 줄이 없거나 맞지 않으면 그 자리를 찾는 문서 차례의 첫 도식이다
    (본문이 바뀌어 줄이 어긋난 옛 댓글을 되찾는다. 원래 화면도 블록을 잃은 댓글을 처음 찾는 도식에 붙인다). 도식 전체에 단 댓글은 줄이 가리키는 도식에서만 본다.
- 서버는 새 도식 댓글을 쓸 때 세 가지를 따로 본다. 어느 것이든 틀리면 아무것도 쓰지 않는다(초안의 판·본문·첨부·다른 주석이 그대로다).
  - 모양(400 `AGENT_A_INVALID_DIAGRAM_ANCHOR`): 판 번호·갈래·종류·이름과 글의 길이·줄 번호(양수, 첫 줄 ≤ 끝 줄, 100만 이하).
  - 화면이 본 본문(409 `AGENT_A_BODY_CHANGED`): 대상 본문은 지금 화면이 보이는 본문이다. 본문 초안이 있으면 그 초안(빈 글이어도 초안이다),
    없으면 그 검토가 고정한 정본이다. 초안에서 지운 도식을 정본에 있다는 이유로 받지 않는다. 문서 열기가 그 본문의 표(`bodyMark`: 초안인지 정본인지와
    글의 지문)를 주고, 화면은 도식 댓글에 그 표를 실어 보낸다. 그사이 다른 화면이 본문을 바꿔 표가 지금 본문과 다르면 쓰지 않는다.
    화면은 까닭을 보이고 지금 본문을 다시 불러온다. 표를 싣지 않은 요청은 지금 본문에 묶이는지만 본다.
  - 그 본문의 한 도식에 묶이는지(400 `AGENT_A_DIAGRAM_NOT_IN_DOCUMENT`): 줄이 있으면 그 줄을 품은 Mermaid 조각 하나가 대상이고,
    줄은 화면이 자리를 만드는 규칙으로 그 조각에서 찾은 줄과 같아야 한다(부분은 그 이름이 그 조각에 처음 적힌 줄, 도식 전체는 그 조각의 글 전부).
    도식 전체는 글도 그 조각의 첫 줄 글이어야 한다. 그래서 다른 조각에서 따로 맞는 글·이름·줄을 섞은 자리는 받지 않는다. 도식 전체는 줄이 있어야 한다.
    글에서 줄을 찾는 규칙은 화면과 같은 코드다(`shared/agent-a-diagram.ts`).
  - 검사와 쓰기 사이: 쓰기는 초안 판 조건 저장이다. 본문을 읽은 그 초안 판에만 주석을 더한다. 그사이 다른 화면이 초안을 저장했으면 Agent-A 가 받지 않고,
    서버는 다시 읽어 위 검사를 처음부터 한다(네 번까지. 계속 끼어들면 409 `AGENT_A_DRAFT_CONFLICT`). 검사한 본문과 다른 본문에 쓰지 않는다.
  - 새 쓰기가 아닌 것은 이 검사를 하지 않는다: 이미 초안에 있는 id 와 Agent-A 가 받은 적 있는 id 의 재전송(그사이 본문이 바뀌었어도 Agent-A 가
    같은 내용이면 처음 결과를 확인하고, 다르면 409 로 거절한다), 지난 판·닫힌 검토(자리가 맞든 틀리든 Agent-A 가 409 로 거절한다).
  - 가리지 않는 것(서버는 도식을 그리지 않는다. 이 범위의 요청은 200 으로 저장된다): 갈래와 부분의 보이는 글이 그려진 도식과 같은지,
    줄이 없는 부분(글에서 이름을 찾을 수 없는 부분: 번호뿐인 선 등)이 어느 조각의 것인지(본문에 Mermaid 조각이 있으면 받는다).
    지난 판인지는 쓰기 전에 한 번 본다(조건 저장은 초안 판만 견준다. 그 사이에 정본이 바뀌면 방금 지난 판이 된 검토의 초안에 남는다).
    닫힌 검토는 Agent-A 가 쓰는 순간에도 거절한다.
- 읽을 때는 원래 화면처럼 너그럽게 읽는다. 모양이 틀린 자리는 자리 없는 댓글로 남고, 문서 밖 줄·다른 갈래의 이미 있는 댓글도 그대로 읽는다
  (새 댓글의 연결 검사는 읽기에 쓰지 않는다). 검토 제출 글에는 `(diagram: node 검토 (B), line 7)` 같은 한 줄이 붙는다.
- 실제 Agent-A 서버는 검토를 제출할 때 댓글의 대상 블록을 원문 칸의 글로 찾는다. 부분의 글이 본문에서 하나뿐이면 그 도식 블록에 붙고,
  아니면 문서 전체 의견으로 넘어간다(그 서버가 `diagramAnchor.sourceLine` 을 숫자 하나로 기대해서다. 원래 화면이 보낸 댓글도 같다).
- 부품과 그 안에 묶인 패키지의 라이선스 고지는 `THIRD-PARTY-NOTICES.md` 의 'Diagram runtime (Mermaid)'에 있다(elkjs 는 EPL-2.0).

## 원래 화면과 다른 점 · 옮기지 않은 것

- 앱 업데이트(Agent-A 앱 자신의 코드를 AI 가 고치는 수정안·미리 보기·적용): 대표 결정(2026-11-16)으로 이 화면에 넣지 않는다.
  원래 Agent-A 화면에서만 쓴다. 그런 딸린 내용이 있는 답에는 '원래 화면에서만 다룬다'고 적어 보인다.
- 본문 고치기의 편집기: 원래 화면은 서식을 바로 그려 주는 편집기(CodeMirror 기반)다. 이 화면은 마크다운 글 입력칸에
  서식 막대(굵게·기울임·취소선·코드·링크·제목·목록·번호·인용·코드 블록)·단축키·미리 보기를 둔다. 저장되는 글은 같은 마크다운이다.
- 빠른 라벨: 고른 글에는 라벨 목록에서 골라 붙인다. 그림 영역에는 원래 화면처럼 '좋아요' 하나만 한 번에 붙인다(원래 화면도 그림 영역에는
  라벨 목록을 두지 않는다. 글을 쓰거나 그림을 붙였으면 눌리지 않는다). 기본 라벨은 우리말로 옮겼고, 고친 라벨은 이 기기 브라우저에만 기억한다.
- 블록의 근거(출처): 보기만 한다(원래 화면도 고치지 않는다). 요약은 직접 고치기에서 고친다.
- 배치 보드: 넓은 화면에서만 그린다. 좁은 화면은 읽는 순서만 바꾼다(원래 화면도 모바일은 읽는 순서를 유지한다).
- 도식의 한 부분에 댓글(원래 화면의 도식 위치 주석): 위 '도식의 한 부분에 댓글'처럼 한다. 원래 화면과 다른 점은 다음과 같다.
  - Graphviz 도식은 그리지 않는다(이 화면은 Mermaid 만 그린다). 원래 화면이 Graphviz 도식에 남긴 댓글은 댓글 목록에서만 읽는다
    (Mermaid 도식에 같은 이름의 부분이 있어도 번호 표시를 붙이지 않는다).
  - 원래 화면은 댓글에 적힌 블록이 문서에 남아 있으면 그 블록에서만 찾는다. 이 화면이 단 댓글에는 블록 이름이 없어 문서 줄로 도식을 가린다:
    줄이 가리키는 도식에 그 부분이 없으면 같은 이름의 부분이 있는 첫 도식에 표시한다.
  - 부분이 사라져 못 찾는 댓글에 원래 화면은 도식 원문의 그 줄에 표시를 둔다. 이 화면은 표시 없이 댓글 목록에만 남긴다.
  - 도식 댓글 칸에 'AI 에 묻기' 단추를 따로 두지 않는다. 이 화면의 댓글은 달면 AI 가 답한다.
  - 한 번에 한 부분만 고른다(원래 화면도 문서 보기에서는 하나만 고른다). 도식 부분에는 빠른 라벨이 없다(원래 화면도 없다).
