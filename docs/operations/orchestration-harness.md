총괄 입력 묶음 세 건과 기존 후속 점검 간격 30초 재사용은 구현 선택이다. 사용자가 지정한 실패 반복 기준 세 번과 구분한다. 짧은 사실 질문은 총괄이 직접 답하고, 자료 작성이나 실행 검증은 직원에게 맡긴다.

담당 직원의 계약에는 해당 직원이 직접 수행하고 검증할 수 있는 결과를 적는다. 다른 담당자의 검토·통합·적용은 앞 단계의 산출물을 입력으로 받는 별도 업무로 연결한다. 상위 업무는 승인된 전체 결과를 추적한다.

직원은 계약 범위에서 고칠 수 있는 실패의 원인을 찾아 수정하고 다시 검사한다. 조건이 남은 채 실행을 마치면 진행 보고의 `continue_work: true`로 이어 할 행동을 기록한다. 이 진행은 실행 보고 의무만 마감한다. 같은 담당자가 재개할 수 있는 업무는 보고가 빠져도 다음 실행에서 남은 조건을 이어 간다. 외부 담당자의 결과나 추가 권한이 필요한 막힘은 총괄에게 전달하고, 같은 검사 실패는 실행마다 한 번씩 세어 세 번째에 총괄이 개입한다.

## 직원이 다음 업무를 받는 과정

직원이 일을 마치거나 유휴 상태가 되면 서버는 이미 배정된 지시를 먼저 확인한다. 이어서 공용 진행판의 `next` 카드 중 확정 계약과 선행 조건을 충족한 카드를 찾는다. 원 담당자가 지정된 검수 보완은 해당 직원에게, 공용 카드는 담당 이름과 역할에 맞는 직원에게 배정한다. 서버는 직원 지시를 만들고 카드를 `doing`으로 옮기는 일을 한 DB 트랜잭션에서 처리한다. 서버를 재시작하면 직원의 기존 터미널과 세션을 먼저 확인하고 이전 전송 기록을 복원한다. 터미널 입력 전에 거절된 지시는 기존 배정으로 다시 보내고, 이전 입력의 수신 여부가 불분명하면 그 직원의 중복 전송을 막는다.

업무가 끝나면 `task_stage_marks`에 완료 근거가 기록되고 연결된 진행판 카드도 `done`으로 이동한다. 이후 검사 결과가 정정되어 업무가 다시 열리면 자동으로 완료된 카드는 이전 칸으로 돌아간다. 수동 보류와 대표의 결정은 해당 업무에 계속 적용된다.

팀 화면의 ‘대표 응답’은 업무에 직접 연결된 열린 결재·대표 할 일, 직원의 승인·선택·로그인, 수동 조치가 필요한 전달을 업무별로 한 번씩 센다. 직원 검수, 총괄의 반복 점검과 내부 막힘은 ‘팀 처리’에서 확인한다. 같은 업무에 결재와 터미널 조치가 함께 있으면 목록 한 행에서 두 곳으로 이동할 수 있다. 프로젝트에만 연결된 전달 알림은 해당 직원의 전달 알림에서 확인한다.

## main 통합과 브랜치 정리

프로젝트 단위의 기존 승인은 대표 인증으로 `POST /api/projects/:id/main-policy`에 등록한다. `origin`은 승인한 GitHub 저장소, `paths`는 제품 디렉터리 목록, `source`는 승인의 출처와 범위다. 서버는 등록한 `policyId`를 반환한다. 일반 푸시 승인을 철회할 때는 같은 프로젝트의 `POST /api/projects/:id/main-policy/revoke`에 이 ID를 보낸다.

서버는 업무의 확정 계약, 등록 워크트리, 원격 저장소, 해당 완료 보고에 연결된 커밋 변경 범위를 대조한다. 일치하면 유효한 계약의 `main_authority`에 출처를 표시한다. 이전 계약 판과 검사 영수증은 그대로 조회할 수 있다. 업무 계약의 main 제외 및 작업 브랜치 한정 조건이 우선한다.

총괄은 해당 저장소에서 승인된 main 통합·일반 푸시의 출처와 범위를 업무 계약의 `main_authority`에 기록한다. 담당자가 현재 계약의 완료 조건을 검사하고 작업 브랜치의 전체 SHA를 보고하면, 하네스가 작업 커밋과 비교 기준을 대조하고 같은 담당자에게 통합 업무를 한 번 배정한다. 브랜치까지만 승인된 업무는 그 브랜치에서 검수를 받는다.

담당자는 최신 원격 main과 작업 커밋을 통합하고 통합판에서 검사한다. 원격 main을 일반 푸시한 뒤 하네스가 통합 전후 원격 조회의 실행 근거와 Git 커밋 포함 관계를 확인한다. 전담 검수 직원은 통합 영수증이 생기면 원격 main의 통합 전후 차이를 읽고, 필요한 경우 같은 도구에서 원래 기능 브랜치의 전체 변경과 대조한다. 병합할 때만 바뀐 파일도 검수에 포함된다. 원격 확인 후 브랜치 정리 업무가 열린다. 정리 담당자는 브랜치 끝점과 다른 작업의 사용 여부를 확인한 뒤 승인 범위에서 처리한다.

검수와 통합은 별도로 진행한다. 검수 직원이 통합 후 결함을 재현하면 기존 완료·통합 이력에 연결된 수정 업무가 원 담당자에게 배정된다. 수신 여부를 확인할 수 없는 검수 지시는 원래 세션에 보존하고 총괄에게 한 번 알린다. 그 세션에 새 입력을 쓸 수 없을 때는 프로젝트당 예비 검수 세션 한 개가 무관한 업무를 받는다. 하네스가 이미 배정한 지시는 전송 시도·실행·수신 기록이 없는 경우에만 예비 세션으로 넘긴다. 예비 검수자는 자신에게 배정된 보고만 판정한다. 이미 수신한 검수 지시에 판정이 없으면 최소 5분 뒤 한 번 더 요청하고, 계속 미처리이면 총괄에게 알린다.

## 저장과 실행 경계

기존 계약에 `inputs`, `outputs`, `constraints`, `exclusions`를 추가한다. 배포된 기억 저장 마이그레이션 v42를 보존하고 계약 확장 v43, 비동기 검수 v44를 뒤에 적용한다. 검수는 업무·보고·계약 판·완료 표시·확인 상태와 알림 전달 ID를 저장한다. v48은 활성 프로젝트마다 전담 직원을 한 명 유지할 수 있게 한다. 새 요청은 전담 직원에게 보내고 이전 전달의 수신 이력은 보존한다.

전달 봉투는 원래 지시를 고치지 않고 실행 당시의 최신 계약을 포함한다. 이후 계약이 바뀌면 오래된 봉투를 재전송하지 않는다. 수신 여부를 읽어 확인하는 경로는 유지하며, 불확실한 과거 입력을 미전달로 바꾸지 않는다.

직원의 검사 통과가 확인되지 않았거나 실행 근거가 미지원이면 자동 완료하지 않는다. 최종 확인 대기는 후속 업무의 차단 조건이 아니다. 승인된 통합 이후에 확인된 결함은 기존 완료 이력에 연결한 별도 업무에서 처리한다.

## 제공자와 운영 적용

제공자별 실제 도구 제한과 검증 범위는 [총괄 실행 권한](conductor-role-policy.md)에 정리했다. Claude와 Codex의 관리되는 총괄은 쉬는 시점에 새 권한으로 같은 대화를 이어 연다. 기존 진행 턴과 승인 창은 강제로 종료하지 않는다. Antigravity는 총괄의 네이티브 권한 제한을 검증할 수 없어 총괄 실행을 보류한다. 전담 검수 직원은 기존 Claude 또는 Codex 설정을 사용하고 제작·배정 권한 없이 검수 근거를 조회한다.

작업 브랜치의 소스 검증과 운영 서비스 반영은 별도 상태다. 운영 적용 전에는 이 문서를 실제 서비스 변경의 영수증으로 사용하지 않는다.
