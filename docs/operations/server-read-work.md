# 웹 조회와 업무 점검의 서버 비용

프로젝트를 열거나 직원 대기열을 확인할 때, 한 번 읽은 업무 근거와 이미 전달된 지시를 반복해서 처리하는 비용을 줄인다. 적용 대상은 IAMCEO의 기존 웹 조회와 서버 점검 경로다.

| 요구사항 | 완료 조건 |
| --- | --- |
| R1. 서버는 한 프로젝트의 상태 응답에서 업무 목록과 팀 배정도를 같은 진행 근거로 만든다. | A1. 업무가 있는 프로젝트의 일반·간략 상태를 각각 한 번 읽으면 전체 진행 근거 조회가 한 번이다. 새 결재를 저장한 다음 응답은 바뀐 단계를 반영한다. |
| R2. 후속 점검은 실행 기준이나 선행 업무를 확인할 때 대기 중인 지시만 상세 조회한다. | A2. 전달 이력이 늘어도 완료된 전달의 본문 조회는 0회다. 앞선 대기 지시 뒤에 이미 전달된 지시가 있어도 계약 확인 대상을 유지한다. |
| R3. 서버는 대기열을 점검할 직원의 ID만 조회한다. | A3. 전역·프로젝트별 조회에서 기존 수신 순서와 중복 제거 결과가 일치한다. 주기 점검과 복구의 보류 처리 차이를 보존하고 수신자 조회에서 전달 본문을 가져오지 않는다. |
| R4. 직원에게 전달할 항목이 실제 업무에 연결될 때 순서 검사를 시작한다. | A4. 업무 없는 직원 알림은 발송 직전까지 프로젝트 업무 순서를 조회하지 않는다. 연결된 지시에서는 선행 업무·중단·승인 상태가 바뀌면 실제 전송을 차단한다. |
| R5. 서버는 후속 업무 후보의 재시도 예정 시각을 프로젝트 단위로 읽고 메모리에서 순서를 정한다. | A5. 후보 정렬 중 업무별 상태 조회는 0회다. 예정 시각이 없는 후보는 생성 시각을 사용하고, 저장된 예정 시각을 바꾸면 다음 점검 순서가 달라진다. |

각 항목은 격리 데이터에서 먼저 비용 초과를 재현하고, 변경 뒤 같은 검사에 기존 기능 검사를 더해 확인한다. 조회 결과는 한 요청이나 동기 판정 안에서만 재사용한다. 운영 연결 끊김의 빈도와 프로세스 분리의 효과는 별도 검증 대상이다.

## 확인 결과

| 업무 | 격리 데이터에서 관찰한 변화 |
| --- | --- |
| 프로젝트 화면 조회 | 일반·간략 응답 모두 한 요청에서 전체 진행 근거를 두 번 읽던 경로가 한 번으로 줄었다. 새 결재 뒤에는 업무 단계가 갱신됐다. |
| 전달 이력 확인 | 업무 80건에 전달된 지시가 한 건씩 있을 때 후속 후보 검색의 과거 본문 조회가 160회에서 0회로 줄었다. |
| 수신 직원 조회 | 직원 6명에게 대기 전달 128건을 배분했다. 수신자 조회가 서버 코드로 가져온 행은 128개에서 6개로, 본문은 2 MiB에서 0바이트로 줄었다. |
| 업무 없는 알림 | 한 건의 발송에서 프로젝트 업무 순서 조회가 5회에서 0회로 줄었다. 같은 직원에게 업무 지시를 보내는 경로에서는 전송 직전의 선행 업무·보류 검사를 통과해야 한다. |
| 후속 점검 정렬 | 같은 업무 240건에서 정렬할 때 개별 상태를 읽던 1,652회가 0회로 줄었다. 이 변경 전후의 전체 점검 SQL 읽기는 각각 2,409회와 758회였다. |

화면 조회는 `tests/task-progress-read-cost.test.ts`, 후속 점검은 `tests/task-continuation.test.ts`에서 재현할 수 있다. 수신자 조회와 알림 발송은 `tests/delivery-read-cost.test.ts`와 `tests/orchestration-completion.test.ts`에서 검증한다.

### 웹 응답과 연결

맥미니의 격리 서버에서 같은 합성 데이터베이스를 복사해 `9bf6df9`와 `e35f9b7`를 비교했다. 업무와 완료 보고 각 240건, 직원 6명, 대기 알림 128건을 넣었다. 1초마다 후속 후보를 점검하는 동안 별도 클라이언트가 웹소켓 연결을 유지하고, 응답 캐시를 무효화한 뒤 간략 `/api/sync` 응답 본문을 끝까지 받는 시간을 쟀다. 실제 직원 실행은 사용하지 않았다.

| 측정값 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 47초씩 두 회차의 HTTP 요청 수 | 423건 | 435건 |
| 응답 시간 중앙값 | 13.1ms | 9.1ms |
| 응답 시간 95백분위 | 35.6ms | 31.9ms |
| 최대 응답 시간 | 94.6ms | 62.7ms |
| 15초 주기 연결 신호 수신 / 예상치 못한 종료 | 6회 / 0회 | 6회 / 0회 |

두 회차는 버전 실행 순서를 뒤집었고 각 버전의 두 회차 표본을 합쳤다. 첫 요청 전 준비 조회 3회는 회차마다 통계에서 뺐다. 이 결과로 확인한 범위는 격리 서버의 조회 비용과 해당 부하에서의 연결 유지다. 운영망의 끊김 여부와 빈도는 배포 뒤 확인해야 한다.

최종 구현 커밋에서 관련 35개 파일의 회귀 검사 669개와 별도 브라우저 팀 배정 화면 검사 10개가 통과했다. Bun 1.3.14에서 타입 검사와 앱 빌드도 통과했다.
