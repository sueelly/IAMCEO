## 원인

1. 보관 409 뒤 재개·재시도 (서버)
   - 보관은 깬 칸을 차례로 끝내며 줄의 전달을 '보관' 보류로 바꾼다. 이때 한 번이라도 시도한 전달(attempts>0)은 결과를 모를 수 있어 건너뛴다.
   - 실제 실행기(herdr·core)가 입력칸이 차 있어 쓰기 전에 거절하면(not_written) 그 전달은 '확인된 미기록'이지만 attempts>0 이라 줄(queued)에 남는다.
   - 다음 칸이 거부해 보관이 409 로 끝나면, 먼저 끝낸 칸은 잠들었는데 줄에 깨움 전달이 남아 틱이 그 칸을 다시 연다(가짜 start 1, Fake.send 시도 1→5).
   - 가짜 실행기의 결과에 효과(deliveryEffect)가 없으면 서버는 결과를 모른다(delivery_unknown 보호 보류). 이 길은 원래대로 보류·재개 0 이 맞다.
2. 연결 중 입력칸이 먼저 보임 (화면)
   - 입력칸·카드 잠금은 연결 상태가 offline 인 채로 1.5초가 지나야 걸렸다. '지금 다시 연결'을 누르면 connecting 이 되어 잠금이 풀리고, 서버가 아직 끊겨 있어도 입력칸이 보였다.
3. 연결 게이트 묶음 3실패 (원인 셋)
   - '직원 상세 연결 안내'·'연결 없음 잠김/초안': 시험의 '연결 안 된 프로젝트' 대역이 옛 /api/bootstrap·/state 응답만 고치고 소켓을 아예 잇지 않았다.
     지금 화면(02b54e8 부터)은 /api/sync 한 번으로 읽고 소켓 hello 가 있어야 online 이다. 그래서 고친 값이 닿지 않고 서버 끊김 안내가 먼저 떴다(시험 대역 문제).
     대역을 고치면 '직원 상세'는 시작 안내 글을 실행 상태 확인(/api/runtime) 전에 읽는 시점 문제가 이어서 드러난다(시험 동기화 문제).
   - '서버 409 복원/첨부': 02b54e8 의 전송 시도(outbox)가 연결 때문에 저장 전에 거부한 409 를 '결과 모름'으로 다뤄 글을 되돌리지 않고, 첨부 거부도 실패 칩으로 남겼다(제품 문제).

## 바꾸는 것

- 서버: DeliveryRecovery.unwritten(id) — 마지막 봉투가 입력 전 거절(rejected)이고 not_received 로 정리됐고 쓰는 중·모름 봉투가 없는 queued 전달만 참.
  sleepMember 의 보관 보류는 이 전달도 보류한다. 모름·받음·확인 중 전달은 그대로 건너뛴다.
- 화면 잠금: online 이 아닌 때(connecting·offline)가 유예(1.5초)보다 길면 잠그고, online 이 될 때까지 풀지 않는다. 유예 안에 돌아오는 잠깐은 그대로.
- 화면 전송: send 가 연결 게이트 409 를 SubmissionRefused 로 넘긴다. 이 화면에서 처음 보낸 새 id 이고 입력칸이 그대로면 원래 글·대상·첨부를 되돌리고 시도를 지운다.
  바뀐 입력칸·이미 나간 id 의 재시도는 되돌리지 않고 '같은 내용 재시도'로 남긴다. 처음 보내는 중인 시도는 결과 전까지 따로 보이지 않는다(sending).
  연결 게이트로 거부된 첨부는 칩을 남기지 않고 문구만 보인다(02b54e8 전 동작).
- 시험 대역: openDisconnected 가 /api/sync 의 요약·프로젝트 연결 값도 고치고, 소켓은 hello 만 잇는다. '직원 상세'는 실행 상태 확인 뒤 시작 안내를 읽는다. 단언은 그대로다.
