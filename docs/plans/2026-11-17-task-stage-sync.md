## 바꿀 것
1. 업무 단계(서버 한 곳에서 계산, `server/task-progress.ts`): 같은 업무 id 의 보고·검사·계약 판정·열린 결재/할 일·보류 전달·승인 창·총괄 단계 표시로 단계·원인·다음 차례를 정한다. 팀 목록과 대화가 같은 값을 쓴다.
   - 단계: 진행 중, 대표 차례, 승인 창 대기, 전달 보류, 총괄 점검, 고칠 것, 확인 대기, 작성자 납품, 검토 중, 합치기 대기, 메인 합침(통합 뒤 확인), 반영됨, 보류, 완료.
   - 막힘 원인: 검사 실패(기술) · 실행 안 함만 남음(시험·검토·적용 대기) · 검사 없음(원인 미확인) · 결재/할 일(대표) · 승인 창 · 전달 보류(unknown·보호, 자동 재생 안 함).
   - 완료는 끝 단계다. 늦은 막힘·중복·순서가 뒤바뀐 이벤트가 완료를 되돌리지 않는다(총괄이 다시 열 때만). 화면은 판 번호(`rev`)가 낮은 단계를 버린다.
2. 총괄 단계 표시(`task_stage` 도구, 총괄만): 검토 맡김·메인 합침(SHA 근거)·대표 화면 반영·완료·보류·다시 열기. 완료는 열린 결재/할 일이 없고, 묶이는 계약이면 지금 판의 통과 완료가 있고 그 뒤 실패 보고가 없으며, 코딩 계약이면 메인 합침 표시가 있어야 받는다. 계약 없는·브랜치 없는 업무는 작성자 완료가 곧 완료다.
3. 반복 감시(`task_watch`): 업무마다 막힘의 시작 시각·시도 수·실패 지문·같은 실패 연속 수·마지막 진척을 DB 에 둔다(재시작에도 남음). 같은 실패 3번 또는 2시간 진척 없음(직원 쪽 단계일 때만)이면 한 번 멈춘다: 단계가 '총괄 점검'이 되고 총괄에게 원인·한 일·남은 조건을 한 번 보낸다. 그 뒤 같은 실패의 막힘은 총괄을 깨우지 않는다. 총괄이 다시 열거나 통과 완료가 오면 풀린다.
   - 3번은 기존 재시도 상한(설정·병렬 오류 3번, 전달 3번)과 같다. 2시간은 이 프로젝트의 한 차례 보완(수정·시험·올리기) 관찰 길이에서 고른 구현 기본값이다. 대표 정책이 아니고 `OrchestratorTimings`로 바꿀 수 있다. 기존 시간·예산·재시도 한도는 늘리지 않는다.
   - 새 자동 재전송은 만들지 않는다. 기술 재시도는 기존 전달 복구(같은 전달 id, 3번)만 쓴다.
4. 완료 알림(`task_notices`): 완료 단계가 될 때 한 번 만든다(완료 표시 id 로 하나). 결재함 '결재할 항목' 위에 읽기용으로 보이고, '확인'은 서버에 남아 두 화면이 같다. 결재 수·승인 입력으로 세지 않는다.
5. 진행판 연결: `work_set`이 `task_id`로 기존 업무를 가리킬 수 있다. 팀 목록은 진행판 항목(연결된 업무의 단계로) + 진행판에 없는 대화 업무(완료 전)를 같은 단계로 보인다.
6. 대기열: 직원에 `heldCount`를 더해 팀 카드에 '대기 N · 보류 M'으로 나눠 보인다(옛 `queuedCount`는 그대로, 네이티브는 이번에 안 바꿈).
7. 보고 끝 단계 줄: 총괄에게 가는 보고에 '업무 단계: … · 다음 차례'를 붙여 납품 뒤 차례가 기억이 아니라 보고에 남게 한다.
8. 저장소 최적화 도구(`scripts/optimize-storage.ts`)의 '안 바뀐 데이터' 대조를 최적화 전 표·칸으로 한정한다. v36 이 더한 빈 표·null 칸 때문에 기존 데이터가 같아도 거절되던 것을 고친다(기존 칸 값의 변화는 그대로 잡는다).
