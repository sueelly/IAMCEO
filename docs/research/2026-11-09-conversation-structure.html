지금 구조에서 이미 되는 것과 빈자리

이미 갖춘 바탕

프로젝트별 총괄과 직원, 프로젝트 밖 일을 받는 본사 AI, 결재함, 자료 보관, 전달 대기열이 있습니다. 네이티브 앱에는 프로젝트 전체 대화와 직원별 대화 보기도 있습니다.

따라서 본사와 직원별 대화를 새 개념처럼 추가할 필요는 없습니다.

업무를 식별하는 연결이 부족

확인한 메시지 모델은 프로젝트·발신 직원·수신 직원에 연결됩니다. 업무별 대화 ID는 없습니다. 진행판의 업무도 메시지·결재·자료와 업무 ID로 직접 연결되어 있지 않습니다.

직원 한 명이 서로 다른 조사 두 건을 맡으면, 직원별 보기만으로 두 대화를 구분하기 어렵습니다.

근거: 현재 작업 트리의 README.ko.md, shared/types.ts의 Message·WorkItem·Decision·FileDoc, native/Sources/IAMCEO/Views/ChatView.swift의 ChatScope. 네이티브는 직원별 필터를 제공하며, 확인한 웹 Thread.tsx는 프로젝트 메시지를 표시합니다. 이 관찰은 로컬 코드 기준이며 설치된 앱 버전의 동작 검증은 아닙니다.

공개 사례에서 가져올 원칙

오픈소스 · Paperclip

업무에 대화와 진행을 붙인다

공식 Issues 문서는 업무마다 상태·담당자·댓글 대화를 두고, 프로젝트나 담당자로 목록을 거르게 합니다. 새 업무에서 No project(프로젝트 없음)도 선택할 수 있습니다. 별도 Decisions 화면은 사람이 결정할 사안을 모읍니다. [1] [2]

적용 제안: 대화의 기준을 업무로 두고, 결재는 한곳에서 처리하되 원래 업무로 돌아가는 링크를 둡니다.

오픈소스 · OpenClaw

대화 주소와 AI 문맥을 구분한다

공식 문서는 세션을 로컬 모델 문맥, conversation을 특정 상대·채널·스레드의 주소로 구분합니다. 둘은 연결되지만 같은 개념은 아닙니다. [3]

적용 제안: 대표가 보는 업무 대화의 수명을 CLI 세션의 수명과 분리합니다. 모델 교체 뒤에도 대화는 유지하고 필요한 문맥을 인계합니다.

개인 운영 · Peter Steinberger

3~8개 병행에도 주력 업무는 분명하게

2025년 개인 작업기에서 에이전트 3~8개를 병행하며, 주력 기능 하나와 작은 주변 업무를 함께 다룬다고 설명합니다. 관련 작업을 대기열에 넣는 방식과 별도 창에서 조사하는 방식도 소개합니다. [4]

적용 제안: 업무를 여러 개 접수할 수 있어야 하지만, 모든 업무를 즉시 실행할 필요는 없습니다. 대화 목록에서 실행 중과 차례 대기를 구분합니다.

개인 운영 · Simon Willison

검토하는 사람의 처리량이 기준

2025년 작업기에서 큰 변경은 한 번에 하나씩 검토하면서, 조사·작은 유지보수·명확히 정한 업무는 병행한다고 설명합니다. 결과를 검토할 부담이 병행 작업의 제약이라는 관찰입니다. [5]

적용 제안: 홈은 대화량보다 대표가 답할 것, 막힌 것, 결과가 나온 것을 먼저 보여줍니다.

위 ‘사례’는 출처에서 확인한 사실이고 ‘적용 제안’은 IAMCEO를 위한 해석입니다. 개인 개발 작업기 두 편은 1인 기업 전체 운영이나 비개발 업무에서의 효과를 검증한 자료가 아닙니다. 당시 모델 성능·요금·현재 제품 기능의 근거로도 사용하지 않았습니다.

출처 간 차이와 확인 한계

Paperclip의 Projects 문서는 모든 issue가 프로젝트에 속한다고 쓰지만, Issues 문서는 ‘No project’를 명시합니다. 문서 간 차이가 있어 내부 필수 관계를 단정하지 않았습니다. 이 자료에서는 확인 가능한 사용자 선택 흐름만 참고합니다. [6]

전달받은 withhind.dev는 검색 결과를 찾지 못했고 직접 접속도 DNS 조회에 실패했습니다. 글 내용과 작성자를 확인하지 못해 근거로 인용하지 않았습니다. 이 세션에는 board 도구가 노출되지 않았으며 인증된 도구 목록에서도 제외되어, 실시간 대화·열린 결재·작업 목록은 조회하지 못했습니다. 기존 맥락은 제공된 인계 내용과 로컬 코드로 확인했습니다.

  • 프로젝트 종합 대화: 목표 조정·우선순위·여러 업무를 아우르는 논의를 합니다. 업무의 상세 진행을 모두 복제하지 않고 요약과 링크로 연결합니다.
  • 업무별 대화: 독립적으로 끝낼 수 있는 요청을 단위로 만듭니다. 세부 질문·수정·검토는 같은 대화에 잇고, 별도 결과와 종료 조건이 생길 때 나눕니다.
  • 직원별 보기: 팀 화면의 담당자 확인 경로로 유지합니다. 대표의 기본 탐색 기준은 업무 제목으로 둡니다.
  • 프로젝트 밖 일반업무: 별도 프로젝트 생성 없이 본사 아래에서 시작합니다. 화면에서는 ‘일반업무’, 내부에서는 기존 본사 소속으로 관리할 수 있습니다.

이 구조는 기존 홈·결재함·팀·대화·자료 안에 배치할 수 있습니다. 새 상위 메뉴를 늘릴지 여부는 화면 설계 때 정하면 됩니다.

‘대화 구조 조사’를 열어 “두 번째 안을 더 설명해 줘”라고 말하면

해당 업무의 대화와 자료를 근거로 답합니다. 다른 업무를 맡던 같은 직원에게 전달되더라도 그 업무의 문맥을 지정합니다. 업무를 선택하지 않은 곳에서 “그거 진행해”처럼 대상이 모호하면, 대상부터 확인하고 실행합니다.

대화가 섞이지 않게 하는 운영 규칙

  1. 접수와 실행을 구분합니다. 여러 요청은 각각 기록하고 제목을 보여줍니다. 실행 자리가 부족하면 차례 대기로 표시합니다. 대화를 다섯 개 만든다고 세션도 다섯 개 띄우는 방식은 아닙니다.
  2. 후속 지시의 대상을 전송할 때 고정합니다. 업무·대화·받는 대상을 함께 기록합니다. 전송 뒤 다른 대화를 열거나 담당자가 바뀌어도 전달 대상이 조용히 바뀌지 않아야 합니다.
  3. 수정 지시와 다음 일을 구분합니다. “지금 하는 일 수정”과 “끝난 뒤 할 일”을 대기열에 다르게 기록합니다. 같은 업무의 후속 말은 이어 보내고, 무관한 새 일은 분리합니다.
  4. 결재 답은 물었던 안건으로 돌아갑니다. 업무와 결재 ID를 연결하고, 원래 물은 담당자에게 답하는 기존 원칙을 유지합니다. 담당자·세션이 바뀌어도 승인 대상과 대표 원문을 보존하며, 현재 대화 선택만으로 답을 전달하지 않습니다.
  5. 본사에서 프로젝트로 옮겨도 기록을 잇습니다. 반복 운영, 여러 담당자, 별도 작업 폴더·목표가 필요해지면 승격을 제안합니다. 대표가 정한 뒤 업무 ID와 원래 주소·자료·결재 연결을 유지하며 옮깁니다. 소속 변경이 파일 접근 권한이나 외부 작업 승인까지 넓히지는 않습니다.
  6. 완료와 재개를 구분합니다. 완료 업무는 보관해 찾을 수 있게 하고, 같은 결과의 수정 요청이면 재개합니다. 독립된 새 결과물이면 새 업무를 만들고 원래 업무를 연결합니다.

홈 알림은 대표 차례·막힘·완료를 우선합니다. 세부 도구 실행과 반복 진행 보고는 업무 안에서 접어 보고, 중요도 기준은 사용해 보며 조정합니다.

화면만 나누면 AI 문맥은 여전히 섞일 수 있습니다

현재 직원별 보기는 메시지를 걸러 보여주는 방식입니다. 업무별 필터를 추가하는 것만으로 모델 내부 문맥이 분리되는 것은 아닙니다. 업무 대화와 실행 세션 사이의 명시적인 연결이 함께 필요합니다. 대화·세션 구분은 OpenClaw 사례에서 참고한 원칙입니다. [3]

업무에 남겨야 할 기록

대표의 목적·완료 기준, 현재 상태와 다음 단계, 대표가 내린 결정의 원문 링크, 최신 결과물, 미해결 질문을 남깁니다. 요약은 원문을 대체하지 않고 원문을 찾는 길잡이로 씁니다.

세션을 이어 쓰거나 바꿀 때

같은 업무는 가능한 한 기존 실행 문맥을 이어 씁니다. 다른 업무로 전환하거나 제공자를 바꾸면 해당 업무의 인계 기록을 불러옵니다. 무관한 전체 대화를 한꺼번에 넣지 않습니다.

구현 검토 시 필요한 연결

최소한 메시지·결재·자료·전달에서 안정적인 업무 ID를 참조해야 합니다. 진행판 WorkItem을 업무 원장으로 발전시킬지, 별도 업무 개체를 만들지는 구현 전에 결정합니다. 업무 1개에 기본 대화 1개를 두는 것으로 시작하면 복잡도를 줄일 수 있습니다.

직원 ID·CLI 세션 ID·업무 ID는 수명이 다르므로 분리합니다. 기존 데이터는 먼저 ‘기존 프로젝트 대화’로 보존하고, 과거 메시지 전체를 AI 추측으로 재분류하지 않습니다. 전달 재시도·결재 답·담당자 변경 시에도 같은 업무 참조를 검증해야 합니다.
