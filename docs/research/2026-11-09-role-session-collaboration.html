직원을 두는 세 가지 방법

비교는 IAMCEO의 사용 목적에 대한 설계 판단입니다. 효과·비용을 실험으로 측정한 결과는 아닙니다.

대안어떻게 작동하나좋은 경우부담과 불리한 경우
A · 고정 직원
전용 세션 중심		조사 직원·개발 직원마다 전용 세션을 이어 씁니다. 담당자를 골라 일을 맡깁니다.업무가 적고 같은 담당자의 긴 대화를 이어가는 사용, 직원 성격을 직접 다듬는 재미가 중요한 경우담당자가 바쁘면 줄이 길어집니다. 여러 업무가 같은 세션에 섞이거나 직원 2호·3호를 관리하게 됩니다.
B · 업무별 실행
고정 직원 최소화		새 업무마다 필요한 실행 세션을 만들고 공통 기본 지침을 줍니다. 업무 기록이 연속성을 책임집니다.일회성·다양한 요청이 많고 역할별로 축적할 방식이 아직 없는 초기 제품같은 전문 지식·판단 기준을 반복해서 불러와야 합니다. 역할 경험을 재사용하려면 별도 체계가 생겨 C안에 가까워집니다.
C · 지속되는 역할
업무별 실행 분리
추천		역할은 판단 기준과 검증된 지식을 유지합니다. 업무별 세션은 필요할 때 연결하고, 기본 화면에는 업무만 표시합니다.반복되는 조사·구현·문서 업무가 섞이고, 담당 교체와 경험 재사용이 필요한 경우역할 기억의 범위를 정하고 갱신 근거를 관리해야 합니다. 요청이 드물면 B안보다 구조가 무겁습니다.
C안을 작게 시작하는 것이 추천입니다.

대표에게 직원 명부를 관리하게 하지 않으면서, 대표가 원하는 ‘일하는 방식이 쌓이는 담당 역할’을 유지할 수 있습니다. 처음에는 조사·구현처럼 실제 반복 수요가 있는 역할만 두고 세션 하나로 끝나는 일을 기본으로 삼습니다. 역할을 많이 만드는 것이 목표는 아닙니다.

C안이 불리할 때: 하루 몇 건의 서로 무관한 짧은 질문만 처리한다면 B안이 단순합니다. 특정 직원과의 장기 대화 자체가 핵심 경험이라면 A안이 더 직관적입니다. 공유 기억의 검증 부담을 감당하기 어렵다면 C안을 서둘러 도입할 이유가 없습니다.

최소한의 네 가지 단위로 시작합니다

프로젝트·본사는 기존 묶음으로 유지합니다. 새 대화방·부서·지식 관리자 등을 각각 독립 체계로 늘리기보다, 업무 안에 대표 대화와 협업 기록을 둡니다.

업무
대표가 보는 대화 포함		접수부터 완료·보관·재개까지. 프로젝트 또는 본사에 속함. 기본 대화 1개, 담당 역할 1개, 실행 여러 개 가능결과의 기준과 최종 책임을 기록합니다. 담당자·모델이 바뀌어도 같은 업무 ID와 주소를 유지합니다.
역할
화면의 ‘직원’은 선택 표현		여러 업무에 걸쳐 유지. 한 역할이 여러 세션을 운용할 수 있음판단 기준·전문성·허용 범위·검증 지식 참조를 가집니다. 역할 자체가 항상 켜진 AI 프로세스일 필요는 없습니다.
실행
CLI 세션과 실행 이력		한 업무의 특정 작업 동안. 같은 업무에서는 세션 재개 가능, 제공자 교체 때는 새 세션입력·작업 범위·도구·자원 한도·사용 지식 버전·결과를 기록합니다. 한 실행의 활성 문맥은 한 업무에만 묶습니다.
지식 항목
범위와 버전이 있는 기록		업무보다 오래 유지할 수 있으나, 검토일·유효 범위·폐기 조건을 둠근거가 있는 사실·작업 방법·검증 결과를 보관합니다. 초기에는 문서와 목록으로 충분하며 별도 검색 인프라는 필수가 아닙니다.

‘역할이 세션을 만든다’의 실제 뜻: 그 업무를 맡은 주담당 실행이 필요성을 판단해 추가 실행을 요청하고, 서버가 정해진 한도와 허용 범위를 확인해 연결합니다. 역할 밖에 세션을 관리하는 AI를 또 하나 반드시 두는 뜻은 아닙니다. 승인된 한도 안에서는 대표가 매번 직원·세션·모델을 고르지 않도록 설계할 수 있습니다.

장기 역할 설정과 개별 실행 문맥을 분리하는 근거로 Claude Code의 사용자 정의 subagent 설정·개별 context·지속 memory 범위를 참고했습니다. 그대로 IAMCEO 기능으로 옮길 수 있다는 뜻은 아닙니다. [1]

공유할 기억과 업무에 남길 문맥

범위공유해 가져올 것범위를 넘기지 않을 것
업무현재 목표·진행·판단 근거·미해결 질문·대표 승인 원문 링크를 같은 업무의 실행끼리 공유다른 업무의 승인 근거로 재사용하지 않음. 임시 가설은 확정 사실과 구분
프로젝트확인한 제품 용어·구조·작업 제약. 근거·확인일을 붙여 선택해서 불러옴일반업무나 다른 프로젝트에 해당 사실이 똑같이 적용된다고 가정하지 않음
역할 + 적용 범위검증한 조사 방법·검토 기준. 프로젝트 한정 경험은 그 프로젝트에서만 재사용실패 경험 한 번으로 모든 업무의 방법을 바꾸지 않음. 주관적 판단과 대표 결정 구분
공통대표가 명시한 지속 선호와 범용성이 따로 검증된 방법특정 업무의 조건·예외·승인을 공통 지침으로 확대하지 않음

업무 대화 안의 기억과 여러 대화에 걸친 기억을 범위로 나누는 원칙은 LangChain 공식 Memory overview를 참고했습니다. 구체적인 범위·갱신 절차는 우리의 제안입니다. [2]

담당자·모델 교체 때도 연결은 업무에 남깁니다.

새 실행에 업무 요약과 원문·자료·열린 결재 참조를 인계합니다. 결재에는 업무·질문·대상 행위·현재 담당 연결을 보존합니다. 단순 인계라면 같은 답을 이어 처리하고, 실제 승인 대상이 바뀌면 다시 판단받습니다. 자료와 후속 지시는 현재 선택된 화면이나 옛 세션 ID만으로 찾아 보내지 않습니다.

모든 말을 총괄에게 보내 다시 전달받을 필요는 없습니다. 같은 업무의 담당 실행끼리는 질의·검토·인계를 직접 주고받고, 재사용할 결론과 근거를 공유 업무 기록에 남기는 방식을 제안합니다. 다른 세션에 메시지를 보내는 기능 자체는 Claude Code 공식 문서에서도 확인됩니다. 전체 문맥이 자동으로 함께 옮겨지는 것은 아닙니다. [3]

종합과 충돌만 보고

주담당이 최종 결과를 책임집니다. 업무 범위나 다른 일의 우선순위와 충돌하면 총괄에 올립니다.

  • 직접 해결: 같은 업무 안의 사실 확인·자료 요청·검토 의견. 메시지에는 업무 ID, 목적, 필요한 답, 종료 조건을 붙입니다. 총괄 참조는 기본값으로 강제하지 않습니다.
  • 총괄에게 올림: 다른 업무의 일정·자원 침범, 같은 파일 변경 충돌, 합의하지 못한 선택, 목표·완료 기준 변경 필요. 대표 결정이 필요한 부분은 총괄도 대신 정하지 않습니다.
  • 서버가 처리: 출처 표시, 접근 범위, 정확한 수신 대상, 중복 전달 방지, 실행 수·횟수 한도. 다른 직원의 메시지를 대표 승인으로 표시하지 않습니다.

계속 회의하는 낭비를 막는 최소 규칙

추가 세션 요청에는 왜 기존 실행으로 부족한지와 기대 결과를 적습니다. 초깃값 제안은 협업 질의·답변 1회, 미해결이면 보완 1회입니다. 그래도 답이 안 나면 논쟁을 이어가기보다 쟁점과 근거를 남겨 주담당 또는 총괄에게 올립니다. 실제 횟수·시간·사용량 한도는 검증 때 조정합니다.

주담당 역할과 현재 주담당 실행을 한 업무에 하나씩 지정합니다. 협업 담당은 자기 결과의 근거를 책임지고, 주담당은 채택·보류 이유와 최종 보고를 책임집니다. 동시에 같은 내용을 고칠 때는 서버가 갱신 충돌을 알리고 주담당이 결론을 정리합니다. 세션을 늘려도 자기 복제와 재위임이 끝없이 이어지지 않게 합니다.

Anthropic의 다중 에이전트 연구 사례는 위임 범위·결과 형식·노력 한도의 중요성과 과도한 생성·소통 비용을 설명합니다. 그 사례의 성능·사용량 수치를 IAMCEO에 일반화하지 않았습니다. [4]

자가개선은 ‘잘 기억하기’보다 한 단계 더 필요합니다

기억 축적

“이번 업무에서 X를 시도했고 Y가 실패했다”를 남겨 다음 실행이 맥락을 알게 합니다. 다른 상황에서도 X가 나쁘다는 결론은 아직 아닙니다.

작업 방법 개선

“이 조건에서는 X 대신 Z를 쓰면 결과가 나아진다”는 후보를 만들고, 정한 사례와 기준으로 비교한 뒤 해당 범위에만 적용합니다.

  1. 근거 수집 → 업무 회고

    대표의 수정 요청, 실패 결과, 실제 검사 결과를 링크합니다. 무엇이 잘못됐는지와 어떤 조건에서 일어났는지 기록합니다.

  2. 개선 후보 → 시험 기준

    바꿀 방법 1개, 기대 효과, 적용 역할·프로젝트, 기존 버전, 실패 시 되돌릴 버전을 정합니다. 후보는 즉시 공통 지침이 되지 않습니다.

  3. 기존 방법과 비교 시험

    동일 조건의 사례와 별도로 남겨 둔 확인 사례를 사용합니다. 결과 품질·대표 수정량·시간·사용량을 함께 봅니다. 편차가 크면 반복 확인합니다. 시험은 별도 승인된 검증 단계에서 수행할 제안이며 이번에는 실행하지 않았습니다.

  4. 검토 → 좁은 범위 적용

    코드는 실제 검사 결과, 조사는 출처 일치·요구 범위 충족, 문서는 명시한 기준과 대표의 표본 검토로 확인합니다. 다른 에이전트의 평가는 보조 근거이며 서로의 동의만으로 채택하지 않습니다.

  5. 적용 후 관찰 → 되돌리기

    사용한 지식·방법의 버전을 실행 기록에 남깁니다. 기준 미달이면 이전 버전으로 돌아가고 원인과 영향을 적습니다. 역할별로 따로 검증한 경험을 곧바로 모든 역할에 적용하지 않습니다.

처음 자동화할 범위는 ‘개선 후보 작성’까지가 적절합니다.

최소 검증판에서는 후보를 자료로 남기고, 적용은 대표가 정한 뒤 진행합니다. 장래에는 대표가 미리 허용한 범위·평가 기준 안에서 좁은 작업 방법을 자동 적용할 수도 있습니다. 권한 확대·새 외부 접근·대표 결정 변경은 별도 판단으로 남깁니다. 에이전트가 자기 평가 기준까지 바꿔 통과시키지 않도록 합니다.

평가에서 실제 결과와 실행 기록을 구분하고, 코드 검사·모델 평가·사람 판단을 조합하며 기존 동작의 퇴행도 확인하는 근거는 Anthropic의 공식 평가 글입니다. 이 글이 IAMCEO의 자가개선 효과를 검증한 것은 아닙니다. [5]

총괄은 여러 업무 사이의 판단을 책임집니다

총괄은 항상 켜져서 모든 대화를 읽는 전담 세션일 필요가 없습니다. 역할은 유지하되, 새 복합 요청·우선순위 충돌·막힘·결과 종합이 필요할 때 관련 요약과 원문 링크를 보고 판단하는 구조를 제안합니다.

영역총괄 또는 주담당의 판단서버의 정해진 처리
대표 의도·업무 경계총괄은 복합 요청을 나누고 완료 기준을 해석합니다. 중요한 모호함과 범위 변경은 대표에게 확인합니다.대표 원문·업무 ID·수정 이력을 보존하고 정확한 업무에 연결합니다.
우선순위·상호 의존총괄은 어떤 일을 먼저 할지, 의존성이 무엇인지 판단하고 충돌을 조정합니다.정해진 대기 순서와 선행 조건을 적용하고 상태 변화를 알립니다.
담당·추가 실행총괄은 낯선 복합 업무의 담당을 정합니다. 주담당은 같은 업무 안의 협업 필요성을 판단합니다.기존 담당·명시된 규칙에 따른 기본 연결, 중복 방지, 가용 실행 수·자원 한도·허용 범위를 확인합니다.
도구·권한·결재주담당이 필요한 행동을 판단합니다. 총괄은 대표 승인을 대신하지 않습니다.미리 정한 실행 정책과 승인 상태를 검사하고, 결재 답을 정확한 질문·업무에 전달합니다.
결과 종합주담당은 업무 결과를 책임집니다. 총괄은 여러 결과가 대표 목표를 함께 충족하는지 판단하고 부족·충돌을 보고합니다.상태·자료·결재를 한 화면에 모읍니다. 전달 완료와 업무 완료를 서로 다른 상태로 보존합니다.

작은 일은 바로 보냅니다

기존 업무의 수정은 현재 주담당으로 연결합니다. 범위가 명확한 일회성 요청은 미리 정한 기본 역할로 보내고, 총괄의 별도 AI 호출을 생략할 수 있습니다.

복합·모호한 일은 총괄이 봅니다

업무 경계가 불명확하거나 여러 역할·프로젝트의 우선순위를 바꿔야 하면 총괄이 판단합니다. 서버의 고정 분류가 틀릴 때도 이 경로로 올립니다.

즉, 총괄의 가치는 메시지를 전달한 횟수보다 대표가 일 전체를 다시 설명하지 않아도 목표와 순서가 맞게 유지되는가로 봅니다. 지금 적용되는 ‘총괄은 조사·구현을 직접 하지 않는다’는 역할 지침은 그대로이며, 위 경로 축소는 장래 제품 제안입니다.

프로젝트 업무 3개 + 밖의 업무 2개가 이어지는 한 흐름

아래는 제안 구조의 가상 시나리오입니다. 실제로 업무·직원·세션을 생성하거나 실행한 현황이 아닙니다. 문서 검토인 이번 실행은 비서 한 명이 순차 진행했습니다.

  1. 대표가 프로젝트 대화에 세 일을 말합니다.

    “연동은 계속하고, 대화 구조를 검토하고, 소개 글도 준비해 줘.” 총괄 역할이 세 업무의 경계를 확인합니다. 예시 응답은 “세 업무로 나눴습니다. 연동·구조 검토를 진행하고, 소개 글은 검토 결과가 나온 뒤 이어갑니다.”입니다.

  2. 본사에 프로젝트 밖 요청 두 개를 말합니다.

    출장 동선 조사와 견적 비교가 일반업무 대화로 접수됩니다. 기존 프로젝트 폴더나 기술 맥락을 자동으로 가져오지 않습니다. 별도 프로젝트를 만들 필요도 없습니다.

  3. 역할과 세션을 연결하고 필요한 협업만 요청합니다.

    조사 역할은 대화 구조와 출장 동선에 각각 별도 세션을 연결합니다. 같은 역할이지만 업무 문맥은 분리됩니다. 연동 업무의 주담당은 구조 검토 쪽에 “현재 전달 방식과 충돌하는 제안이 있는가”를 좁게 질의하고 근거를 받습니다. 소개 글은 검토 요약이 준비될 때까지 기다립니다.

  4. 자료·결재·후속 지시가 업무로 돌아옵니다.

    대표는 ‘견적 비교’ 카드의 조건을 정하고, 답은 그 업무로 전달됩니다. 구조 검토를 열어 “둘째 안을 더 설명해 줘”라고 하면 해당 대화로 이어집니다. 담당 실행이나 모델이 교체돼도 업무 기록과 자료 주소는 유지합니다.

  5. 결과를 종합하고 경험을 다음 업무에 남깁니다.

    각 주담당이 결과와 근거를 보고합니다. 총괄은 소개 글이 이전 결론을 반영했는지 등 업무 사이의 연결만 종합합니다. 조사 역할은 “비교 자료의 출처 확인일을 빠뜨렸다”는 대표 피드백을 개선 후보로 적습니다. 검증과 채택이 끝난 뒤에만 다음 조사에 쓸 공통 방법으로 올립니다.

기본 사용: 대표는 업무 제목을 고르고 말합니다. 매번 직원·세션·모델을 고를 필요가 없습니다. 개입할 때: 상세에서 담당 역할, 왜 세션을 나눴는지, 진행·대기·사용량, 사용한 지식 버전, 협업 근거를 보고 특정 역할 지정·우선순위 변경·일시중지를 할 수 있도록 제안합니다.

가장 작게 검증할 범위와 남겨 둘 질문

다음 검증을 하기로 정한다면, 처음부터 직원 명부·전체 기억 체계를 바꾸기보다 조사 역할 하나가 프로젝트 업무와 본사 일반업무를 분리해서 다루는 경우부터 보는 것이 적절합니다.

  • 화면 검토: 앞의 다섯 업무를 예시 데이터로 놓고, 직원 선택 없이 하던 일·결재·결과를 찾을 수 있는지 확인합니다. 이 단계에는 실제 세션 자동 생성이 필요 없습니다.
  • 후속 실행 검증: 별도 착수 결정 뒤 조사 역할 1개·독립 업무 2개·작은 실행 수 한도로 확인합니다. ‘진행 중 역할의 두 번째 세션’과 ‘하나의 세션에서 서로 다른 업무 혼합’을 구분해 검증합니다.
  • 협업 검증: 질의·답 1건, 담당 교체·모델 교체 인계, 열린 결재의 답 전달을 각각 확인합니다. 기존 결재·자료·원문 링크가 유지돼야 합니다.
  • 학습 검증: 개선 후보 1개를 기록하고 기존·후보 방법의 결과를 비교합니다. 채택 전 자동 기억 갱신은 하지 않고, 범위와 버전·되돌리기 근거를 확인합니다.

측정할 것은 잘못 연결된 지시·결재, 문맥 혼입, 중복 세션·질의, 결과 찾는 시간, 대표 수정량, 실행 사용량입니다. 작은 검증에서 문제가 없었다는 사실만으로 전체 품질 향상을 보장하지 않습니다. 개발 일정·사용량 예산·구현 비용은 아직 산정하지 않았습니다.

다음 논의에서 대표에게 남겨 둘 핵심 질문 하나

“계속 경험을 쌓는 역할의 일하는 기준을 대표가 직접 다듬고 싶은가, 아니면 업무와 결과만 보고 싶고 역할 관리는 맡기고 싶은가?”

이 답이 역할을 대표 화면에 얼마나 드러낼지와, 처음부터 역할별 경험 관리를 둘지의 우선순위를 바꿉니다. 아직 어느 답도 가정하지 않았으며, 이 문서는 선택·구현 승인을 요청하거나 확정한 문서가 아닙니다.

앞선 대화 구조 사례 조사를 반복하지 않고, 역할·기억·협업·평가에 필요한 공식 원문만 보강했습니다. 아래는 공개 사례의 사실이며 위의 운영 단위·한도·채택 절차는 IAMCEO를 위한 설계 제안입니다.
