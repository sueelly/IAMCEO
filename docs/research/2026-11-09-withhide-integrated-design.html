전체 제안을 담은 최신 논의 자료구조 선택·구현 미승인역할 관리 선호 답변 대기
직원은 필요한가

고정 직원 관리는 선택으로

대표의 기본 화면에는 업무와 결과를 둡니다. 내부의 역할·주담당 책임은 남기고, 상세에서 확인·조정하게 합니다.

필요한 조사·실행·검토 문맥을 분리하되, 세션 수·사용량·권한의 미리 정한 한도를 지킵니다.

소통과 자가개선

직접 협업하고 검증한 지식만 재사용

직원별 비공개 기억에만 의존하지 않습니다. 업무 기록·근거·자료를 공유하고 개선 후보는 시험 뒤 좁게 적용합니다.

총괄은 무엇인가

목표·우선순위·충돌·종합 담당

모든 메시지의 중계자가 될 필요는 없습니다. 단순 업무는 바로 담당으로, 여러 업무의 조정은 총괄로 보냅니다.

hide의 단위기존안 재평가대안 비교추천 구조협업·학습총괄과 서버5개 업무 흐름검증·남은 쟁점

hide가 보여주는 것은 ‘프로젝트 밖의 또 다른 폴더’만이 아닙니다

바로잡은 withhide.dev 공식 사이트를 실제로 열어 읽었습니다. 공식 소개는 여러 코딩 에이전트를 함께 운용하며 사람이 판단할 것만 우선 올리는 제품이라고 설명합니다. Conductor의 mission 실행, 부모·자식 에이전트, Projects·Tasks·PRs 보기, Hide AI와 Project Memory를 구분합니다. [H1]

‘프로젝트 외의 다양한 단위’는 아래의 서로 다른 관점으로 확인됩니다. 모두 같은 층위의 업무함도 아니고, Project → Mission → Task → Plan 순서로 항상 포개지는 고정 계층도 아닙니다.

정확한 이름공개 원문에서 확인한 용도·관계IAMCEO에 적용할 해석
Projects
Workspace / checkout		Projects는 체크아웃과 그 안의 에이전트를 묶어 보여줍니다. Workspace 경로는 project / checkout이며 Git이 아닌 일반 폴더의 경우도 문서에 나옵니다. [H2] [H3]프로젝트는 지속 목표·자료·작업 범위를 묶는 단위로 유지합니다. 대표가 모든 요청마다 폴더나 체크아웃부터 만들게 하지 않습니다.
Tasks공개 UI 규약에서 Task는 루트 에이전트와 다른 기기를 포함한 그 자손들, 관련 체크아웃·PR을 묶은 보기입니다. 원래 issue·memo가 함께 붙을 수 있으며, 기존 사실에서 도출합니다. [H3]실행 관계를 한 업무 아래 접어 보여주는 원칙을 참고합니다. hide의 실행 묶음을 IAMCEO의 영속 업무 원장과 같은 개체라고 보지는 않습니다.
Mission / Conductor공식 소개·README는 Conductor가 여러 PR 작업을 계획하고 worker를 시작해 보고하는 mission을 설명합니다. 별도 mission 화면은 프로젝트별 필터와 지도·진척을 제공합니다. [H1] [H3]여러 업무를 묶는 ‘목표’를 필요할 때만 둡니다. IAMCEO의 끝점은 PR뿐 아니라 조사·문서·대표 결정도 될 수 있습니다.
Plan
hide task		공식 문서 지도는 이를 한 세션의 자체 계획으로 구분하고, 검토 질문과 자식에게 단계 넘기기를 명시합니다. 공개 상태 규약에도 위임 단계와 검토 대기가 나옵니다. [H4] [H6]작업 절차는 업무 안의 계획으로 시작합니다. 모든 단계마다 대표 대화를 새로 만들거나 새 직원을 만들 필요는 없습니다.
Backlog
GitHub issues / local memos		공식 README는 issue·local note를 한 backlog에 모으고 시작 시 worktree·agent·첫 지시를 연결한다고 설명합니다. 공개 UI의 빠른 추가는 backlog를 둘 프로젝트를 요구하며 Local과 GitHub 목적지를 구분합니다. [H2] [H3]접수된 요청과 실행 중 업무를 구분합니다. 다만 hide의 backlog만으로 프로젝트 없는 일반업무 접수가 지원된다고 결론내릴 수는 없습니다.
Pull requests / PRs같은 작업을 PR 관점에서 보여주며 사람이 행동할 항목을 앞세웁니다. 하나의 Task에 관련 PR이 연결될 수 있습니다. [H2]결과물·검토·결재 중심의 보기로 확장합니다. 비개발 업무에 PR이나 Git 작업을 의무화하지 않습니다.
Desk / jobs공개 전달 규약의 Desk agent는 pane·checkout이 없고, 자신이 시작한 세션을 관찰하며 자리 부족 시 대기열을 사용합니다. checkout이 필요한 명령과 Project Memory 접근은 거부됩니다. Desk 화면·job 상세 설계는 비공개로 옮겨져 있습니다. [H5] [H4]특정 프로젝트에 묶이지 않은 접수·연결 역할을 분리할 수 있다는 참고입니다. 비개발 일반업무 전반을 지원한다는 증거로 확대하지 않습니다.
Hide AI / Project Memory
Needs You		소개는 세션 요약·사람 차례 우선 표시를, README는 결정의 카드화·저장소 대조·다음 에이전트 전달·문서 반영 PR을 설명합니다. Needs You는 사람이 개입할 대상을 모은 관점입니다. [H1] [H2]담당자의 이름보다 대표 차례를 먼저 보여줍니다. 기억의 재사용과 작업 방법의 검증·채택은 별도 단계로 설계합니다.
실제 사용자 흐름을 요약하면

프로젝트에서 에이전트에 요청하거나 backlog를 시작 → 필요한 worker를 분담 → Task에서 부모·자식 실행을 묶어 확인 → 복합 작업은 mission·plan으로 진행을 표시 → 결과는 PR 관점으로 검토 → 사람이 할 일은 Needs You로 모으는 방식입니다. 서로 다른 보기와 기록을 연결해 인지 부담을 줄이는 것이 핵심으로 읽힙니다. 마지막 해석은 우리의 판단입니다.

원문 확인 범위와 확인하지 못한 것

공식 사이트는 직접 HTTP 요청으로 200 응답을 받아 소개·FAQ를 읽었고, 공식 GitHub 연결 도구로 README와 관련 공개 문서 구간을 읽었습니다. 검색 도구의 사이트 열기 실패를 실제 사이트의 접근 불가로 취급하지 않았습니다. 설치·실행 시험은 하지 않았습니다.

공식 문서 지도는 mission·plan·task identity·Desk·Project Memory 등의 핵심 상세 설계를 별도 비공개 저장소로 옮겼다고 명시합니다. 공개 문서에 남은 설명·규약만 사용했으며 비공개 문서를 열거나 추정해 채우지 않았습니다. ‘100+ agents’ 같은 소개 수치는 이번 검토에서 성능 검증한 결과가 아닙니다.

읽은 구간에서 IAMCEO처럼 지속되는 직원 명부·역할별 경험의 전체 모델은 확인하지 못했습니다. 그렇다고 hide에 해당 기능이 없다고 단정한 것은 아닙니다. 제품 소개의 기억 전달 기능도 자가개선 품질이 입증됐다는 뜻은 아닙니다.

새 근거로 기존안을 다시 평가했습니다

항목기존 후속안최신 판단과 이유
업무별 대화담당자가 바뀌어도 같은 대화 유지유지. hide의 Task 보기에서 실행들을 묶는 방식을 참고하되, IAMCEO는 세션보다 오래가는 업무·대표 결정의 기록을 기준으로 삼습니다.
지속 역할과 세션고정 직원 대신 지속 역할·업무별 세션가볍게 유지. 역할은 재사용하는 판단·작업 기준으로 둡니다. 항상 켜진 역할 관리자나 고정 직원의 자아가 있어야 하는 구조는 피합니다.
기억의 중심역할의 경험 축적을 전면에 설명수정. 업무·프로젝트의 근거 있는 기록을 공통 기준으로 두고 역할이 선택해 활용합니다. 역할별 장기 기억은 재사용 효과가 확인될 때 추가합니다.
여러 업무 묶기프로젝트 종합 대화에서 종합보강. 하나의 대표 목적에 속하는 업무는 선택적인 ‘목표 묶음’으로 연결합니다. 영구 프로젝트 생성과 일회성 복합 요청을 구분합니다.
총괄과 요약총괄이 우선순위·종합 담당유지·구분. hide도 Conductor, Hide AI, core를 다르게 설명합니다. IAMCEO도 의미 판단·요약·정해진 처리를 구분하되 상주 AI를 셋 더 만드는 식으로 옮기지 않습니다.
프로젝트 밖 업무본사 일반업무로 접수유지. Desk는 착안점이지만 hide backlog는 프로젝트를 요구하는 구간도 있습니다. IAMCEO의 일반업무는 별도 제품 요구로 설계합니다.

목적의 차이: hide는 코딩 에이전트·체크아웃·PR 중심 IDE입니다. IAMCEO는 대표가 개발·조사·문서·프로젝트 밖 요청을 함께 지시하고 결정하는 창구입니다. 따라서 hide의 명칭과 내부 개체를 1:1로 가져오는 대신, 여러 실행을 접어 보기, 사람이 할 일 우선, 근거 있는 기억의 재사용이라는 원칙을 취합니다.

직원과 실행을 관리하는 세 대안

아래 평가는 공개 근거와 사용 요구를 대조한 설계 판단입니다. 실제 사용량·품질을 측정한 비교는 아닙니다.

대안작동 방식유리한 경우부담
A · 고정 직원
전용 세션		조사 직원·개발 직원마다 세션을 이어 쓰고 대표가 담당자를 고릅니다.업무가 적고 특정 직원과 장기 대화를 쌓는 경험이 중요한 경우3~5개 일이 겹치면 대기·문맥 혼합·직원 2호 관리가 생깁니다. 실행 수와 책임 주체가 강하게 묶입니다.
B · 업무별 실행
공유 업무·프로젝트 기록		필요할 때 세션을 연결하고, 연속성은 업무 기록과 공통 지식이 맡습니다.서로 무관한 일회성 요청이 많고 반복 역할이 아직 적은 초기 제품반복되는 판단 기준·작업 방식이 매번 다시 구성될 수 있습니다. 역할의 재사용이 커지면 C안이 유용해집니다.
C · 재사용 역할
업무별 실행 분리
추천		B안 위에 조사·구현 등 반복 수요가 있는 역할의 기준을 재사용합니다. 검증 지식은 업무·프로젝트에 두고 역할별 기억은 선택합니다.반복 전문 업무와 일반업무가 섞이며, 대표가 직원 관리 없이 일관된 처리를 원하는 경우역할 기준과 지식 적용 범위를 관리해야 합니다. 요청이 드물면 B안보다 무겁고, 직원의 개성을 직접 키우고 싶다면 A안보다 덜 직관적입니다.
C안을 최소 형태로 추천합니다.

hide 사례는 B안처럼 실행·공유 기록 중심으로도 충분한 구조를 만들 수 있음을 보여주는 참고입니다. 그래도 반복되는 조사·구현의 판단 기준을 재사용할 필요가 있어 C안을 유지합니다. 다만 ‘직원별 장기 기억부터 구축’하는 우선순위는 낮춥니다. 대표의 역할 관리 선호는 아직 답이 없으므로 화면 노출 정도까지 확정하지 않습니다.

역할과 세션

주담당 역할이 작업·검토를 맡고, 협업이 필요하면 범위가 정해진 추가 실행을 요청합니다.

단위수명과 연결대표에게 보이는 것
프로젝트 / 본사지속되는 업무 범위. 업무는 프로젝트 또는 본사에 속합니다.프로젝트 상황·자료, 본사 일반업무. 프로젝트가 없는 요청을 가짜 개발 프로젝트로 만들지 않습니다.
목표 묶음
선택 정보		복합 요청을 끝낼 때까지. 업무 여러 개를 연결하는 제목·완료 기준·관계로 시작합니다.‘출시 준비’에 연결된 개발·소개 글·조사 진행. 작은 일에는 추가하지 않습니다.
업무 + 기본 대화접수→진행→완료·보관→재개. 주담당 역할 하나, 실행 여러 개. 결재·자료가 이 업무를 참조합니다.업무 제목·현재 상태·대표 차례·결과. 직원이나 모델이 바뀌어도 같은 기록으로 이어집니다.
역할여러 업무에서 재사용하는 판단·작업 기준. 필요한 지식을 참조하며 상시 프로세스일 필요는 없습니다.기본 선택은 자동, 원하면 상세에서 담당 역할과 기준을 확인·조정합니다.
실행 / 세션한 업무의 특정 작업 동안. 같은 업무는 세션을 재개할 수 있고 제공자 교체 시 새 문맥을 인계합니다.진행·대기·사용량, 나눈 이유, 협업 결과. 세션·모델을 매번 고르지 않습니다.
지식 항목업무 이후에도 재사용하되 근거·적용 범위·버전·검토일을 둡니다.검증된 사실·방법과 바뀐 이유. 처음에는 문서·목록으로 충분합니다.

처음부터 모든 것을 독립 개체로 만들 필요는 없습니다. 기존 프로젝트·본사를 유지하고, 업무 안에 대화·계획을 둡니다. 목표 묶음은 업무 사이의 연결 정보로, 역할은 재사용 설정으로 시작할 수 있습니다. 복잡한 조직도·상시 역할 관리자·별도 지식 서비스부터 만들자는 제안이 아닙니다.

하나의 역할이 여러 세션을 운용한다는 뜻

조사 역할이 제품 비교와 출장 동선을 동시에 맡아도 실행 문맥은 업무별로 나눕니다. 해당 업무의 주담당 실행이 추가 세션의 목적과 결과 기준을 요청하고, 서버가 중복·자원·허용 범위를 확인합니다. 다섯 업무를 접수했다고 다섯 세션을 즉시 띄울 필요는 없습니다.

문맥·결재·자료를 이어가는 규칙

  • 업무에 남김: 대표 원문·완료 기준·현재 판단·미해결 질문·승인 대상·최신 결과물. 같은 업무의 실행끼리 공유하며 다른 업무의 승인으로 쓰지 않습니다.
  • 프로젝트에서 재사용: 확인한 구조·용어·작업 제약. 역할별로 필요한 부분만 가져옵니다. 특정 프로젝트 경험을 본사 일반업무나 다른 프로젝트의 사실로 확대하지 않습니다.
  • 역할에서 재사용: 검증한 조사·구현·검토 방법. 개인적인 추측이나 원시 대화 전체를 역할의 공통 기억에 자동 누적하지 않습니다.
  • 담당·모델 교체: 같은 업무 ID 아래 요약과 원문·자료·열린 결재를 인계합니다. 답은 업무·질문·대상 행위에 연결하고 현재 화면이나 옛 세션 ID만으로 보내지 않습니다. 실제 승인 대상이 달라졌으면 다시 판단받습니다.

대화 범위의 기억과 여러 대화에서 쓰는 기억을 나누는 근거는 기존에 확인한 LangChain 공식 Memory overview를 재사용했습니다. 구체적인 업무·프로젝트·역할 범위는 우리의 제안입니다. [M]

hide는 lead→worker→helper와 편지 소통을 공개 설명하며, 자식은 부모에게 보고하도록 합니다. [H2] IAMCEO도 모든 질의를 총괄이 중계할 필요는 없습니다. 다만 사람이 정할 일을 부모 에이전트가 임의로 대신 답하는 구조로 옮기지는 않습니다.

주담당의 책임

채택·보류·최종 보고

업무 결과는 주담당 한 곳이 책임집니다. 다른 업무와 충돌하면 총괄, 대표 결정은 결재함으로 올립니다.

  • 목적 있는 협업: 필요한 답이나 검토 결과가 나오면 종료합니다. 초깃값 제안은 질의·답변 1회와 보완 1회입니다. 계속 합의가 안 되면 쟁점·근거를 남겨 주담당 또는 총괄이 판단합니다.
  • 불필요한 회의 방지: 기존 답 재사용 여부, 같은 실행의 중복 요청, 추가 세션의 기대 결과를 확인합니다. 실행 수·시간·사용량 한도와 재위임 깊이는 미리 정한 규칙으로 제한합니다.
  • 역할 간 소통 범위: 같은 업무는 필요한 기록을 공유하고, 다른 업무에는 요청 목적에 필요한 요약·근거만 보냅니다. 상대의 메시지는 대표 승인과 구분합니다.

자가개선: 기억 카드가 생겼다는 것과 방법이 나아졌다는 것은 다릅니다

hide의 Project Memory는 결정의 카드화·다음 에이전트 전달·문서 반영 흐름을 참고할 만합니다. [H2] 그것만으로 일반적인 품질 향상이 보장되지는 않습니다. IAMCEO에서는 다음의 최소 흐름을 제안합니다.

  1. 경험 기록 → 개선 후보

    대표 수정·실패·검사 결과를 근거로 바꿀 방법 하나와 적용 범위를 적습니다. “이번에 실패했다”를 “모든 업무에서 금지”로 바꾸지 않습니다.

  2. 기준 고정 → 기존 방법과 비교

    결과 품질·대표 수정량·시간·사용량 기준을 미리 정합니다. 같은 사례와 별도 확인 사례로 비교하고, 편차가 크면 반복합니다. 후보가 자기 평가 기준을 바꿔 통과시키지 않게 합니다.

  3. 검토 → 좁게 적용

    코드는 실제 검사 결과, 조사는 출처·요구 충족, 문서는 명시 기준과 사람의 표본 검토를 사용합니다. 에이전트끼리의 동의나 자체 점수는 보조 근거입니다.

  4. 버전 기록 → 관찰·되돌리기

    사용한 지식·방법 버전을 실행에 남기고 기준 미달이면 이전 판으로 되돌립니다. 프로젝트 한정 경험을 역할 전체나 모든 프로젝트로 자동 확대하지 않습니다.

초기 자동화는 개선 후보 작성까지를 추천합니다.

적용은 대표가 정한 뒤 진행하고, 이후 미리 허용한 범위·평가 기준 안에서 좁은 작업 방법을 자동 적용하는 방식을 검토할 수 있습니다. 권한 확대나 대표 결정 변경은 별도 판단 대상입니다. 이번에는 기억·지침을 실제 변경하거나 비교 시험을 실행하지 않았습니다.

평가가 실제 결과를 확인하고 코드·모델·사람 판단을 조합해야 한다는 근거는 기존에 확인한 Anthropic 공식 평가 글을 재사용했습니다. 자가평가·상호 동의가 개선을 보장한다는 근거로 쓰지 않았습니다. [E]

총괄의 책임은 ‘여러 일 사이의 판단’입니다

hide의 Conductor는 mission 실행, Hide AI는 요약·사람 차례·기억 관련 보조, core는 상태·실행 규칙을 담당한다고 공개 설명됩니다. [H1] [H2] IAMCEO에서도 이 책임을 구분하되 모든 대화와 도구를 총괄이 건별로 승인하는 병목은 만들 필요가 없습니다.

책임총괄·주담당의 판단서버의 정해진 처리
대표 의도·업무 경계총괄이 복합 요청을 나누고 완료 기준을 해석합니다. 중요한 모호함·범위 변경은 대표에게 확인합니다.대표 원문·업무·목표 연결을 보존합니다. 같은 업무 수정은 현재 담당으로 연결합니다.
우선순위·의존성·자원총괄이 앞뒤 순서와 업무 간 충돌을 조정합니다. 주담당은 업무 안의 협업 필요성을 판단합니다.선행 조건·대기열·가용 실행 수·사용량 한도와 허용 범위를 적용합니다.
담당 지정총괄은 낯선 복합 업무의 담당을 정합니다. 작은 일은 미리 정한 기본 역할로 갈 수 있습니다.기존 담당·명시된 기본 연결을 적용하고 중복 실행과 잘못된 수신을 막습니다.
결재·실행주담당이 필요한 행동을 판단합니다. 총괄도 대표 결정을 대신하지 않습니다.승인 상태·실행 정책을 확인하고 답을 정확한 질문·업무로 돌려보냅니다.
결과 종합주담당은 개별 결과, 총괄은 여러 결과가 대표 목표를 함께 충족하는지 책임집니다.상태·결재·자료를 모아 보여줍니다. 전달됐다는 사실과 업무 완료를 구분합니다.

작은 일: 기존 업무 수정이나 범위가 명확한 요청은 바로 담당 역할로 연결하고 총괄 AI 호출을 줄일 수 있습니다. 복합·충돌하는 일: 총괄이 필요한 요약·근거만 읽고 판단하며, 필요할 때 원문으로 내려갑니다. 총괄이 모든 세션을 계속 읽어야 한다고 전제하지 않습니다.

현재 IAMCEO의 ‘총괄은 조사·구현을 직접 하지 않고 직원에게 맡긴다’는 기본 지침과는 구분한 장래 제안입니다. 총괄 단계를 줄이는 경로를 이번에 적용한 것은 아닙니다.

프로젝트 업무 3개 + 일반업무 2개가 흐르는 예시

아래는 제안 구조의 가상 예시입니다. 실제 업무·직원·하위 에이전트·시험 세션을 생성한 기록이 아닙니다.

  1. 프로젝트에서 대표가 세 일을 말합니다.

    “연동은 계속하고, 대화 구조 검토와 소개 글도 준비해 줘.” 세 업무를 접수하고 ‘출시 준비’라는 목적이 같다면 목표 묶음으로 연결합니다. 예시 응답은 “세 업무로 나눴습니다. 연동·구조 검토를 진행하고 소개 글은 검토 결과를 반영해 이어갑니다.”입니다.

  2. 본사에 출장 동선·견적 비교를 말합니다.

    프로젝트를 새로 만들지 않고 일반업무 대화로 각각 접수합니다. 프로젝트의 기술 맥락이나 승인 조건을 가져오지 않습니다.

  3. 역할이 필요한 실행을 나눕니다.

    조사 역할이 구조 검토와 출장 동선에 각각 별도 세션을 연결합니다. 역할 기준은 재사용하되 업무 문맥은 분리합니다. 연동 담당은 구조 검토에 전달 방식의 제약을 좁게 질의하고, 결과를 공유 업무 기록으로 받습니다. 실행 자리가 부족하면 다른 업무는 차례 대기로 남습니다.

  4. 대표는 ‘내 차례’와 업무 대화에서 답합니다.

    견적 조건은 관련 결재 카드에서 정하고, 구조 검토의 “둘째 안을 더 설명해 줘”는 그 업무 대화로 이어집니다. 직원·세션·모델을 매번 고르지 않아도 됩니다.

  5. 결과 종합 뒤 개선 후보를 남깁니다.

    주담당은 자료와 근거를 보고하고, 총괄은 소개 글이 검토 결론을 반영했는지 등 업무 간 연결을 종합합니다. 출처 확인일 누락 같은 피드백은 개선 후보가 되며 시험·검토 전에는 모든 조사 역할의 지침을 바꾸지 않습니다.
