두 추천안을 하나의 체험판으로
기존 서버와 분리해 확인하기

업무별 대화·프로젝트 묶음·전체 내 차례와 선택적 직원 관리·재사용 역할·업무별 실행을 함께 구현하는 웹 우선 체험판입니다. Hindsight는 기존 서버 업로드·MCP 검색에 연결할 접점만 준비합니다.

체험판 구현 승인됨운영 반영은 체험 후 결정Hindsight 실연결 계약 미확인순차 개발·개발 보조 하위 에이전트 없음
대표가 확인할 핵심

직원을 매번 고르지 않고 다섯 업무를 오가며 지시·결재·자료를 찾을 수 있는지, 같은 역할의 다른 업무가 실제 실행 입력에서도 구분되는지 체험합니다. 역할 상세 노출 정도는 체험 후 바꿀 수 있게 둡니다. 같은 선택이나 사전 설계 승인을 다시 묻는 단계는 추가하지 않습니다.

1. 이번 개발 범위

대표 화면

홈에서 전체 업무를 보고 프로젝트·일반업무·선택적 목표 묶음으로 좁힙니다. 대화는 업무별로 이어지고, 결재함은 프로젝트를 넘나드는 ‘내 차례’로 모읍니다. 자료는 해당 업무로 돌아갈 수 있게 합니다.

내부 실행

업무의 주담당 역할과 실행을 구분합니다. 같은 역할의 여러 업무는 다른 실행 문맥을 사용합니다. 직원·역할·모델 선택은 기본 필수 입력으로 두지 않고 상세에서 조정할 수 있게 합니다.

  • 최소 기록: 업무 ID, 소속(프로젝트 또는 본사 일반업무), 제목·완료 기준·상태, 선택적 목표 연결, 주담당 역할, 실행 이력, 메시지·결재·자료 참조. 계획은 업무 안에 두고 별도 조직 체계를 늘리지 않습니다.
  • 목표 묶음: 예시의 프로젝트 업무 세 개를 ‘출시 준비’로 묶을 수 있습니다. 일반업무에 가짜 개발 프로젝트나 작업 폴더를 요구하지 않습니다.
  • 협업: 업무 안의 직접 질의·답변·인계 기록과 주담당의 최종 결과를 구분합니다. 업무 간 우선순위·자원 충돌은 총괄이 종합합니다.
  • 기억: 업무·프로젝트의 검증된 기록·회고·개선 후보를 Hindsight로 넘길 준비만 합니다. 자체 기억 DB·검색 엔진·자동 지침 수정은 만들지 않습니다.

여기서 두 추천안은 A/B 버전 두 개를 따로 만드는 뜻이 아닙니다. 위 화면 구조와 역할·실행 구조를 한 체험판에 함께 적용합니다. 네이티브 앱의 새 구조 구현이나 원본 데이터 이전은 이번 범위에 추가하지 않습니다.

2. 기존 서버와 분리하는 조건

구분이번에 읽기 전용으로 확인한 사실체험판 수용 조건
소스main은 확인 시점 0a8cabd. Antigravity는 feat/antigravity의 b5fe3ec에 별도로 존재하며 그 시점 main에 포함되지 않았습니다.별도 워크트리·브랜치에서 개발합니다. 예: 새 feat/work-trial. 착수 시 최신 main·머지 상태를 다시 확인하되 Antigravity 머지 작업을 반복하거나 대신 승인하지 않습니다.
로컬 주소현재 세션 연결 주소는 http://127.0.0.1:7881. 확인 시 7880도 사용 중이며 7882는 비어 있었습니다.후보 http://127.0.0.1:7882로, 시작 직전 사용 여부를 확인합니다. 점유됐다면 다른 빈 포트 사용 후 실제 URL을 보고합니다. 기존 프로세스를 종료해 자리를 만들지 않습니다.
데이터·접속현재 홈은 /private/tmp/iamceo-compare.mrhaOF/native-codex-data. 현행 IAMCEO_HOME 아래 DB·업로드·받은 파일·역할 설정이 파생됩니다.새 짧은 경로의 IAMCEO_HOME, 새 DB·업로드·로그·접속 코드를 사용합니다. 예: /private/tmp/icxp-<고유값>/data. 기존 데이터를 자동 복사·이전하지 않습니다.
실행 연결현행 core 소켓은 홈 아래에서 결정되고 state/config도 홈 아래로 파생됩니다. 코어 session label은 코드에서 iamceo를 사용합니다.테스트 실행을 기본으로 하며 기존 세션 ID·터미널·토큰에 재연결하지 않습니다. 실제 core 경로를 제공한다면 새 소켓·state/config·세션 바인딩을 사용합니다. 같은 라벨을 쓰더라도 소켓·저장 경계가 분리됐음을 확인합니다.
설정·프로세스IAMCEO_PORT, IAMCEO_CORE_SOCKET 설정 지점이 있습니다. 현행 기본 hosts는 환경에 따라 로컬 외 주소를 포함할 수 있습니다.체험판 hosts를 127.0.0.1로 명시합니다. 운영 서버 재시작·launchd 등록·전역 CLI 설정 수정 없이 시작·종료할 수 있어야 합니다.

체험판 화면에 ‘로컬 체험판’과 실행 방식(테스트 실행 / 실제 연결)을 표시합니다. 개발자는 최종 보고에 실제 URL, 브랜치·워크트리, 데이터 홈, 실행 연결 경계, 시작·종료 방법을 남깁니다. 임시 폴더는 삭제하지 않고 보존합니다.

결재함 · 내 차례

한곳에서 답하기

프로젝트와 일반업무의 답할 일을 모아 보고, 답한 뒤 원래 업무로 돌아갑니다.

체험 업무소속·관계확인 동작
연동 구현체험 프로젝트 · 출시 준비진행·후속 지시·검토 요청·결과 자료를 확인합니다. 이름은 샘플이며 실제 Antigravity 작업을 중복 실행하지 않습니다.
대화 구조 검토같은 프로젝트 · 출시 준비 · 조사 역할‘둘째 안을 보강’이라고 후속 지시하고 해당 업무 자료·결재에만 연결되는지 봅니다.
소개 글 작성같은 프로젝트 · 출시 준비구조 검토의 결과를 기다리는 상태와 이후 재개·완료를 확인합니다.
출장 동선 조사본사 일반업무 · 같은 조사 역할별도 프로젝트 생성 없이 접수하고 대화 구조 검토와 다른 실행 문맥을 사용합니다.
견적 비교본사 일반업무전체 내 차례에서 조건 선택에 답하고 비교 자료를 봅니다. 담당·모델 변경과 완료 후 재개를 확인합니다.

새 업무 입력과 다섯 샘플 데이터는 체험 서버에 실제 저장합니다. 임의 자연어 요청을 완벽히 분해하는 새 모델 기능을 완료 조건으로 추가하지 않습니다. 테스트 실행은 정해진 샘플 응답·이벤트로 접수와 상태 변화를 보여줄 수 있습니다.

기존 홈·대화·결재함·자료·팀 화면을 활용합니다. 프로젝트 종합 대화에서는 여러 업무의 요약과 링크를, 업무 대화에서는 그 일의 기록을 보여줍니다. 역할·직원과 실행 상세는 선택적으로 펼쳐 보며 노출 정도는 체험 중 조정할 수 있게 합니다.

4. 완료로 볼 수 있는 수용 기준

번호검증 동작통과 기준·남길 증거
A1 · 분리기존 서버가 살아 있는 동안 체험 서버를 별도 주소로 실행·종료합니다.서로 다른 홈·DB·접속 코드·소켓/테스트 실행 바인딩을 기록합니다. 체험 동작이 기존 서버에 쓰기 요청이나 세션 제어를 보내지 않으며 기존 서버를 재시작하지 않습니다.
A2 · 접수·탐색다섯 업무를 접수하고 전체→프로젝트 3개→일반업무 2개→목표 묶음으로 이동합니다.모든 업무가 직원 선택 없이 등록되고 독립 ID·대화를 가집니다. 새로고침 후에도 상태와 연결이 유지됩니다.
A3 · 후속 지시대화 구조 검토에 글을 보내는 중 출장 동선 대화로 이동합니다.전송 때의 업무·수신 실행이 고정됩니다. 늦게 온 결과·초안·재시도가 다른 업무에 붙지 않습니다.
A4 · 내 차례·자료프로젝트·일반업무의 열린 결재를 전체 결재함에서 보고 답한 뒤 결과 자료를 엽니다.결재와 자료에 업무의 출처·돌아가기 경로가 있습니다. 같은 답을 중복 실행하지 않으며 답이 정확한 안건에만 적용됩니다.
A5 · 실행 문맥같은 조사 역할이 두 업무를 처리하도록 테스트 실행에 다른 식별 문구를 넣습니다.실행 ID·문맥 저장/입력 기록이 다르고 상대 업무의 문구가 입력에 섞이지 않습니다. 메시지 필터만 바꾸고 같은 실행 이력을 계속 쓰면 실패입니다.
A6 · 교체·재개열린 결재·자료가 있는 견적 비교의 담당 역할·테스트 모델을 바꾸고 답을 처리한 뒤 완료·재개합니다.업무 ID·결재·자료·후속 지시는 유지됩니다. 새 실행에는 해당 업무의 명시적 인계만 들어가고, 옛 실행의 지연 결과가 새 담당 상태를 덮지 않습니다. 재개는 같은 업무에 이력을 추가합니다.
A7 · 협업·종합테스트 실행 경로에서 업무 내 질의·답변·인계 1건과 소개 글의 선행 결과 대기를 처리합니다.협업 근거와 주담당 최종 결과를 구분합니다. 모든 말을 총괄이 중계하지 않고, 총괄은 업무 간 선후·충돌·종합을 보여줍니다.
A8 · Hindsight 접점미설정 상태, 주입한 테스트 업로드 어댑터의 성공·실패·응답 유실, 검색 범위 전달을 검사합니다.미설정이면 외부 호출 없이 ‘연결 전’으로 남고 업무 흐름은 계속됩니다. 테스트 성공과 실제 연결 성공을 구분하며, 출처·범위·판/중복 키를 보존합니다. 실제 MCP 주소·도구가 없으면 검색 성공이라고 표시하지 않습니다.
화면 분리와 실제 모델 문맥 분리는 같은 검증이 아닙니다.

체험판의 기본 완료 조건은 서로 분리된 테스트 실행 상태·입력 기록으로 A5·A6을 확인하는 것입니다. 이것은 화면 모형만의 분리보다 강한 검증이지만 외부 모델의 실제 격리·호환성을 확인한 결과는 아닙니다. 실제 공급자 세션 검증 여부는 별도 항목으로 보고하고 미실행이면 그대로 표시합니다.

5. Hindsight 연결 계약과 미확인 정보

확정된 운영 방향: 대표의 기존 서버가 업로드를 맡고 에이전트가 필요한 내용을 기존 MCP로 검색합니다. 이번에 읽은 저장소·현재 서버 설정에서는 Hindsight 업로드 API·MCP 이름·인증 계약을 확인하지 못했습니다. 아래는 체험판 내부의 제안 계약이며 Hindsight 실제 HTTP 스키마나 엔드포인트가 아닙니다.

서버 → 업로드 접점

검증된 기록·회고·개선 후보를 종류별로 구분해 넘깁니다. 시험 데이터의 출처는 체험판임을 보존하고, 미설정이면 전송하지 않습니다. 기존 업무 DB에는 원문 참조와 전송 상태만 둘 수 있으며 별도 기억 DB는 만들지 않습니다.

에이전트 → 기존 MCP 검색

설정된 MCP 서버·도구를 실행 단위에 연결하고 프로젝트·업무·역할 범위를 전달합니다. 자체 검색 서버·색인을 만들지 않습니다. 범위 필터의 실제 인자와 강제 방식은 기존 MCP 계약 확인 후 매핑합니다.

개발용 내부 어댑터 인터페이스 · 실제 서비스 계약 아님 
UploadRecord = {
  recordId, revision, kind,             // verified_record | retrospective | improvement_candidate
  scope: { trialInstanceId, projectRef, taskRef, roleRef? },
  content, sourceRefs                  // 원문·결재·자료 참조, 후보와 확정 내용을 구분
}
publish(record, idempotencyKey) → {
  status: not_configured | uploaded | failed | unknown,
  remoteReceipt?                      // 실제 확인 응답이 있을 때만
}
idempotencyKey = trialInstanceId + recordId + revision

SearchBinding = {
  mcpServerRef, toolRef, authRef?, scopeMapping
}
buildSearchContext(task, role, binding) → {
  bindingRef, scope, sourceRefs        // 실제 MCP 인자는 확인된 계약으로만 매핑
}

위 필드·함수 이름은 개발 인계용 내부 계약입니다. 외부 업로드 주소·HTTP 메서드·은행/메모리 ID 체계·MCP 도구명·인자 형태를 새로 사실처럼 정하지 않습니다. 어댑터가 확인된 기존 계약으로 변환하도록 합니다. 인증값 자체는 문서·브라우저·명령행 인자에 노출하지 않고 기존 설정의 참조로 전달합니다.

  • 연결 전: 업로드 어댑터·주소/인증 또는 MCP 바인딩이 없으면 준비한 기록과 범위를 확인할 수 있고 외부 호출은 0건입니다. 요청 내용은 기존 업무·자료 기록에 남겨 나중에 같은 판으로 다시 전달할 수 있게 합니다.
  • 설정됨·미검증: 연결 설정이 있다는 사실만 표시합니다. 가짜 어댑터의 성공은 테스트 성공으로만 표시하고 실제 업로드·검색 성공으로 올리지 않습니다.
  • 실제 확인됨: 업로드는 실제 확인 응답, 검색은 실제 MCP 호출 결과를 각각 기록한 경우만 해당합니다. 두 경로의 상태를 따로 관리합니다.
  • 실패·미확인: 실패 또는 타임아웃/응답 유실을 성공으로 처리하지 않습니다. 미확인 전송을 새 키로 자동 중복 업로드하지 않습니다. 실제 서비스의 중복 처리 계약은 연결 시 확인합니다.

나중에 받아야 할 정보: 서버 업로드 호출 계약·콘텐츠/범위 매핑·인증 참조·확인 응답과 중복 처리 방식, MCP 서버 식별자·실제 도구명·검색 인자·범위 제한 방식·연결 권한입니다. 이 정보 없이도 어댑터 미설정과 테스트 대역으로 체험판 개발을 완료할 수 있습니다. 개선 후보 업로드가 자동 지침 수정이나 대표 결정 변경을 뜻하지는 않습니다.

6. 개발 순서와 확인할 코드 지점

  1. 격리된 체험 서버와 업무 원장을 먼저 연결

    새 워크트리·브랜치·홈·포트에서 시작하고 다섯 샘플을 체험 DB에 등록합니다. 업무·선택적 목표·역할·실행 연결을 추가하되 기존 Member를 실행 바인딩에 활용하는 최소 변경도 가능합니다. 역할 ID와 실행 ID를 같은 것으로 쓰지는 않습니다.

  2. 웹의 업무별 흐름과 전체 내 차례 구현

    접수·후속 대화·자료·결재를 업무 ID로 연결합니다. 입력 초안·비동기 응답·전달 재시도도 업무 범위를 유지합니다. 재사용 역할의 상세는 필수 선택 없이 접근하게 합니다.

  3. 테스트 실행·교체·재개·협업 확인

    외부 모델을 자동 생성하는 대신 테스트 Runner를 주입해 별도 문맥과 입력 이력을 검증합니다. 테스트 모델 교체는 새 실행 이력과 인계로 표현합니다. 실제 공급자 세션 ID를 가짜로 만들어 지원됐다고 표시하지 않습니다.

  4. Hindsight 접점과 검증·체험 보고

    업로드 어댑터와 MCP 연결 설정·범위 전달을 추가합니다. 기본은 미설정 상태입니다. 아래 검증을 마친 뒤 실제 URL·체험 데이터·수용 기준 결과·남은 실연결 항목을 대표에게 보고합니다.
