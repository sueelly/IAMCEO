1. 추천: 자료 검토는 자료 곁에, 업무 책임은 기존 작업·담당에

자료별 검토 스레드에 자세한 댓글과 답글을 남기고, 업무 대화에는 결정·이유·변경 결과·미해결과 원문 링크를 연결합니다. 수정 요청은 자료·버전·task·담당을 고정해 전달하고, 직원은 변경안을 반환합니다. 검토와 필요한 승인을 거쳐 새 버전을 정본으로 지정합니다.

자료 화면

본문 + 버전 선택 + 옆 검토 패널. 무엇을 보고 한 말인지, 어떤 변경안이 돌아왔는지 한곳에서 확인합니다. 폰에서는 본문/검토 탭으로 전환할 수 있습니다.

업무 대화

작업의 목표·범위와 통합 결과를 봅니다. 모든 댓글 전문을 중복 저장하지 않고 같은 스레드를 참조합니다. 자료의 세부 수정이 업무 대화 전체를 채우지 않게 합니다.

작업·직원

task는 업무 연결, 직원은 담당과 책임, 실행은 실제 수행 단위입니다. 자료 A/B를 같은 직원이 맡을 수 있지만 요청의 대상과 결과는 각각 유지합니다.

기존 프로젝트·직원 구조를 통째로 갈아엎지 않습니다. 앞선 세 대안 중 자료 전용 검토 기록 + 업무 대화 요약 연결을 유지합니다. 하나의 메시지를 두 화면에 전부 노출하는 안보다 자세한 검토와 업무 진행을 읽기 쉽고, 자료 태그만 붙이는 안보다 버전별 미결을 관리하기 좋기 때문입니다.

2. 대표 요청 한 건이 도는 흐름

가정: 같은 문서 담당 W가 자료 A ‘소개서’와 자료 B ‘멘토링 기록’을 맡고 있습니다. 실제 직원 실행을 시작한 예시가 아닙니다.

① 자료 A · v2
대표가 원문을 보고 수정 요청
② 고정된 요청
A·v2·task A·담당 W·원문 ID
③ 실행·결과
대기열 → W가 변경안·근거 반환
④ 검토·새 버전
기준 버전 확인 → v3 게시·정본 지정
⑤ 업무 대화
결정·결과 링크 → 원래 댓글로 복귀
  1. 자료를 보며 입력. 단순 의견은 저장하고, ‘답변 요청’ 또는 ‘수정 요청’으로 보낸 항목만 실행 대상으로 만듭니다. 인증된 대표 댓글의 출처를 보존합니다. 본문 속 문장이나 HTML 내부 버튼의 문구는 대표 지시가 아닙니다.
  2. 누구에게 보낼지 결정. 자료의 지정 담당 W에게 전달합니다. 담당이 없거나 범위가 달라지면 프로젝트 총괄이 배정합니다. W가 B를 처리 중이면 A 요청은 현재 전달 규칙에 맞춰 대기합니다. 총괄이 같은 요청을 다시 쌓지 않게 원문과 전달 ID를 잇습니다.
  3. 화면을 옮겨도 대상 유지. 대표가 B로 이동하거나 W가 다른 task를 처리해도, A 요청의 원래 자료·버전·task는 바뀌지 않습니다. 최신 선택 화면이나 직원의 마지막 작업을 근거로 귀속을 추정하지 않습니다.
  4. 직원이 결과 반환. W는 원래 요청 ID를 명시해 답글·변경안·근거/반례·검증·미결을 반환합니다. 자료 스레드에는 상세 내용을 남기고 상사/총괄에는 요약과 원문 참조를 올립니다. 단순 답변과 실제 수정 완료를 구분합니다.
  5. 변경안을 검토. 변경 전후와 기준 버전을 확인합니다. 현재 정본이 여전히 v2인지 검사한 뒤 정책상 필요한 명시 승인을 받아 새 file을 v3으로 연결합니다. 초안 게시·정본 지정·외부 배포는 같은 행동이 아닙니다. 기존 승인 규칙을 넓히지 않습니다.
  6. 업무 결과로 통합. 주담당이 해당 작업의 다른 결과와 일관성을 확인하고, 총괄은 목표·미결·다음 행동을 종합합니다. 업무 대화의 링크에서 A·v2의 원문 댓글과 반영된 v3을 다시 열 수 있게 합니다. 상사에게 모든 토큰을 복사하지 않습니다.

두 종류의 상태를 함께 봅니다. 댓글은 미답변/답변됨, 수정은 미요청/접수/대기/작업 중/변경안 준비/검토·승인 대기/반영 완료/충돌·실패로 구분합니다. 수신 확인·답변·대표 승인·정본 반영·스레드 해결을 같은 완료 상태로 합치지 않습니다.

요청: project / task 또는 명시적 없음 / 자료 ID / 대상 file·버전 / 댓글 ID 전달: 요청 ID / 담당·배정 세대 / 허용 범위 / 전달·실행 참조 결과: 원래 요청 ID / 변경안·산출물 버전 / 근거·검증 / 미결·다음 행동 통합: 결정 원문·이유 / 반영한 새 버전 / 상사·업무 대화의 원문 링크

서버가 기억할 것: 댓글/결과와 알림을 저장하고 전달·수신·통합 상태를 구분합니다. 같은 이벤트는 같은 ID로 재전달하고, 상사 모델이 기억하는지로 중복 여부를 판단하지 않습니다. 알림 미수신 때문에 수정 작업 자체를 다시 실행하지 않습니다. 현재의 보고·전달 저장 재료를 활용하되, 자료 검토 전체가 이미 같은 계약으로 구현됐다고 가정하지 않습니다.

4. 여러 업무와 버전·담당 변경

A 요청 뒤 B로 이동

A·v2·task A를 전송 시 고정합니다. B의 화면과 입력 중인 초안은 그대로 두고 A의 결과 도착을 알립니다. 클릭하면 A의 원래 댓글로 돌아옵니다. W가 순차 처리해도 결과를 최근 task에 붙이지 않습니다.

이전 버전 댓글

v3이 생겨도 v2 원문·댓글은 남습니다. v2 요청이 v3에도 유효한지 담당이 대조합니다. 자동으로 최신본에 위치를 옮기거나 덮어쓰지 않고, 새 기준으로 옮긴 경우 관계와 이유를 남깁니다.

W→V 교체 뒤 늦은 답

W의 결과는 이전 배정 세대의 답으로 보존합니다. V의 답으로 위장하거나 최신본에 자동 반영하지 않습니다. V가 확인해 통합하고, 미전달/실행 중인 요청의 소유가 불명확하면 중복 배정부터 하지 않습니다.

같은 정본을 두 명이 수정

처음은 자료별 쓰기 작업 하나로 순차 처리합니다. 반영할 때 예상 기준 버전과 현재 정본을 대조하고 다르면 충돌로 멈춰 재검토합니다. 마지막으로 도착한 결과가 자동으로 이기지 않습니다.

5. 현재 구현, 필요한 보완, 장래 실행의 구분

구분이 설계에서의 위치
현재 활용할 기반file 업로드·자료별 뷰어·원본 보고/자료 참조, 프로젝트별 총괄 배정과 직원 대기열, 결재 원문과 답변 전달입니다. task 연결은 기존 개발 작업의 실제 적용 범위에 맞춥니다. 이번에 최신 서버 반영 상태를 다시 조사하거나 변경하지 않았습니다.
자료 검토의 보완지속 자료 ID와 버전 계보, 자료별 댓글/답글, 고정 대상과 출처가 있는 전달, 담당 세대, 수정·검토·반영 상태, 기준 버전 충돌 검사, 업무 요약 연결이 필요합니다. 기존 file ID 하나만으로 이 관계가 자동 생기지는 않습니다.
현재 직원 운영같은 직원이 여러 자료/작업을 순차로 처리할 수 있습니다. 원래 요청의 범위와 자료를 전달하되 같은 CLI 세션의 모델 문맥은 여전히 섞일 수 있습니다. 현재 총괄·직원의 도구 권한 안에서 배정합니다.

첫 적용 범위 제안: 기존 자료란에서 문서/HTML 전체 버전 댓글·답글·변경안·새 버전·업무 요약 연결을 먼저 다룹니다. 정밀 블록 선택, 이미지 영역, PDF 위치 댓글, 직접 편집 서버와 별도 작업 실행은 후속 범위입니다. 새 멈춤/후속 지시 문제의 실제 중단 기능은 별도 개발 안건이며 여기서 구현하지 않습니다.

검증 기준: A/B 이동 뒤에도 원래 대상에 결과 연결, v1/v2의 원문·댓글 보존, 담당 교체의 늦은 결과 구분, 동시 반영의 버전 충돌 처리, 의견 저장과 실행 요청 분리, 업무 요약에서 자료 댓글 왕복이 가능해야 합니다. 이 기준은 제안이며 구현 완료 선언이 아닙니다.
