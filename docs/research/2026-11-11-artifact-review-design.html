2. 대화와 분리하는 세 방식

방식데이터·화면장단점
업무 대화에 자료 태그기존 메시지에 자료/버전/댓글 대상 정보를 붙이고 자료에서 걸러 봅니다.구조가 작지만 검토 대화가 업무 흐름에 섞이고 자료별 미해결 상태를 찾기 어렵습니다.
자료 전용 검토 스레드 추천댓글 정본은 자료에 저장하고, 업무 대화에는 원문 링크·결정·완료 요약 이벤트만 연결합니다. 실행 전달은 기존 대기열을 활용합니다.자료를 보며 검토하기 좋고 상사 문맥에 모든 댓글을 복사하지 않아도 됩니다. 자료 버전·댓글·전달을 잇는 작은 추가 모델이 필요합니다.
동일 메시지의 두 화면하나의 정규화된 기록에 자료 스레드 속성을 두고 자료/업무 대화 양쪽에서 같은 레코드를 렌더링합니다.중복 저장은 없지만 업무 화면이 쉽게 복잡해집니다. 어떤 댓글을 업무 대화에 노출할지 별도 규칙이 필요합니다.

추천안은 검토 기록은 분리하되 업무 추적은 연결합니다. 댓글 본문을 대화 메시지로 다시 저장하지 않고 같은 댓글 ID를 참조합니다. ‘분리’가 독립된 직원 조직·새 프로젝트·고립된 정보 저장소를 뜻하지는 않습니다.

3. 최소 연결 모델과 실제 직원 전달

지속 자료 ID는 ‘소개서 A’라는 묶음, 버전별 file ID는 그때의 내용과 첨부를 가리킵니다. 현재 file ID를 버전 재료로 재사용하되 게시 시점 내용을 고정해야 합니다. 수정되는 외부 로컬 파일 경로만으로는 과거 원문을 보존할 수 없습니다. 같은 제목·최신 업로드를 근거로 버전 계보를 추측하지 않고 새 버전 등록 때 이전 자료를 명시합니다.

댓글/스레드가 고정할 값: project ID · 자료 묶음 ID · 대상 file/버전 · thread/comment ID · 작성자/시각·종류 · 원래 task ID 또는 명시적 ‘없음’ · 선택 위치/인용. 실행 전달에 덧붙일 값: request ID · 수신 담당과 배정 세대 · 원래 지시 ID · 전달/실행/결과 참조. 댓글을 보낼 때 대상을 서버가 검증해 고정하고 화면 선택이 바뀌어도 바꾸지 않습니다. task가 없는 자료를 현재 선택된 task로 자동 귀속시키지 않습니다.

  1. 의견은 저장. 단순 감상·참고 의견은 기본적으로 실행시키지 않습니다. 대표가 ‘답변 요청’이나 ‘수정 요청’으로 제출한 댓글만 실행 입력으로 만듭니다. 자료 본문·HTML 내부 문장은 외부 자료이며 대표 지시로 승격하지 않습니다.
  2. 누가 받는가. 자료의 명시된 담당 직원에게 보내고, 담당이 없거나 범위가 충돌하면 현재 프로젝트 총괄이 배정합니다. 첫 구현에서는 기존 총괄 배정·직원 대기열 경로를 사용하도록 서버 연결을 추가합니다. 직원이 바쁘면 큐에 쌓이고 ‘접수/대기/실행’을 보여 줍니다. 현재 댓글만 달면 이 동작이 이미 된다는 뜻은 아닙니다.
  3. 어떻게 실행하는가. 같은 직원이 여러 업무를 맡으면 댓글 요청마다 고정한 자료·버전·task·스레드와 필요한 원문을 전달합니다. 현행 같은 CLI의 순차 큐를 사용하며 작업별 문맥 격리를 보장하지 않습니다. 개발 중 관리 도구의 실제 계약에 맞춰 연결해야 합니다. 상사+작업별 실행안 f_k134NYyhbo3e는 제안이므로 전제하지 않습니다.
  4. 어디에 답하는가. 결과가 현재 화면/최근 직원 상태가 아니라 원래 request·thread·task를 명시해야 합니다. 댓글 답변과 새 버전은 원래 요청에 연결하고 업무 대화에는 결과 링크·결정/이유·미해결 요약만 남깁니다. 접수/수신 확인은 완료가 아닙니다.
  5. 무엇을 반영하는가. 새 file 후보에 기준 버전과 변경점·검증을 붙입니다. 초안 게시, 최신 정본 지정, 스레드 해결, 외부 배포는 구분합니다. 대표의 명시 승인과 현행 정책이 필요한 반영은 기존 ask에 대상 버전·댓글을 연결합니다. ‘좋아요’ 같은 모호한 답이나 직원의 완료 보고로 결재를 대신하지 않습니다.

상태는 두 줄로: 대화는 미답변/답변됨, 수정은 미요청/대기/작업 중/수정안 준비/반영 완료/충돌·실패/검토 후 해결로 구분합니다. 불필요해져 닫은 스레드는 ‘수정 완료’와 다른 사유를 남깁니다. Hindsight는 후속 연결 시 확정 결정·이유·결과와 원문/버전 참조를 기존 업로드 접점에 넘기는 정도이며 이번 연동 작업을 바꾸지 않습니다.

4. 여러 자료·담당 교체·같은 정본 충돌

사례필요한 동작
직원 W가 A/B와 여러 task 담당A의 댓글을 접수한 뒤 화면을 B로 옮겨도 전달은 A·v2·task A 그대로입니다. W의 B 작업이 끝나면 A 요청을 순차 전달합니다. 요청/답변에 task를 명시하고 ‘마지막 작업’을 따라 붙이지 않습니다. 같은 요청 재전송은 ID로 중복 억제합니다.
최신 v3인데 v2에 댓글v2 원문과 댓글을 그대로 열고 ‘이전 버전 대상’ 표시. 담당은 v3에도 필요한 수정인지 대조합니다. v3에 자동으로 위치를 옮기거나 덮어쓰지 않습니다. 이관 시 새 기준·원래 댓글을 연결하고 위치가 모호하면 확인합니다.
W→V 담당 교체 뒤 W의 늦은 답원래 W·배정 세대의 결과로 보존하고 ‘이전 담당 결과’로 표시합니다. 현재 담당 V의 답변으로 위장하거나 최신본에 자동 반영하지 않습니다. 미전달 요청은 이전 전달을 취소/미수신 확인한 뒤 명시 재배정하며, 실행 중/전송 불명확이면 확인 없이 둘에게 중복 실행시키지 않습니다.
둘이 같은 정본 수정첫 범위는 자료별 쓰기 실행 1개로 순차 처리합니다. 반영은 예상 최신 버전과 현재 버전이 같을 때만 허용합니다. 다르면 충돌로 멈추고 새 기준으로 비교·재검토합니다. 마지막 응답이 이기는 덮어쓰기는 하지 않습니다.

5. 첫 범위와 수용 기준

초기 후보: 이미 올린 HTML 논의 자료 f_k134NYyhbo3e 하나. 이를 선택·구현 승인한 것은 아닙니다. 먼저 ‘자료 전체/해당 버전 대상 댓글 + 답글 + 새 버전 연결’까지 만들면 자료란 안에서 실제 검토 흐름을 평가할 수 있습니다.

먼저

자료 묶음·고정된 버전·검토 스레드·담당/전달 ID, 전체 버전 댓글, 원문 링크, 답변/수정 상태, 새 file 후보·최신 버전·전후 요약을 추가합니다. 자료 뷰어 밖에 검토 패널을 두어 HTML 스크립트에서 댓글을 직접 쓰지 못하게 합니다.

나중

문서는 블록 ID·인용·문자 범위, HTML은 신뢰 가능한 렌더러의 안정된 블록/선택 연결이 필요합니다. 동적 DOM의 CSS 선택자·화면 좌표만 쓰면 취약합니다. 이미지 영역은 고정 첨부·정규화 좌표, PDF는 고정 파일·페이지·영역/인용을 저장하고 회전·재배치 차이를 다뤄야 합니다.

형식 공통 한계

이미지/PDF도 전체 버전 댓글은 같은 원리로 확장할 수 있습니다. 위치 댓글은 렌더러와 앵커 검증이 필요하므로 첫 범위에 넣지 않습니다. 자료를 새 버전으로 바꿨다고 이전 위치가 자동 보존된다고 보지 않습니다.

  1. A 댓글 작성 중 B로 화면을 바꿔도 제출된 대상 자료·버전·task가 고정되고 답변이 A에 돌아옵니다.
  2. 같은 요청을 두 번 제출/전달해도 한 요청으로 식별하며, 재시작 뒤 스레드·대기 상태·원문을 다시 볼 수 있습니다.
  3. v2 댓글·답변은 v3 게시 뒤에도 남습니다. 새 버전 묶음/계보는 명시 연결하고 기존 file과 첨부 원본을 보존합니다.
  4. 이전 담당의 늦은 결과와 구버전 기준 변경안은 자동 반영되지 않습니다. 같은 정본의 동시 반영은 버전 충돌로 거절됩니다.
  5. 의견 저장은 실행을 만들지 않고, 답변 요청/수정 요청은 담당·원문·고정 대상이 있는 기존 전달 경로에 들어갑니다. 본문 속 가짜 지시는 대표 댓글로 처리되지 않습니다.
  6. 답변됨·수정안 준비·승인·정본 반영·스레드 해결이 구분되고, 업무 대화에는 중복 댓글 전문 대신 같은 기록 링크와 결정/완료 요약이 보입니다.

결론: 자료를 보며 대화하고 새 버전을 받는 경험은 현행 자료란에 추가할 수 있는 설계입니다. 먼저 자료별 검토 스레드와 버전 연결을 만들고, 위치 댓글·직접 정본 편집·작업별 별도 실행은 검증 뒤 확장하는 안을 권합니다. 참고 서비스의 완전한 재현 가능성은 아직 확정하지 않습니다.
