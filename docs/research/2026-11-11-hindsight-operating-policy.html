1. 지금 실제로 있는 동작

7881에 이미 연결

63e0634로 기억 연결을 반영했다는 원본 보고를 확인했습니다. 검색·전문 조회·업로드·중복 억제의 실연결은 그 보고의 검증 결과입니다. 활성 범위는 현재 ‘네이티브 · Codex 체험’ 프로젝트입니다.

현재 자동 전송

대표가 결재 카드에 답해 상태가 바뀌면 서버가 결정 사본을 outbox에 넣고 전송합니다. 대화 속 결정, 모든 직원 보고, 자료 변경, 매 메시지 검색이 자동으로 켜진 것은 아닙니다.

아직 없는 실제 사례

대표 결재 자동 업로드의 첫 실제 사례는 원본 보고에서 미발생이었고, 이번 읽기 확인에서도 현재 프로젝트의 memory_outbox는 0건이었습니다. 이번 설계로 시험 기록을 만들지 않았습니다.

실제 도구: memory_search, memory_get, memory_record, memory_feedback. 프로젝트와 키는 서버가 정합니다. 검색은 같은 프로젝트의 여러 작업 기록을 찾습니다. task ID는 출처·작업 키·쓰기/피드백 귀속을 정하며, 검색을 그 task의 과거 기록만으로 제한하는 필터가 아닙니다.

아래 정책은 직원이 따를 운영 제안과 서버 보완 제안입니다. 새 상시 검색·자동수집·스케줄을 이번에 적용하지 않았습니다. 일반 Hindsight의 bank·reflect·retain을 이 게이트웨이의 도구라고 가정하지 않습니다.

2. 언제 검색할까

권장 검색 시점 — 필수도 ‘해당 상황에서 한 번’이라는 뜻입니다
시점권장 정책질문·재검색 기준
새 업무 시작필수: 설계·개발·조사 등 과거 판단을 재사용할 비단순 업무. 현재 목표·task·정본을 먼저 확인한 뒤 1회.‘이번 목표/문제에 같은 조건의 결정·실수·검증 결과가 있었나?’ 단순 오탈자 수정·상태 안내·기존 결과 재보고는 생략합니다.
중요한 선택 직전필수: 구조·범위·고객 약속·되돌리기 어려운 선택의 근거를 만들 때.선택지와 제약을 포함해 새로 조회합니다. 같은 선택의 연속 검토에서는 직전 조회를 재사용하되 조건·정본·명시 결정이 바뀌면 다시 찾습니다.
대표 수정·새 근거 도착현재 원문 확인은 필수, 기억 재검색은 조건부.기존에 적용한 기억과 충돌하거나 선택의 전제가 바뀌면 재검색. 명확한 지시대로 문구만 고치는 경우 검색을 추가해 지시를 지연시키지 않습니다.
담당·모델 교체인계 읽기는 필수, 새 검색은 조건부.목표·정본·명시 결정·채택/기각한 기억 ID·미결을 넘깁니다. 기록이 없거나 다른 질문/단계로 넘어갈 때 다시 검색합니다. 전체 대화 복사는 기본으로 삼지 않습니다.
압축·재개원본 상태 복원은 필수, 검색은 조건부.최근 검색 목적·후보·적용 이유가 남아 있고 조건이 같으면 재사용합니다. 기록 손실·정본 변경·새 결정·장시간 공백이면 재검색. 공백 1일을 재검색 기준으로 보는 것은 첫 운영 가설입니다.
같은 작업의 후속 대화대개 생략.동일 목표·판단·입력 버전이면 재사용합니다. 별도 선택이나 재발 오류가 생겼을 때만 새 질의를 만듭니다.
매 메시지·도구 호출생략.새 재사용 판단이 없는 진행 알림, 파일 읽기마다의 반복 조회, 정해진 수정을 수행하는 각 단계에는 검색하지 않습니다.

검색과 전문 확인의 한 예

가정한 질의입니다. 실제 호출·기억 ID 생성은 하지 않았습니다. task에는 실제 받은 작업 ID를 사용합니다.

memory_search({
  query: "자료 수정 요청이 다른 작업에 섞이지 않게 할 때, 작업 귀속·원문 출처·버전 충돌에 관해 어떤 결정과 검증된 교훈이 있었나?",
  limit: 3,
  task_id: "받은 실제 작업 ID"
})

→ 조건이 맞는 결정/검증 후보만 1~2건 선택
memory_get({ id: "검색에서 받은 실제 exp-ID", task_id: "같은 작업 ID" })
→ classification·근거·원래 결정/자료 버전 확인
→ 현재 원문과 대조해 적용 또는 기각 이유 기록

검색 본문은 최대 1,600자이고 근거가 빠질 수 있습니다. 중요한 판단에 적용할 후보는 memory_get으로 전문·근거를 확인합니다. 같은 단어가 들어간다는 이유만으로 전부 조회하지 않습니다. explicit_user_decision 분류 근거가 있는 기록과 직원 추론을 구분하고, 그래도 현재 승인·지시는 IAMCEO 원문에서 다시 확인합니다.

재검색·캐시·실패 처리

현재 IAMCEO에는 검색 결과를 이 정책대로 재사용/무효화하는 전용 캐시가 확인되지 않았습니다. 우선 작업 인계/보고에 검색 목적·질의·시각·후보 ID·적용/기각·원문 버전을 남겨 같은 검토 라운드에서 재사용하는 안입니다. 서버의 MCP 연결 키 보관은 검색 결과 캐시와 다릅니다.

무효화 조건: 프로젝트/task 또는 질문 변경, 최신 지시/정본/결정 변경, 적용 중인 기록의 정정 발견, 반례/새 검증 도착, 후보 전문 미확인, 검색 기록이 인계되지 않은 경우. 다른 직원의 새 기록을 즉시 감지하는 공통 memory revision 기능은 확인하지 못했으므로 중요한 새 선택 직전에는 다시 조회합니다.

관련 결과가 없으면 표현을 좁히거나 바꿔 1회 더 찾아보고 없다고 기록한 뒤 현재 근거로 진행합니다. 검색 실패는 ‘기억 없음’과 구분합니다. 일시 장애는 같은 질의의 제한된 1회 재시도를 운영 가설로 두고, 계속 실패하면 현재 자료로 안전하게 가능한 부분만 수행합니다. 이전 결정의 해석이 필수인 부분은 그 원문을 확인할 때까지 보류합니다. 장시간 반복 검색이나 다른 프로젝트로 범위 확대는 하지 않습니다. 의미 색인이 unavailable여도 키워드 검색이 가능한 계약이며, 결과를 같은 품질의 의미 검색이라고 쓰지는 않습니다.

3. 어떤 데이터를 언제·어떻게 넘길까

‘다시 비슷한 상황에서 선택을 바꿀 수 있는가?’와 ‘원문·실제 결과를 확인할 수 있는가?’가 선별 기준입니다. 새로움·근거·적용 범위가 없는 대화 요약은 보내지 않습니다.

대상시점·단위주체·실제 전달 방식 / 보완
대표 결재 답즉시 사건. 답변 상태가 바뀐 한 결정.현재 자동: 서버가 질문·선택지·선택한 버튼/메모·답변 시각·범위·결재 ID를 구성해 outbox 전송. 직원은 같은 결재를 memory_record로 중복 기록하지 않습니다. 직원 작성 설명은 대표 원문과 구분해야 합니다.
대화 속 명시 결정·제약의미가 확정된 사건. 모호한 논의는 후보로 남기고 확정 뒤 한 번.서버 보완 필요: 인증된 대표 메시지·대상 task·적용 범위를 보존해 대표 결정으로 수집. 현재 직원 memory_record로 옮기면 어디까지나 직원 보고입니다. 임시로 기록한다면 kind=lesson, basis=verified와 직접 확인한 원문 ID·인용을 넣고 ‘대표 원문을 확인한 직원 보고’라고 표시합니다. 대표 결정 분류를 직원이 만들어 붙이지 않습니다.
대표 수정 피드백안정된 수정 라운드 묶음. 한 글자 바뀔 때마다 보내지 않음.주담당이 수정 전후·이유·독자/목적·문서 버전·원문 ID를 정리해 lesson/verified로 기록할 수 있습니다. 그 문서의 기준을 모든 글의 취향으로 일반화하지 않습니다. 맥락이 확정되지 않은 의견은 후보로 보관합니다.
업무 결과·검증완료 또는 의미 있는 검증 단계. 한 작업의 결과 1묶음.직원이 memory_record(kind=outcome, basis=verified, evidence=실제 근거) 사용. 합격 기준·변경 버전/커밋·실행 결과·미확인·조건을 담습니다. 통과 수를 성과나 고객 가치로 바꿔 쓰지 않습니다.
실패 원인·교훈원인 확인 후. 오류 발생마다가 아니라 원인→조치→재검증이 연결될 때.확인된 mistake/lesson은 verified와 재현·원인 근거·재검증을 붙입니다. 증상만 있으면 outcome으로 ‘실패 관찰’만 기록합니다. 원인 가설은 ai_inference로 구분하며 재사용 가치가 없으면 업로드하지 않습니다.
자료의 채택한 변경안채택/반영 사건 + 후속 결과.자료 댓글 기능은 미구현: Agent-A 고려 설계 f_43Ud4K8WDtRK의 댓글·자료 ID·대상 버전·변경안·승인 원문·새 버전을 묶어 서버 사건으로 넘기는 제안입니다. 지금은 주담당이 실제 자료/결정 원문을 확인한 결과만 직원 보고로 남길 수 있습니다. 댓글·답변 자체를 자동 승인으로 읽지 않습니다.
외부 멘토링·학습 자료정리 완료 묶음. 출처별 핵심 주장과 적용 후보만.전체 녹취/강의 원문을 반복 전송하지 않습니다. 원문 참조·발언자 역할·조건·인용과 채택 여부를 구분합니다. 주담당이 외부 발언을 확인한 사실은 verified 근거로, 그 적용 추론은 ai_inference로 나누어 기록합니다. ‘외부 의견’은 content/evidence의 논리 분류이며 실제 enum이 아닙니다.
AI 추론·개선 후보선택적으로 안정된 후보.다시 시험할 수 있는 가설만 lesson/ai_inference로 남깁니다. 초안·자기평가·모델끼리의 동의는 자동 승격하지 않습니다. 이후 검증되면 새 결과 기록으로 연결합니다.
주기 정리주 1회, 10분 검토를 시작 가설로.새 사건·적용 결과·실패가 있는 때만 미수집/중복/정정 필요를 확인합니다. 새 근거가 없으면 기록과 모델 호출을 생략합니다. 주간 전체 요약을 무조건 재업로드하지 않으며 스케줄은 이번에 만들지 않습니다.

기록량 시작값: 한 완료 작업에 outcome 1건, 재사용할 교훈이 있으면 lesson 1건을 기본으로 검토합니다. 서로 다른 결정이 여러 개면 억지로 하나로 합치지 않되, 같은 사실을 직원별로 복제하지 않습니다. 이는 상한이나 현재 서버 규칙이 아닌 비용·중복을 줄일 운영 가설입니다.

제외: 비밀 키·인증 헤더·개인정보·민감한 제3자 정보, 전체 터미널 로그, 반복 진행 알림, 원문 없는 추측, 같은 사건 재요약, 검증하지 않은 원인, 선택되지 않은 초안. 필요한 로그는 핵심 명령·관찰 결과만 정리하고 정본 위치를 참조합니다. 게이트웨이의 일부 민감 문자열 차단이 모든 민감정보를 제거해 주는 것은 아닙니다.

4. 기억 계약: 사실의 등급과 실제 도구 필드를 나눕니다

논리적으로 구분할 종류: 명시한 기준 / 조건부 결정 사례 / 외부 의견 / AI 추론 / 검증 결과. 대표가 선택한 사실과 실제 성과는 별도입니다. 임시로 애니메이션을 뺐다는 한 결정에서 ‘애니메이션을 싫어함’이라는 공통 취향을 만들지 않습니다.

위는 내용 구성 계약입니다. 지금 없는 필드를 몰래 추가하지 않습니다. 현재 직원 도구에는 kind·basis·summary·content·evidence·commit_sha·task_id가 있고, 상세 상황/대안/범위/원문 ID·시각·버전·기대/실제 결과·대체 관계는 content와 evidence의 이름 붙인 항목으로 담을 수 있습니다. 구조화된 원문/버전/대체 필드와 자동 검증은 별도 보완입니다.

현재 프로젝트/작품 범위

IAMCEO 프로젝트를 게이트웨이 프로젝트로 매핑합니다. 같은 프로젝트 안에서는 다른 task의 경험을 검색할 수 있어 적용 범위를 반드시 확인합니다. task가 다르다고 문체·작품 설정이 자동 격리되는 것은 아닙니다.

공통 사용자 기준

대표가 공통 적용을 명시한 기준만 공유 후보로 둡니다. 지금은 다른 프로젝트를 자동 조회/업로드하거나 공통 bank를 상속하지 않습니다. 범위 확대가 필요하면 원문·공유 목적·활성 프로젝트 정책을 별도로 정해야 합니다.

게이트웨이 REST에는 supersedes가 있지만 현재 IAMCEO ExperienceInput/직원 도구는 이를 노출하지 않습니다. MCP 기록 도구와 IAMCEO memory_record도 같지 않습니다. IAMCEO 기록은 REST를 사용해 outcome도 받으며 source.service를 직접 정합니다. 원시 MCP의 제한을 그대로 옮기거나 일반 Hindsight API 필드를 추가하지 않습니다.

결재 outbox는 즉시 전송을 시도하고, 서버 시작과 기본 60초 간격으로 대기 건을 처리합니다. 같은 사건은 같은 ID·같은 본문으로 재전송합니다.이 60초는 기존 전송 대기열 처리이지 매분 새 기억을 수집/검색하는 정책이 아닙니다. 새 주간 정리와 혼동하지 않습니다.
일시 장애/5xx·키 읽기 오류는 제한된 지연 재시도, 최대 총 6회. 비재시도 오류 또는 소진은 rejected입니다.실패 건의 원인·담당·재개 여부를 확인할 운영 보기와 명시적 복구가 필요합니다. 반복 400/401/403을 무한 재시도하지 않습니다. 기억 업로드 실패로 원래 대표 결정이 무효가 되지는 않습니다.
직원의 memory_record/feedback은 현재 직접 호출이며 결재 outbox를 자동 공유하지 않습니다.장애 시 원문과 업로드 후보를 IAMCEO에 먼저 남기고 실패/미확인 여부를 구분하는 절차를 둡니다. 장래 공통 outbox를 쓰려면 별도 코드 보완이 필요합니다. 응답 유실 재시도는 같은 내용으로만 합니다.

정정·철회와 낡은 기억

현재 지시와 충돌하면 과거 기억을 적용하지 않고 최신 대표 원문을 확인합니다. 정정한 원문·버전·대상 기억 ID를 IAMCEO에 남깁니다. 현재 도구로는 새 content를 가진 정정 보고를 기록할 수 있지만 이전 기억을 검색에서 자동 제외하는 대체 처리는 되지 않습니다. 신뢰하는 서버가 게이트웨이 REST의 supersedes를 전달하도록 보완해야 합니다. 원본은 보존하고 기본 검색에서 제외하는 계약이며 삭제와 다릅니다. 철회된 내용은 정정 기록이 준비되지 않았더라도 현재 업무에서 사용 중지합니다.

같은 event_id에 본문/근거를 바꿔 재전송하지 않습니다. 정정은 새 사건과 명시적 대체 관계로 처리합니다. 현재 검색 래퍼가 superseded_by 등 모든 원시 메타데이터를 반환하는 것은 아니므로 정정 원문 확인을 대신할 수 없습니다. 결재를 다시 열어 새 답을 남기면 별도 사건은 생기지만 이전 결정의 자동 대체까지 구현된 것은 아닙니다.

유용성 피드백

helped: 실제로 적용해 합격 기준 충족이나 재발 방지에 도움이 된 근거가 있음. did_not_help: 실제 적용했지만 의도한 문제 해결에 도움이 없었음. contradicted: 같은 조건에서 원문·검증으로 내용의 오류/충돌이 확인됨. 단순 취향 변화나 다른 상황이면 범위 차이를 기록하고 바로 사실 오류로 투표하지 않습니다. 관련 없어 읽고 버린 기록, 아직 시험하지 않은 기록에는 자동 긍정/부정 피드백을 보내지 않습니다.

주담당 한 명이 적용 근거를 확인해 피드백을 남기는 안입니다. 현재는 기록한 작업과 다른 작업이어야 하고 동일 경험·작업·턴의 첫 피드백이 보존됩니다. IAMCEO는 turn_id를 직원별 고정값으로 전달하므로 같은 직원·같은 task에서 나중에 결과가 바뀌었다고 기존 값을 덮어쓸 수 없습니다. 다른 직원도 같은 건에 중복 투표하지 않게 운영상 한 명을 정하고, 후속 정정은 근거 있는 새 결과 기록으로 남깁니다.

코드에서 확인한 신뢰성 한계와 최소 보완

answerDecision은 결재/지시 저장을 마친 뒤 queueDecisionMemory를 호출합니다. 따라서 결재 원본과 memory_outbox 생성이 동일 트랜잭션이라는 보장은 없습니다. 그 사이 중단/실패의 누락 방지를 위해 원자적 사건 저장 또는 원본-미전송 재대조를 제안합니다. 실제로 누락이 발생했다는 뜻은 아닙니다.

현재 자동 본문에는 직원이 쓴 선택지 설명과 배경도 포함됩니다. 대표 선택 버튼 글·메모와 직원 설명을 더 명확히 분리하는 개선이 적절합니다. 직원 기록의 중복 ID는 직원·범위·kind/basis·summary/content로 계산되므로 담당이 달라진 동일 사건을 전역으로 묶거나 근거만 바꾼 정정을 처리하는 표준 사건 ID는 별도 보완입니다.

게이트웨이는 원본 저장과 색인을 구분합니다. 원본 저장 성공이 의미 색인 최신화/완료를 보장하지는 않습니다. 문서에는 키워드 검색과 색인 실패 상태가 별도로 설명돼 있습니다. 작업 MCP 키 자동 만료/현재 어댑터의 폐기 연동도 확인되지 않았으며 이번 운영 설계에서 임의로 켜지 않습니다.

6. 대표가 평가할 세 가지 예

A · 서비스 개선/개발

시작: ‘동일 직원의 여러 작업에서 원문과 task 귀속을 어떻게 보존하기로 했나?’를 limit 3으로 검색하고 적용 후보의 전문·결정 원문을 확인합니다.

선택 직전: 정본/요구가 바뀌면 재검색합니다. 예전 성공 사례로 현재 반영 권한을 추정하지 않습니다.

남길 것: 완료 시 실제 기준 커밋·재현/시험·한계는 outcome/verified 1건, 확인한 재발 원인이 있으면 lesson/verified. 대표 결재는 기존 자동 전송을 사용합니다. 다른 task에서 그 교훈을 적용·확인한 뒤에만 피드백합니다.

B · 자료 문체 수정

검색: ‘이 목적·독자·문서 유형에서 대표가 명시한 표현 기준과 수정 이유는?’를 수정 라운드 시작에 한 번 찾습니다. 이번 대표의 구체 수정 원문이 우선이며 단순 문장 수정마다 찾지 않습니다.

남길 것: 수정이 확정된 라운드의 전후 버전·대표 원문·바꾼 이유·범위를 lesson/verified로 선별합니다. 자료 댓글 사건 자동 전송은 Agent-A 설계에 해당하는 후속 기능입니다.

분리: 대표가 선택한 문체와 실제 독자 반응은 다른 결과입니다. 아직 읽는 사람의 반응을 보지 않았다면 성과가 좋았다고 쓰지 않습니다.

C · 작품/다른 프로젝트

현재: 다른 프로젝트가 비활성인 상태에서는 이 프로젝트의 memory_*로 그 작품을 자동 검색하거나 업로드하지 않습니다. 제공받은 현재 작품 원문·작가 의도·승인 범위로 진행합니다.

장래 활성화 시: ‘사업 소개서’ 기준을 ‘소설’로 가져오기 전에 작품 범위의 기준을 별도로 조회합니다. 공통 적용이 명시되지 않았다면 공유 취향으로 삼지 않습니다.

남길 것: 나중에 허용된 해당 범위에서 작품의 장면 의도·수정 원문·버전과 결과를 보존합니다. 외부 멘토 조언은 조언으로, 대표 채택은 별도 결정으로 남깁니다.

7. 첫 적용 범위와 평가

추천 시작 범위: 현재 활성 프로젝트에서 기존 결재 자동 전송은 그대로 두고, 비단순 업무의 시작/중요 선택 검색과 검증된 개발 결과·교훈의 선별 기록을 먼저 평가합니다. 대화 결정 자동 분류·자료 댓글 수집·공통 기준 공유·정정 supersedes·추가 outbox는 별도 보완으로 둡니다. 이번에 정책이나 자동 기능을 켠 것은 아닙니다.

대표 부담불필요한 재질문 수와 설명·검토·수정 시간을 비교합니다. 필요한 새로운 승인까지 줄였다고 평가하지 않습니다.
기록/조회량작업당 신규 사건 수·중복/정정 수·본문량·검색/get 수와 재시도·실패를 봅니다. 현재 도구가 자동 대시보드로 제공한다고 가정하지 않고 운영 기록부터 남기는 안입니다.
판단 재현결정 시점 이전의 원문·기억 스냅샷만 사용합니다. 현재 도구에는 시점 필터가 없으므로 검색어에 ‘이전’이라고 쓰는 것만으로 누출이 차단되지 않습니다. 사후 결정·회고·파생 요약을 제외한 별도 평가 자료가 필요합니다. 대표 의도 일치와 당시 현실 근거의 품질은 따로 채점합니다.

남은 선택: 첫 운영 평가를 ‘개발 재발 방지’와 ‘자료 수정 피드백 재사용’ 중 어느 반복 업무로 할지입니다. 현재 연결과 검증 근거를 활용하기 쉬운 개발 결과·교훈부터를 권합니다. 적용 범위 확대·새 자동수집·위임 권한은 아직 선택/승인하지 않았습니다.
