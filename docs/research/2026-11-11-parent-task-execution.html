여기서 상사 직원은 장래 제안의 책임 역할입니다. 현행 총괄의 직접 조사/구현 금지와 직원의 다른 직원 호출 불가는 현재 정책입니다. 그것을 이상적 구조의 필수조건으로 고정하지 않습니다. 적용하려면 직원에게 제한된 작업 실행 요청 권한을 주고 서버가 범위·수량을 검사하는 도구가 필요합니다. 기존 직원 토큰이나 전체 권한을 자식에게 그대로 복사하는 방식은 피해야 합니다.

CLI 세션·문맥모델이 보고 이어가는 대화입니다. 한 작업 실행은 여러 턴으로 이어질 수 있고, 제공자 교체 시 새 세션이 필요할 수 있습니다.

결정 원문·정본대표 결정과 실제 코드/문서의 기준 버전입니다. 자식의 완료 보고는 이 원문을 대체하거나 자동 승인하지 않습니다.

입력은 골라 줍니다. 역할 지침, 작업 목표·완료 조건, 필요한 결정 원문, 자료/정본 버전, 허용된 도구·범위만 전달합니다. 부모 전체 대화를 fork하거나 다른 작업 기록·공통 메모를 모두 로드하면 문맥 분리 효과가 줄어듭니다. 프로젝트 규칙·MCP·파일을 통해 다시 섞일 수도 있으므로 ‘별도 대화창’만으로 완전 격리됐다고 표현하지 않습니다.

2. 두 실행 방식 비교와 공급자별 확인 범위

CLI 내부 하위 에이전트IAMCEO 관리 작업 실행 기본안
적합한 일범위가 작고 요약 반환으로 끝나는 조사·로그 분석·검토.장시간 작업, 같은 업무 후속 대화, 실패 재개, 제공자 교체.
수명·재개공급자·버전·종류에 따라 다릅니다. 일시적 사용에 편하지만 모두 일회성이거나 모두 영속적이라고 단정할 수 없습니다.서버가 부모·task·native 세션 ID·세대·상태·마지막 확인 입력을 기록합니다. 지원되는 경우 같은 세션을 재개하고 불가하면 새 실행으로 인계합니다.
보고·취소부모 CLI 알림과 로컬 기록을 그대로 IAMCEO 수신 확인으로 볼 수 없습니다. 자식 상태 수집 어댑터가 필요합니다.출력 저장, 상사 알림, 수신 확인, 취소 요청과 실제 중단 확인을 별도 상태로 관리하도록 보완합니다.
비용·복잡성도입이 작지만 공급자 종속과 누락된 수명 관리가 남습니다.추가 관리가 필요하나 프로젝트 책임과 실행의 수명을 분리할 수 있습니다. 당장 모든 업무에 세션을 미리 만들 필요는 없습니다.

Codex

공식 문서는 하위 agent thread의 조정·중단과 부모 권한/MCP 상속을 설명합니다. App Server는 thread 시작·읽기·재개·fork를 구분하며 fork는 저장 이력을 복사합니다. 저장된 제공자와 다른 제공자로의 resume는 거절될 수 있습니다. [1] [2]

이 기능이 IAMCEO의 작업 실행 API로 이미 연결됐다는 뜻은 아닙니다. App Server 도입도 이번 결론의 필수조건은 아닙니다.

Claude Code

일반 하위 에이전트는 별도 문맥에서 시작하고 fork는 부모 대화를 물려받습니다. agent ID로 재개할 수 있으며 같은 부모 세션을 재개하면 재시작 뒤에도 이력을 사용할 수 있다는 안내가 있습니다. Explore/Plan은 재개 ID를 반환하지 않는 예외입니다. [3]

종류·버전·기록 보존에 따른 차이를 실행 어댑터에서 확인해야 합니다. ‘하위 에이전트는 전부 일회성’이라는 전제는 고칩니다.

Antigravity

공식 문서는 부모 대화 이력을 물려받지 않는 문맥, idle 자식의 메시지 재개, killed 자식의 재개 불가와 이력 조회를 설명합니다. [4]

이 문서만으로 프로세스 재시작 뒤 자식 재개나 IAMCEO의 현재 CLI 버전에서 같은 동작을 보장하지 않습니다. 이번에 공급자 실행 시험은 하지 않았습니다.

다른 제공자로 바꿀 때는 native 세션 ID를 옮겨 붙이지 않습니다. task와 부모 책임은 유지하고 새 run_id에 확정 입력·변경물·검증·미결 체크포인트를 넘깁니다. 이전 실행이 살아 있는지 불명확하면 새 쓰기 실행을 시작하지 않습니다.

3. 상사에게 남길 최소 보고와 서버의 전달 책임

식별: project_id / task_id / run_id / 부모 직원 / 이벤트 ID·순번 작업: 목표·완료 기준 / 입력 정본·버전 / 허용 범위 보고: 명시 결정·이유와 원문 ID / 확인 근거·반례 산출물 ID·버전 / 검증 결과·미확인 / 미결·다음 행동 상태: 진행·완료 보고·실패·판단 대기 / 체크포인트 참조

하위에서 선택한 구현 방법과 대표가 승인한 결정은 구분합니다. 주요 결정·가정 변경·충돌·검증·결과는 남기되 모든 토큰을 상사에게 복사하지 않습니다. 상세 도구 출력과 관련 원문은 열어 볼 수 있게 보존하고 상사는 필요한 부분만 읽습니다. ‘보고 받음’, ‘결과 검토됨’, ‘대표 승인됨’, ‘정본 반영됨’은 서로 다릅니다.

  1. 먼저 저장, 뒤에 알림. 서버가 자식 출력/산출물 참조와 보고 이벤트를 영속 저장하고, 상사에게 보낼 전달 항목도 같은 저장 절차에 묶습니다. 상사 알림이 실패해도 결과는 남습니다.
  2. 재전달은 같은 이벤트로. 수신 전 알림은 같은 ID로 재전달하고 서버가 중복을 억제합니다. 모델이 “전에 본 것 같다”고 판단하게 맡기지 않습니다. 알림 재시도 때문에 자식 작업을 다시 실행하지 않습니다.
  3. 수신 확인과 채택을 분리. 상사 수신함의 처리 위치·ACK를 저장하고, 검토/통합은 별도 기록합니다. ACK가 결과 채택을 뜻하지 않습니다. 중간에 상사가 중단돼도 미통합 결과를 다시 찾을 수 있어야 합니다.
  4. 불확실한 실행은 조회부터. 입력 전송 여부나 중단 여부가 불명확하면 unknown으로 두고 기록·native 상태를 대조합니다. 확인 없이 중복 생성/입력하지 않습니다. 취소는 요청과 실제 중단 확인을 나누고 결과·작업 사본을 보존합니다.

이것은 제안 계약입니다. 기존 IAMCEO에도 보고 저장과 전달 항목 연결, 재시작 시 보고 복구의 재료가 있지만, 임의의 상사 직원 아래 자식 실행 전체를 다루는 같은 계약이 완성됐다고 보지는 않습니다.

4. 작업 A 한 흐름으로 보는 누락·재개·충돌 처리

가정한 예시: 상사 직원이 서비스 소개 문구를 고치는 작업 A를 책임지고, 뒤이어 작업 B도 받는 상황입니다. 아래 식별자는 설명용이며 실제 실행은 없습니다.

  1. A 접수. task A에 run A1을 연결하고 새 실행 문맥에 목표·문서 v4·구현 근거·대표 결정 원문만 줍니다. 부모 전체 대화는 복사하지 않습니다. 수정 범위와 검토 기준을 고정합니다.
  2. 결과는 저장됐지만 상사가 못 받음. A1의 변경안 v1·검증·근거를 서버에 저장합니다. 알림 실패 시 같은 이벤트를 재전달합니다. 상사는 수신 확인 뒤 검토하며, ‘알림 미수신’을 ‘작업 실패’로 바꿔 A1을 다시 만들지 않습니다.
  3. 상사가 압축되거나 재시작. 프로젝트 요약, 작업별 최신 체크포인트, 미수신/미통합 이벤트를 서버에서 읽어 책임을 이어갑니다. 부모 모델이 이전 보고를 기억할 필요는 없습니다. 대표 결정은 원문으로 다시 엽니다.
  4. A 후속 지시. 같은 task A와 변경 대상 버전을 지정합니다. 서버가 A1의 native ID·소유·세대·입력 상태를 확인한 뒤 가능한 경우 같은 세션에 새 턴을 넣습니다. 재개 불가 또는 제공자 변경이면 A2를 만들고 A1을 대체/이어받았다는 관계와 체크포인트를 남깁니다. 전송이 불명확하면 재입력하지 않습니다.
  5. 다른 작업 B. B는 별도 task/run/문맥을 사용하며 A의 대화 이력을 자동으로 가져오지 않습니다. 공통 기준은 승인된 범위에서만 공유합니다. 상사에게는 A/B 상태와 필요한 판단만 함께 보입니다.
  6. 같은 저장소 충돌. A/B가 같은 정본 파일을 바꾸려 하면 시작값은 쓰기 1개만 허용하고 순차 처리합니다. 나중에 동시 쓰기를 허용할 때도 별도 워크트리·기준 커밋·변경 범위를 추적하고, 먼저 반영된 정본과 재대조한 뒤 통합합니다. 브랜치가 달라도 논리 충돌은 남습니다. 커밋/반영 권한은 기존 승인과 별개로 확대하지 않습니다.

5. 필요한 보완과 작은 시작값

현행 재료

직원별 세션 ID·세대·native 소유 확인, 공급자별 재개 경로, 보고·자료·전달 저장이 있습니다. task 연결 코드는 업무 기록을 묶습니다. 기존 MemberExecutionState.runId는 직원 실행/턴 추적이며, 이것만으로 task별 자식 세션이 생기지는 않습니다.

필요한 보완

부모–task–run–native 세션 매핑, 작업 범위로 제한된 실행/읽기/재개/취소 도구, 자식별 권한과 입력 제한, 보고 이벤트·ACK·통합 상태, 실패/불명확 상태 처리입니다. 부모 토큰을 자식에게 그대로 주면 task 출처와 권한 분리가 무너질 수 있습니다.

남는 한계

요약에서 중요한 조건이 빠질 수 있어 원문 참조가 필요합니다. 별도 문맥도 파일/MCP 접근까지 자동 차단하지 않습니다. 자식 재개·도구 제한·취소는 설치된 공급자 버전과 어댑터별로 검증해야 합니다. 구조만으로 품질이 보장되지는 않습니다.

장래 파일럿의 시작값 제안: 부모 아래 깊이 1단계, 동시에 실행하는 자식 1개, 각 task에 활성 실행 1개. 한 번에 완료 기준 1묶음만 맡기고, 30분 또는 도구 호출 20회 중 먼저 도달하면 체크포인트를 남겨 상사 검토로 돌아옵니다. 일반 실행 실패의 자동 재시도는 확인된 미실행/안전한 재시도에 한해 1회까지이며, 승인 대기·권한 밖 요청·기준 정본 변경·소유 충돌·전송/중단 불명확은 즉시 멈춥니다. 이 숫자는 검증할 운영 가설이며 공급자 기본값이나 이번 적용 설정이 아닙니다.

Hindsight는 기존 접점만 유지합니다. 검증된 결정·회고·결과를 기존 서버 업로드 경로로 넘기고 필요한 과거 근거를 기존 MCP 검색에서 찾도록 설계합니다. 정확한 실행·수신·승인·정본 상태는 IAMCEO/원본 저장소에 둡니다. 커스텀 API·도구명·범위 계약은 미확인이며 이번에는 업로드/검색을 호출하지 않았습니다.

‘프로젝트별 책임 + 필요 시 전문 능력’은 유지합니다. 여기에 대표가 짚은 한계를 해결하도록 작업별 실행의 수명과 보고 전달을 서버 책임으로 추가하는 안입니다. CLI 하위 에이전트만 켜는 것보다 보완은 크지만, 후속 지시·실패·제공자 교체를 일관되게 관리하는 기본안으로 적합합니다.

이번 검토는 순차로 수행했으며 하위 에이전트·직원·세션을 생성하지 않았습니다. 역할/코드/서버/기억/설정 변경, 실행 시험, 외부 모델 호출도 없습니다. 현재 w1의 추가 보완·7881 적용 결재에 이 제안을 합치거나 승인한 것이 아니며 개발 담당에게 재지시하지 않았습니다.
