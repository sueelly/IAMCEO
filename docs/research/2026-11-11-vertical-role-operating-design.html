추천 구성첫 세팅 계약업무 흐름기억현재 제품과 차이사실 검증첫 실험

1. 추천 구성: 프로젝트 총괄 + 실행 주담당, 전문가 1명은 필요할 때

책임은 버티컬하게, 능력은 공통으로. 서비스·작품의 목표와 최종 결과는 같은 책임선에 두고, 조사·구현·디자인/콘텐츠·검토는 재사용할 역할 계약과 스킬로 준비합니다. 이 네 직무를 모두 상주 세션으로 만들 이유는 없습니다.

지속되는 책임선

프로젝트 총괄 1명: 목표·배정·의존성·결과 종합을 책임집니다.
실행 주담당 1명: 실제 조사·제작과 산출물 통합을 맡습니다.

현행 총괄은 직접 조사·코드·문서 수정을 하지 않으므로 둘을 같은 세션으로 합치지 않습니다. 주담당도 다른 직원을 직접 호출할 권한은 없습니다.

필요할 때만 분리하는 실행

전문 작업자 또는 독립 검토자 1명을 추가하는 것이 첫 파일럿의 시작값입니다. 기본 2명, 필요 시 3명이며 새 직원을 지금 만들자는 지시는 아닙니다.

단순 작업은 주담당이 스킬로 순차 처리합니다. 조사량이 크거나 문맥 분리·별도 검증의 실익이 있을 때만 총괄이 같은 프로젝트의 적합한 기존 직원을 찾아 맡깁니다.

전체 조율은 얇게

대표가 공통 우선순위·검토 시간·프로젝트 간 충돌을 정합니다. 기존 본사는 일회성 일반 업무와 현황 정리에 활용할 수 있습니다.

현재 본사는 프로젝트 총괄을 자동 지휘하는 상위 매니저가 아닙니다. 프로젝트 간 자동 배정·공용 전문 세션 풀은 보완이 필요한 장래 기능입니다.

프로젝트가 N개라고 3N명의 실행을 동시에 돌릴 필요는 없습니다. 책임 기록은 유지하고 당장 진행할 프로젝트의 주담당부터 사용합니다. 시작 실험은 전체에서 실행 작업 1개, 필요 시 검토 1개를 순차로 이어 보는 안입니다. 이는 운영 제안이며 현재 동시 실행 설정을 바꾸지 않습니다.

대안과 선택 이유
구성장점대표에게 남는 부담 / 불리한 경우
직무별 고정 직원전문 절차를 반복하기 쉽습니다.개발·영업·디자인 결과를 대표가 다시 연결하기 쉽습니다. 직무별 물량이 크고 업무 경계가 안정적일 때 유리합니다.
프로젝트 책임선 + 필요 시 전문가 추천목표·고객·작품 의도가 한곳에서 이어지고 공통 능력도 재사용합니다.현재는 총괄과 실행 주담당 사이에 한 단계가 필요합니다. 주담당의 통합 능력이 부족하면 수정 비용이 커지므로 작게 검증합니다.
한 담당자 + 스킬만전달 비용이 작고 연속된 맥락을 유지합니다.짧은 문서 수정·소설 한 장면에는 좋은 기본값입니다. 독립 검증이나 넓은 조사가 필요하면 분리하는 편이 낫습니다. 현행 총괄 자체가 이 실행자가 되는 안은 아닙니다.

같은 결정을 위해 고객·제품 상태를 함께 봐야 하는 개발·영업·소개 콘텐츠는 서비스 책임선에 묶습니다. 인물·세계관·서사 의도가 누적되는 소설은 작품별 책임선에 둡니다. 강의·멘토링은 우선 일반 입력으로 받아 적용할 프로젝트에 근거와 함께 넘깁니다. 독립적인 학습 목표가 계속되면 그때 프로젝트로 둘 수 있습니다.

LOERA·특정 작품·ENOUV는 제공 제안문의 예시/맥락입니다. 이 프로젝트에서 실제 서비스 상태, 과거 취향, ENOUV 구조 결정은 확인하지 않았습니다.

2. 실제 첫 세팅에 쓸 계약

가정: 서비스 A에서 “멘토링 피드백을 검토 가능한 개선안으로 바꾸기”를 시험한다면 아래처럼 둡니다. 목표·제품 상태·예산은 실제 자료를 읽어 채울 값이며 아직 확정되지 않았습니다. 역할 이름보다 입력·산출물·책임 경계가 중요합니다.

① 서비스 A 총괄 — 책임·조정

목적 / 범위
승인된 서비스 목표에 맞춰 일을 나누고 최종 완료 여부와 다음 행동을 종합합니다. 직접 조사·제작은 직원에게 맡깁니다.
현재 목표 / 상태
파일럿 목표와 정본을 먼저 확인. 접수·진행·검토·판단 대기를 구분해 판에 반영합니다.

대표 판단 / 종료
프로젝트 간 우선순위·예산·목표 변경은 대표 판단. 준비 가능한 결과를 모은 뒤 결정 항목을 올리고, 완료 또는 명확한 보류로 끝냅니다.

목적 / 범위

현재 목표 / 상태
예: 피드백 1묶음 → 채택 후보·보류 사유·소개 문구 초안. 실제 기능·기존 결정은 미확인부터 시작합니다.

대표 판단 / 종료

목적 / 범위

현재 목표 / 상태

대표 판단 / 종료
유료 자료·새 접근 권한이 필요하면 판단 요청. 질문별 근거 또는 확인 불가 이유가 있으면 종료합니다.

목적 / 범위

현재 목표 / 상태

스킬 / 검토 기준

대표 판단 / 종료

목적 / 범위

현재 목표 / 상태
예: 소개서 v4의 메시지·배치 개선. 초안인지 확정본인지 표시합니다.

독자·의도·정본·유지 조건 → 변경안/시안, 바꾼 이유, 비교 자료.

문서/시각 제작·목적별 문체·작품 일관성 절차. 설치·접근 가능한 스킬만 사용하며 이름만으로 기능을 가정하지 않습니다.
대표 판단 / 종료
새 주장·작품 핵심 의도 변경·발행은 판단 대상. 지정 형식의 결과와 기준별 확인 내용을 내면 종료합니다.

처음 저장할 것은 ①②의 프로젝트별 계약과 ③~⑥의 재사용 계약입니다. 계약이 여섯 개라고 세션 여섯 개를 켜지 않습니다. 주담당이 충분히 처리할 수 있는 짧은 조사·문체 수정은 같은 세션의 순차 작업으로 끝냅니다. 독립 검토는 스킬을 바꿔 자가검토한 것과 구분해 기록합니다.

작품 프로젝트에서는 ①②의 목표·정본·합격 기준만 인물/세계관/장면 의도로 바꿉니다. 사업의 고객 정보나 소개서 문체를 기본 기억으로 가져오지 않습니다. 영업은 해당 서비스의 주담당 범위에 두고, 발송·약속·계약 판단은 현행 승인선에 둡니다.

새 판단과 결과 연결
  1. 접수. 대표가 서비스 A 대화에서 “이번 멘토링을 개선안으로 정리”라고 지시합니다. 적용할 목표·자료·완료 기준을 주담당에게 넘깁니다. 새 task 기능이 실제 적용되기 전에는 제목의 일관된 업무 참조와 메시지/자료 ID로 잇습니다.
  2. 필요한 문맥만 구성. 주담당이 현재 정본과 명시한 결정을 확인하고, 연결된 경우에만 기존 Hindsight MCP 검색에서 관련 기준·사례를 가져옵니다. 연결 전에는 제공된 원문·자료로 진행하고 ‘기억 검색 미사용’을 표시합니다.
  3. 전문 작업. 사실 확인이 많다면 주담당이 질문·입력 버전·반환 형식을 총괄에 보고합니다. 총괄이 같은 프로젝트의 적합한 기존 직원을 team_assign으로 호출하며, 잠든 직원은 현행 규칙에 맞게 team_resume합니다. 새 직원은 별도 승인 범위에서 판단합니다. 실제 전달은 서버의 대기열과 실행기가 처리합니다.
  4. 결과 반환과 재개. 조사자가 file로 근거 자료를 올리고 post.file_ids로 보고합니다. 보고가 총괄을 깨우고, 총괄이 원본 보고 ID와 자료 버전을 주담당에게 전달합니다. 직원이 글을 남겼다고 다른 직원이 자동 실행되는 구조는 현재 없습니다.
  5. 검토와 통합. 주담당이 변경안 v1을 만들고, 필요하면 총괄이 검토자에게 같은 완료 기준을 보냅니다. 지적은 해당 버전에 연결합니다. 정본이 v4에서 v5로 바뀌었다면 기존 변경안을 그대로 덮어쓰지 않고 다시 대조합니다. 수정된 최종 결과는 주담당이 통합합니다.
  6. 대표 검토. 결과·전후 차이·근거·검증·미확인·남은 판단을 한 보고에 묶습니다. 판단은 ask, 손수 할 일은 todo, 자료는 file로 연결합니다. 이미 허용된 범위 안의 수정까지 매번 새 결재로 올리지는 않습니다. 새로운 외부 발송·반영 권한은 기존 규칙대로 확인합니다.
  7. 기억과 후속. 대표의 결정 원문, 적용한 버전, 실제 결과를 업무 기록에 연결합니다. 검증된 기록·회고의 업로드는 대표의 기존 서버 경로를 사용하도록 설계합니다. 이번에 업로드하거나 지침을 바꾸지는 않습니다.

4. Hindsight: 공통 기준과 프로젝트 경험을 나누고 원문으로 돌아갈 수 있게

대표가 확인한 조건: Hindsight는 이미 구축 중이며, 서버에서 업로드하고 필요한 내용을 MCP로 검색하는 경로가 있습니다. 이번 자료에서는 그 경로에 맞출 기록·범위 계약만 제안합니다. 실제 업로드 API, MCP 주소/도구명, 인증, 배포 버전은 확인하지 못했습니다.

공통 사용자 기준

대표가 명시적으로 여러 업무에 적용한 기준만 공유합니다. 특정 사업 문서에서의 수정 요청을 창작 취향 전체로 일반화하지 않습니다.

서비스·작품 기록

서비스의 고객·결정·실험 결과, 작품의 인물·서사·설정은 해당 범위에 둡니다. 강의 내용은 외부 의견/학습 입력이며, 채택 결정과 구분합니다.

작업 실행 기록

현재 정본·진행·전달·승인·발송 여부는 IAMCEO와 원본 저장소에서 확인합니다. 검색 기억으로 실행 권한이나 완료 상태를 추정하지 않습니다.

기록 종류의미 / 다음 작업에서 쓰는 법
명시한 지시원문·시각·범위·버전 연결. 현재 지시와 충돌하면 최신 원문과 적용 범위를 다시 확인합니다. 기억에 있다는 이유로 승인 범위를 넓히지 않습니다.
결정 사례그 상황에서 채택/기각한 대안과 이유. 비슷한 제약에서만 참고하며 성공 여부는 별도로 봅니다.
추론한 선호AI의 가설임을 표시하고 근거·반례·확신의 한계를 남깁니다. 확정 규칙으로 승격하거나 자동 적용하지 않습니다.

결정 기록 묶음 제안: 프로젝트/작품·작업 참조 → 상황·목표 → 검토한 대안 → 선택/기각 → 이유·제약 → 적용 범위 → 명시/사례/추론 구분 → 결정 원문 ID·정본 버전·시각 → 기대 결과 → 실제 결과와 측정일 → 후속 수정/대체 관계. 이는 IAMCEO 쪽 논리 계약이며 실제 Hindsight API 스키마가 아닙니다.

연결 방식 제안: 기존 서버 업로드 경로에 검증된 기록과 원문 참조를 넘기고, 실행자는 기존 MCP 검색에 업무 목적·허용된 프로젝트/작품 범위·기준 시점을 전달할 수 있도록 맞춥니다. 공통 기준과 개별 기록을 어떤 bank/tag로 표현할지는 기존 계약을 먼저 확인해 정합니다. 단순히 검색어에 프로젝트 이름을 넣는 것만으로 접근 범위가 보장된다고 보지 않습니다.

공식 문서의 retain은 저장, recall은 기억 검색, reflect는 기억 기반 답변 생성입니다. 이는 대표 MCP에서 같은 이름을 제공한다는 확인이 아닙니다. bank는 분리된 단위이며 공통 기억의 자동 상속을 가정할 수 없습니다. directive도 reflect에 적용되는 규칙으로, 외부 실행 권한 통제를 대신하지 않습니다. [S6: Hindsight FAQ] [S7: Memory Banks]

자가개선의 최소 흐름
실제 수정/실패와 결과 기록 → 재사용할 개선 후보 1개와 적용 범위 제안 → 과거 사례·다음 유사 작업으로 비교 → 검토 후 채택 → 버전·효과·되돌릴 기준 기록. 단순 대화 축적, 모델 가중치 재학습, 자동 권한 확대는 서로 다릅니다. 이번에는 자체 기억 DB·검색 엔진·자동 지침 수정 시스템을 만들지 않습니다.

개선이 악화되면 해당 후보를 철회/대체한 원문과 버전을 남기고 이전 기준으로 돌아갈 수 있어야 합니다. 공통 규칙으로 확대하는 일, 대표 결정 변경, 실행 권한 확대는 별도 판단 대상입니다. 에이전트의 자기평가나 상호 동의만으로 채택하지 않습니다.

하나의 검토 화면홈·결재함·대화·자료가 있고, 새 작업 선택이 연결을 강화하는 중입니다.당장은 최종 post 한 건에 자료·근거·판단을 모읍니다. ENOUV식 정본 분기/블록별 변경안 반영이 IAMCEO에 구현됐다고 쓰지 않습니다. 통합 검토 UI는 별도 보완 범위입니다.
전체 조율·Hindsight본사는 일반 업무/프로젝트 생성 역할이며 프로젝트 간 작업을 직접 맡는 지침이 아닙니다. 대표의 Hindsight 서버 업로드·MCP 검색은 제공 사실이나 이번 연결 계약은 미확인입니다.공유 자원 충돌은 대표에게 요약합니다. 자동 전사 배정과 Hindsight 범위·실패/재시도 연결은 필요 시 별도 설계·검증합니다.

현재 활용 가능한 설정 재료: 직원의 이름·역할 설명, 같은 프로젝트 직원 배정/재개, 모델·제공자 선택 화면, 자료/보고·결재 연결입니다. 짧은 역할 목적은 직원 역할에, 목표·현재 상태·이번 입력/산출물은 작업 지시에, 반복 절차는 사용 가능한 스킬/참조 자료에 두는 구성이 적절합니다. 역할 템플릿 전체를 덮어써 승인 규칙까지 바꾸는 방식은 첫 세팅에 필요하지 않습니다.

서버가 처리할 일: 프로젝트/토큰 범위, 원문 출처, ID·자료 연결, 중복/대기열·전달 상태, 세션 소유와 안전한 재개 조건. 총괄이 판단할 일: 목표에 맞는 작업 분해, 선후관계, 담당 적합성, 완료 근거와 충돌 종합. 총괄이 모든 도구 실행을 개별 승인하거나 모든 대화 원문을 중계할 필요는 없습니다. 작은 후속 수정은 기존 주담당에게 직접 이어갈 수 있고, 총괄은 중복 지시 없이 판을 맞춥니다.
