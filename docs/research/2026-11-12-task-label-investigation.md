세 글의 저장 ID가 같은 것은 원본 조회와 읽기 전용 DB 대조로 확인했습니다. **선택 ID를 캡처에서 직접 수집한 것은 아닙니다.** 클릭한 보고의 `m.taskId`를 선택 함수에 넘기는 현행 코드와 원본 기록을 대조하면 위 ID로 이어집니다. 선택된 화면 제목이 비슷하다는 이유만으로 같은 작업이라고 처리하지 않았습니다.

현재 작업 목록에서 이 ID의 제목은 ‘대화 속 작업 클릭·메인 합치기·대표 화면 확인’, 진행판 상태는 done입니다. 당시 캡처에는 끝말이 ‘적용’으로 보입니다. 현재 레코드의 갱신 시각은 13:33:07Z이며 ID는 같습니다. 코드상 작업 이름은 메시지에 옛 이름을 복사하지 않고 현재 작업 목록에서 조회합니다. 정확한 개명 전후 이벤트 이력은 수집하지 않았습니다.

`delivery=delivered`는 보고 전달 상태입니다. 두 총괄 글의 delivery가 null이어도 같은 작업에 저장돼 있습니다. 전달 여부로 작업 연결이나 완료 여부를 판단하지 않았습니다. 카드의 ‘완료/진행’은 그 글의 보고 종류이며, 현재 진행판의 전체 작업 상태와도 별개입니다.

## 4. 직원 필터와 w1 수정의 경계

지금 배포 작업 사본의 visibleTasks는 받는 직원을 고르면 task.memberId가 같은 작업만 보입니다. 진행판 유래 작업은 등록 직원이 null이어서 칩에서 빠질 수 있습니다. 반면 Thread의 작업 대화는 taskId로 글을 고르는 별도 경로이며, 입력칸에서 직원을 고르는 것을 작성자별 보고 검색과 동일하게 볼 수 없습니다. 이미 작업이 선택돼 있으면 칩 목록을 좁히지 않고, 다른 받는 직원을 고르면 작업 선택이 풀리는 규칙도 있습니다.

직원 보고의 작업 귀속 누락 원인·수정은 w3 별도 조사입니다. 이번에는 메시지의 저장 ID를 조회했으며 그 업무를 다시 실행하거나 전체 보고의 원인을 대신 단정하지 않았습니다.

## 6. 최소한으로 더 필요한 증거와 권장 다음 단계

대표에게 새 결정을 요구할 상황은 아닙니다. 정확한 장면이 다시 생기면 **선택한 칩과 문제 카드가 함께 보이는 한 화면, 카드 제목·시각**이면 우선 특정할 수 있습니다. 직원 선택이 걸려 있으면 그 표시도 함께 있어야 합니다. 받는 직원 칩, 실행 띠, 질문 카드 중 어느 부분이 다른지 구분합니다.

그 장면을 개발 담당이 정상 경로로 다시 볼 때 필요한 진단 값은 선택 draft.taskId, 해당 카드의 data-mid/저장 taskId, 그 ID의 현재 제목, 실행 띠라면 별도 run.taskIds입니다. 전후 값이 실제로 다를 때 비로소 표시 결함/선택 갱신 문제로 좁힙니다. 이 값의 수집이나 UI 진단 기능을 이번에 새로 구현하지 않았습니다.

선택한 작업 제목과 실행 작업 제목의 구분이 어렵다는 점은 문구 개선 후보입니다. 예를 들어 실행 띠를 ‘현재 실행 작업’으로 명확히 하고 긴 작업명은 전체 제목을 확인할 수 있게 하는 정도입니다. 이는 검토 제안이며 구현·추가 결재를 올리지 않았습니다.
