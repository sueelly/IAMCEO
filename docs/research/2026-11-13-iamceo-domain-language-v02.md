# 업무·내 차례를 기준으로 쓰는 IAMCEO 공통 사전

v0.2 · 기준 용어 확정판 · 2026-11-13 정리

확정 근거: 결재 d_axaECBEcoHJQ의 대표 답 “업무·내 차례로 부르자”. 맡기는 결과는 업무, 대표 행동은 내 차례로 구분합니다. 나머지 세부 명칭·메뉴 배치·기능 구성은 계속 다듬을 권장안입니다.

기준 용어는 업무·내 차례로 확정했습니다. 이를 중심으로 프로젝트·직원·대화·자료·검토까지 일곱 가지 말을 구분해 씁니다. 앞으로 기능을 고칠 때 이 뜻부터 맞춥니다. 모든 이름을 새로 만들기보다 익숙한 말은 유지하고, 지금 겹치는 말과 범위를 정리합니다.

## 1. 먼저 이 한 문장으로 이해하면 됩니다

프로젝트 안에서 업무를 맡기고, 담당 직원이 대화로 보고합니다. 대표는 자료를 검토하고, 내 차례에 모인 판단이나 직접 할 일을 처리합니다.

예: ‘서비스 A 프로젝트에서, 소개서 수정 업무를 문서 담당에게 맡겨. 수정안은 자료에서 보고, 내가 골라야 하는 것만 내 차례에 올려줘.’

## 2. 기본 말 일곱 가지

| 이름 | 뜻과 경계 | 바로 쓸 문장 |
|---|---|---|
| 프로젝트 | 하나의 목표나 맥락을 계속 이어 가는 업무 공간. 여러 업무·직원·자료를 담음. 서비스뿐 아니라 작품·강의 준비도 가능 | ‘이 프로젝트는 서비스 A를 만드는 곳이야.’ |
| 업무 | 끝낼 결과와 완료 기준이 있는 일 하나. 대화나 직원, 파일 개수와 같지 않음 | ‘이번 업무는 소개서 첫 장을 고치는 거야.’ |
| 직원 / 담당 직원 | 직원은 일을 맡는 AI 역할. 담당은 그 업무 결과를 책임지는 관계. 같은 직원이 여러 업무를 맡아도 업무는 별개 | ‘이 업무 담당은 문서 담당이야.’ |
| 대화 | 지시·질문·보고·후속 의견이 이어지는 기록. 업무별로 볼 수 있으며, 대화를 봤다고 실행한 것은 아님 | ‘소개서 수정 업무의 대화만 보여줘.’ |
| 자료 | 다시 열어 읽고 검토하는 문서·이미지·결과물·참고 내용. 한 업무에 여러 자료, 한 자료에 여러 버전이 있을 수 있음 | ‘최종 소개서는 자료로 남겨줘.’ |
| 검토 | 자료를 보면서 질문하고, 답변·수정안을 확인하고, 채택 여부를 판단하는 과정 | ‘이 문장은 과장돼 보여. 수정안을 보여줘.’ |
| 내 차례 | 지금 대표가 답하거나 선택하거나 직접 처리해야 하는 항목. 직원이 기다리는 모든 상태가 아님 | ‘내가 지금 할 것만 모아서 보여줘.’ |

‘프로젝트 → 업무 → 자료’는 서로 관련된 단위지만 딱 한 줄의 폴더 구조는 아닙니다. 자료가 아직 업무에 지정되지 않았거나, 기존 자료를 다른 업무에서 참고하는 경우도 허용합니다. 프로젝트 전체에 관한 지시도 매번 억지로 업무 하나를 만들 필요는 없습니다.

‘직원’은 사람처럼 부르는 운영 개념이고, 모델은 그 직원이 사용하는 AI입니다. 담당·모델이 바뀌어도 같은 업무의 원문·결정·자료 연결은 이어져야 한다는 것이 이 정의의 기준입니다. 모든 직원을 상주시키거나 새 세션을 늘리자는 뜻은 아닙니다.

## 3. 화면 이름은 이렇게 읽히게 맞춥니다

권장 메뉴 구성(구체 배치는 미확정): 홈 / 내 차례 / 팀 / 대화 / 자료

| 지금 섞여 있는 말 | 권장 표현 | 사용 원칙 |
|---|---|---|
| 작업·task·일 목록·진행판의 일 | 업무 / 업무 목록 | 대표가 맡긴 결과 단위는 ‘업무’. 진행판은 업무 상태를 보는 화면이며 별도 종류의 일이 아님 |
| 결재함·내가 할 일·대표 차례 | 내 차례 | 묶음 이름은 하나. 안에서는 ‘선택 필요 / 직접 할 일 / 실행 허용 요청 / 답변 필요’로 구분 |
| 전체 | 모든 대화 | 이 프로젝트의 업무 대화와 업무 미지정 글을 함께 봄. 다른 프로젝트까지 보는 뜻이 아님 |
| 작업이 없음·task 없음 | 업무 미지정 | 글에 연결된 업무가 없다는 사실. 내용이 쓸모없거나 모든 업무에 공통이라는 판단을 덧붙이지 않음 |
| 지금 상황 | 지금 상황 | 유지. 현재 / 진행 / 대표 차례 / 다음 네 줄로 씀 |
| 진행·완료 옆 직원·작업 이름 | 진행 보고 · 문서 담당 · 업무: 소개서 수정 | 보고 종류 / 작성자 / 글의 업무를 구분. 지난 ‘완료 보고’를 지금 실행 상태로 읽게 하지 않음 |
| 실행 … 작업: A, B | 지금 처리 중: A, B | 직원이 지금 처리하는 범위. 현재 보고 있는 업무 대화와 별개 |
| Agent-A·Workbench 등 기능 이름 | 자료 검토 | 대표가 누르는 기능 이름은 목적 중심. 사용 엔진/서비스 이름은 연결 설정의 세부 정보 |

이 표에서 업무·내 차례의 용어 기준은 확정됐고, 나머지 표현과 메뉴 배치는 권장안입니다. 사전 확정과 실제 메뉴·버튼 적용은 구분합니다. ‘내 차례’로 모은다고 서로 다른 승인 권한과 직접 할 일의 처리를 하나로 합치지는 않습니다.

## 4. ‘모든 대화’와 ‘업무 미지정’은 꼭 구분합니다

- 모든 대화: 이 프로젝트 안의 여러 업무 글과 업무 미지정 글을 모두 보여 주는 보기 범위.
- 업무 미지정: 특정 글에 업무가 연결되지 않은 저장 상태.
- 업무별 대화: 선택한 업무에 실제로 연결된 글만 보는 범위.
- 받는 직원: 지금 쓰는 글을 받을 대상. 그 직원이 쓴 모든 보고를 검색하는 필터와 같지 않음.
- 지금 처리 중: 선택한 직원의 실제 실행 범위. 다른 업무를 보고 있어도 직원이 하던 일은 저절로 바뀌지 않음.

따라서 ‘직원에게 직접 보내기’, ‘업무 대화 보기’, ‘지금 처리 중인 직원 멈추기’는 다른 동작입니다. ‘다른 업무를 골랐으니 그 일로 실행도 바뀌었다’고 표현하지 않습니다. 화면을 선택한 것과 보낸 것은 구분합니다.

## 5. 자료와 검토에서 쓸 말

| 이름 / 버튼 | 뜻 | 구분할 것 |
|---|---|---|
| 댓글 / 답글 | 그 자료·버전에 붙인 의견과 이어지는 답 | 답변 도착만으로 자료가 바뀐 것은 아님 |
| 수정안 / 수정안 보기 | 아직 채택하지 않은 구체적인 변경 후보와 이유 | 새 본문과 전후를 볼 수 있어야 함 |
| 이 수정안 반영 | 확인한 수정안을 실제 자료에 적용 | 일반 답변 동의·개발 실행 허용·배포와 다름 |
| 버전 / 이전 버전 | 같은 자료에 저장된 내용의 특정 시점 | 수정안·과거 원문·현재 반영된 자료를 섞지 않음 |
| 저장됨 | 기록이나 초안이 보관됨 | 현재 자료에 반영됐다는 보장은 아님 |
| 반영됨 | 해당 수정이 현재 자료에 적용되고 새 본문까지 확인됨 | 코드 커밋·서비스 배포·다른 자료 승인과 별개 |

‘정본·snapshot·proposal·artifact’는 대표에게 기본으로 요구하지 않습니다. 화면에서는 ‘현재 자료 / 이 댓글의 원문 / 수정안 / 이전 버전’처럼 대상을 붙여 씁니다. v1·v2 같은 표시는 저장 이력의 이름이고, 새 이름이 업무나 자료의 식별자를 대신하지 않습니다.

## 6. 상태는 한 줄로 뭉치지 않습니다

업무의 상태, 대표가 해야 할 일, 자료의 상태는 따로 말합니다.

| 어디의 상태인가 | 쓸 말 | 뜻 |
|---|---|---|
| 업무 | 예정 / 진행 중 / 보류 / 막힘 / 완료 | 아직 시작 전 / 실제 수행 / 의도적으로 미룸 / 원인 때문에 진행 불가 / 정해 둔 완료 기준 충족 |
| 대표 차례 | 없음 / 선택 필요 / 답변 필요 / 직접 할 일 / 실행 허용 요청 | 무엇을 해야 하는지 명시. 원인을 모르는 입력 대기를 전부 승인 대기로 만들지 않음 |
| 자료 검토 | 답변 도착 / 수정안 준비 / 검토 필요 / 반영됨 | 결과가 도착한 단계와 실제 자료가 바뀐 단계를 구분 |
| 전달 | 보냄 / 대기 중 / 전달됨 / 전달 실패 | 글의 전달 단계. 업무 완료·직원 실행 완료의 근거로 사용하지 않음 |

완료 기준은 업무를 맡길 때 정합니다. 모든 업무가 대표의 수락을 거쳐야만 끝나는 구조로 만들지는 않습니다. 시험·형식 확인으로 끝낼 일과 대표 판단이 필요한 일을 그 업무 기준과 권한으로 나눕니다. 예: ‘안내문은 지정 형식으로 자료에 남기면 완료’, ‘외부 발송은 대표가 허용한 뒤에만 실행’.

위 상태표는 공통 언어의 목표 정의입니다. 현행 진행판의 네 칸이나 직원 CLI 상태가 이미 이 정의대로 자동 판별·통합된다는 뜻은 아닙니다.

## 7. 기억과 기술 용어는 필요한 곳에서만 설명합니다

- 기억: 지난 결정·수정 이유·검증 결과를 나중에 참고하는 기록. 현재 지시·승인·실행 상태를 대신하지 않습니다. 대표 화면에서는 ‘지난 결정 참고’, ‘판단 기준’, ‘이번 업무에 참고한 기록’처럼 용도를 함께 씁니다.
- 모델: 직원이 사용하는 AI. GPT·Claude·Gemini 이름만으로 역할이나 권한을 정하지 않습니다.
- 연결 도구: 다른 서비스에서 읽고 쓰는 기능. MCP 같은 구현 방식은 연결 설정의 세부로 둡니다.
- 현재 실행: 직원이 한 번 시작해 응답하거나 멈출 때까지 처리하는 단위. 업무 하나와 항상 같지 않습니다. 기본 조작은 ‘직원 멈추기’, 실제로 영향을 받는 업무를 함께 표시합니다.
- 업무 번호·자료 번호: 이름을 바꿔도 원래 대화·자료·결정을 찾는 연결 기준. 내부 task_id·file ID와의 정확한 대응은 개발 문서에서 관리합니다.

## 8. 앞으로 고도화할 때 지킬 짧은 규칙

1. 새 기능보다 먼저 ‘대표가 무엇을 보고 무엇을 결정하나’를 한 문장으로 쓴다.
2. 이미 있는 개념이면 같은 말을 쓴다. 새 이름은 기존 개념과 정말 다를 때만 만든다.
3. 기본 사전에 뜻·포함/제외 범위·실제 사용 문장 하나를 추가한다.
4. 화면·알림·직원 보고·자료 안내가 같은 대상을 같은 말로 부르는지 확인한다.
5. 이름을 고쳐도 원래 ID·기록·결정 링크는 유지한다. 실제 단위가 달라지면 명칭 변경과 구조 변경을 따로 다룬다.
6. 대표가 헷갈린 문장을 모아 다음 판을 고친다. 대표가 확정한 용어와 아직 제안인 세부 사항을 구분한다. 제안을 승인된 결정이나 자동 역할 지침으로 확대하지 않는다.

현재 ‘진행판 일’과 ‘작업’은 내부 객체가 따로 있고, 연결된 경우와 직원이 별도로 등록한 경우가 있습니다. 대표 개념을 ‘업무’로 통일하더라도 두 객체의 ID를 자동으로 합치는 것은 아닙니다. 이름 통일부터 할 수 있는 부분과 코드/운영 계약 정리가 필요한 부분을 후속 적용에서 나눕니다.

## 9. 확정한 기준과 다음 적용 순서

대표가 확정한 기준: 맡기는 결과 단위는 ‘업무’, 대표가 직접 처리할 것은 ‘내 차례’라고 부릅니다. ‘할 일’ 하나로 AI 업무와 대표 행동을 함께 부르지 않습니다.

기존 ‘작업·일 목록’ 표시는 후속 적용에서 ‘업무’ 기준으로 맞추고, 대표 행동은 ‘내 차례’로 구분합니다. 대화 보기·받는 직원·현재 실행의 차이는 유지합니다. 이름을 맞춘다고 기록 ID나 권한·실행 구조까지 합치지 않습니다.

다음 적용 순서는 화면 문구 목록 대조 → 같은 개념의 명칭 정리 → 대화·보고·자료 안내의 일관성 확인입니다. 이번 후속 작업에서는 사전만 갱신했으며 제품 코드·서버·역할 설정은 수정하지 않았습니다. 화면 적용 여부도 새로 시험하지 않았습니다.
