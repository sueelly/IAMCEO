# 먼저 보고 보완의 연쇄를 끊고, 같은 결과는 한 묶음으로 보여주길 권합니다

분석·제안 완료 · 구현/설정 변경 전 · 맡기는 결과는 **업무**, 대표 행동은 **내 차례**로 표기합니다.

## 대표가 알아야 할 결론

1. 보고가 저장되지 않은 문제가 아닙니다. 총괄이 ‘알림’ 종류로 결과를 남겼는데 서버는 이를 필수 보고 마감으로 인정하지 않아 다시 보고를 요구했습니다.
2. 보고 보완만이 실행을 깨웠어도, 함께 들어간 조용한 안내 때문에 또 보완을 만드는 조건이 있습니다. 실제 연쇄 5곳을 확인했습니다. 같은 실행을 두 번 재촉한 것이 아니라, 다음 실행마다 재촉 대상이 바뀐 자기증폭입니다.
3. 추천 순서는 **보완 연쇄 차단 → 원보고·총괄 확인을 한 결과로 묶기 → 내 차례 중심의 즉시 알림**입니다. 결재·실패·필수 질문은 유지합니다.

## 3. 자기증폭은 어디서 생겼나

현재 requestMissingReport는 세 가지를 함께 봅니다.

- ‘완료/답변’ 또는 ‘막힘/질문’, 새로 열린 본인 결재 등은 보고 마감으로 인정합니다. ‘진행/알림’만 남긴 실행은 인정하지 않습니다.
- 실행 입력 중 wake=true가 하나라도 있으면 재촉 가능성이 생깁니다.
- 모든 입력이 판 정리나 보고 보완일 때만 재촉을 생략합니다. 여기에는 wake=false인 조용한 안내까지 포함해 검사합니다.

그래서 **보고 보완(wake=true) + 조용한 안내(wake=false)**가 섞이면 ‘모두 보완’ 조건에서 벗어납니다. 새 업무 지시가 실행을 깨우지 않았는데도 새 run ID로 보고 보완이 다시 생깁니다. 보완만 단독으로 들어간 실행은 이 조건으로 멈췄습니다.

### 배제한 가설과 남은 한계

- Codex의 post를 서버가 인식하지 못했다: 확인 사례는 메시지·원본 참조·성공 operation 결과가 남아 있어 이 설명을 지지하지 않습니다.
- 마지막 답이 비어서 생겼다: 마지막 답의 원문을 수집하지 않았습니다. 현재 확인한 재촉은 저장된 보고 종류와 입력 조건으로 설명되므로 빈 답을 원인으로 단정하지 않습니다.
- 같은 네트워크 요청이 보고를 복제했다: 동일 원본 전달·대화 완전 동일 내용·대상 run의 재촉 중복은 이번 모집단에서 찾지 못했습니다.
- 모든 ‘알림’을 완료로 바꾸면 된다: 실제 중간 보고를 완료로 오인할 수 있으므로 추천하지 않습니다. 보고 내용의 처리 결과를 별도로 남겨야 합니다.

결재 사본·원보고·푸시가 같은 사건을 각 화면에서 여는 것은 곧바로 데이터 중복이 아닙니다. 문제는 각 경로가 독립적으로 다시 주의를 요구하거나, 이미 정리한 내용을 새 글로 반복할 때입니다.

## 6. 무엇을 남기고 언제 멈추나

### 즉시 남길 것

- 내 차례: 아직 답하지 않은 결재, 필수 질문, 직접 해야 할 행동, 확인된 실행 허용 요청.
- 새 실패·막힘·기존 결과를 뒤집는 정정과 충돌. 같은 오류라도 해소 뒤 재발한 별도 사건은 새로 알립니다.
- 원래 보고, 선택/승인 원문, 자료 버전과 검증 결과, 오류 근거. 기록은 지우지 않습니다.

### 묶거나 조용히 기록할 것

- 새 결정 없는 ‘받았다/판에 적었다/기다린다’는 원보고에 연결해 기록합니다. 원문을 보려면 펼칠 수 있게 합니다.
- 전달·실행·보완 요청과 확인은 내부 활동에 남기고, 대표가 처리할 상태로 바뀔 때만 내 차례에 올립니다.
- 여러 업무 결과를 섞지 않습니다. 업무가 미지정이면 같은 원인 사건인 것만 묶습니다. 내용이 비슷하다는 이유로 서로 다른 실패·질문을 합치지 않습니다.

### 중복 억제 키와 기간 제안

| 대상 | 한 번으로 보는 기준 | 기간/변경 시 처리 |
|---|---|---|
| 보고 보완 | 원인 입력/위임 ID + 수신 직원 + 원래 실행. 후속 보완은 같은 rootCause를 유지 | 원인 마감까지 최초 보완 1회. 보완 실행 자체는 새 필수 보고 의무를 만들지 않음. 새 실제 지시는 별도 원인 |
| 결과 묶음 | 프로젝트 + 업무 + 원보고 ID + 정정/결과 revision | 원보고의 수명 동안 원문 연결 유지. 같은 원본 재전달은 새 카드 없음. 중요한 정정은 새 상태 표시 |
| 정보성 요약 | 프로젝트 + 업무 + 원인 사건 묶음 | 첫 사건부터 고정 2분(시작 가설). 계속 뒤로 미루는 슬라이딩 창은 피함. 내 차례·실패는 이 창에 묶지 않음 |
| 결재·CLI 질문 | 결재 ID와 내용 revision / 질문 ID와 세션 세대 | 같은 미해결 항목은 한 번 표시하고 유지. 대상·선택지가 바뀌면 새 확인. 모델이 대신 허용하지 않음 |
| 실패·허용 대기 | 직원 + 실제 오류/질문 episode와 generation | 같은 미해결 사건은 중복 팝업만 억제. 새 실패·권한 범위 변경·해소 뒤 재발은 새 알림 |

새 논리 키 이름은 설계 제안입니다. 현재 DB/API에 rootCause·결과 revision 연결이 이미 있다고 주장하지 않습니다. APNs의 source_key·오류 episode·완료 2분 묶음은 이미 있는 계약이므로 재사용 범위를 확인합니다.

### 보고 보완의 종료 조건

정상 결과/막힘/질문/검증된 위임·대기 처리 결과가 원인과 연결됐거나, 대표/총괄 중단이 확인됐거나, 새 일 없는 판 정리·보완-only이면 멈춥니다. 처리 중인 post operation이 있으면 결과 확정/미확인을 먼저 대조합니다. 불확실한 요청을 새 ID로 재실행하지 않습니다.

실제 새 대표 지시/업무 배정에 종료 보고가 없으면 첫 내부 보완은 남깁니다. 그래도 결과가 없으면 원래 실행의 ‘보고 미확인’ 상태를 한 번 올려 담당이 확인하게 하고, 같은 재촉으로 모델을 계속 깨우지 않습니다. 본인 결재/하위 위임을 기다린다고 신고해도 기존 승인 범위와 원문 참조를 검사하며 권한을 넓히지 않습니다.

## 7. 반영 전후 검증 기준

아래는 후속 구현의 수용 기준입니다. 이번에 시험 실행·재현용 보고를 만들지 않았습니다.

1. 새 업무가 완료됐는데 실제 보고가 없으면 첫 내부 보완 1건은 생긴다. 정상 완료/막힘/질문이 원인 실행에 저장됐으면 보완 0건.
2. 알림이라는 글 종류와 결과 마감을 분리한다. 중간 진행만으로 완료 처리하지 않고, 대기·위임은 원인 참조를 검증한 뒤 그 검토 의무만 마감한다.
3. 보완-only + wake=false 안내가 섞여도 후속 보완 0건. 반대로 실제 새 지시가 함께 오면 그 지시의 보고 의무는 사라지지 않는다.
4. 같은 operation/원본 재전달·재시작 후 복구에도 같은 보완·결과 카드·기기 전송이 중복 생성되지 않는다. 전송 결과 미확인에서는 무조건 재전송하지 않는다.
5. 직원 원보고·총괄 확인·보완은 원문으로 돌아갈 수 있다. 새 오류/정정/대표 판단은 묶음 뒤에 숨지 않는다.
6. 같은 업무에서 직원이 바뀌거나 여러 직원이 참여해도 업무와 원인 연결이 유지된다. 다른 직원이 지금 구현 중인 업무 자동 연결·선택 UI와는 계약만 맞추고 이 분석에서 변경하지 않는다.
7. 필수 결재/CLI 질문/실패 누락 0, 자동 승인 0. 대표가 실제 처리해야 할 항목을 정보성 묶음으로 늦추지 않는다.

측정은 같은 단위로 합니다: 대화 AI 글/원인 사건, 보완 전용 추가 실행 수, 재귀 보완 수, 원문 접근 가능 여부, 내 차례 누락·응답 지연, 기기 전송 시도/수락/실제 표시를 각각 기록합니다. 동일 24시간의 업무량이 달라질 수 있어 사건당 수치와 업무별 전후를 함께 비교합니다. 현재 AI 글 75·총괄 35·보완 전용 실행 13·재보완 5를 기준선으로 둡니다.
