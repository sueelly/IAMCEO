# 원본 네이티브 구현에서 선별할 성능 개선

**서버 조회 최적화와 화면의 불필요한 갱신을 줄이는 부분은 가져올 가치가 있다. 네이티브 전체 도입은 성능 개선의 선행 조건이 아니다.** 현재 웹의 페이지 조회·압축은 유지하고, 공통 서버 최적화를 먼저 검토하는 편이 적합하다. 네이티브는 실시간 터미널과 기기 기능을 많이 사용할 때 장점이 더 뚜렷하다.

2026-11-17 12:31 KST 기준으로 원본 `yehsung/IAMCEO`의 `v0.2.7`(`43d1a8552b1b27a32d3a86f47cef2c7178f8057b`)과 실제 운영 소스 `5fe3fb7376f6f9acd85159f694242c12afbf9e2d`를 비교했다. 운영 build ID도 manifest와 실제 API에서 대조했다. 기본 체크아웃의 오래된 main을 현재 서비스로 취급하지 않았다.

원본은 웹 클라이언트를 제거했고 서버·도메인·앱 구조도 함께 변경했다. 현재 운영 소스와 원본은 공통 조상 이후 양쪽에 각각 121개 커밋이 있다. 아래 항목은 변경 부분을 우리 계약에 맞춰 옮길 후보이며, 커밋 전체를 그대로 합치자는 제안은 아니다. 조사 중에는 제품 코드·운영 설정·실행 상태를 바꾸지 않았다.

### 1. 전달 상태 조회를 묶어서 읽는다

원본 [c4609e4](https://github.com/yehsung/IAMCEO/commit/c4609e4)는 `withDeliveryRead`를 도입해 한 번의 동기 조회 동안 필요한 행을 Map으로 보관한다. 알림 미리보기와 연결되지 않은 실패 메시지도 별도 일괄 조회한다. 원본의 현재 구현은 [Store.withDeliveryRead](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/server/store.ts#L917)에서 확인할 수 있다.

우리 쪽 [DeliveryRecovery.items](https://github.com/sueelly/IAMCEO/blob/5fe3fb7376f6f9acd85159f694242c12afbf9e2d/server/delivery-recovery.ts#L609)는 전달별 복구 값을 읽고, 연결되지 않은 실패 메시지를 찾기 위해 메시지 페이지를 끝까지 순회한다. 항목 하나를 표시할 때 추가 메시지·결재·할 일 조회도 한다. 외부 응답을 작게 만들어도 이 서버 내부 작업은 남는다.

원본 `tests/stall-fix.test.ts`에는 메시지·전달 900건, 실시간 클라이언트 3개 조건에서 조회 수·응답 지연을 확인하는 검사가 있다. 검사에 명시된 임계값은 이번 장비에서 측정한 개선 수치가 아니다. **기대 효과는 코드 구조에 근거한 추론이며, 이식 전후 같은 fixture로 SQL 실행 수와 p95를 비교해야 한다.** 커밋에는 APNs와 실행기 변경도 포함돼 있어 조회 관련 부분을 골라야 한다.

### 2. 동기화 응답의 생성 비용을 재사용한다

원본 [93a1a42](https://github.com/yehsung/IAMCEO/commit/93a1a42)는 동기화 결과를 JSON 문자열로 보관한다. 현재 [HTTP 구현](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/server/http.ts#L841)은 epoch·seq·주소가 바뀌면 캐시를 비우고, 프로젝트·lite·앱 호환 필드를 구분한다. `tests/realtime.test.ts`에는 동시 요청 8개가 상태 생성 한 번을 공유하는지 확인하는 검사가 있다. 그 검사는 이번 조사에서 실행하지 않았다.

우리 [동기화 경로](https://github.com/sueelly/IAMCEO/blob/5fe3fb7376f6f9acd85159f694242c12afbf9e2d/server/http.ts#L657)는 요청마다 상태를 만들고 직렬화한다. 이 원칙을 옮기면 같은 상태를 여러 번 읽는 비용을 줄일 수 있다. 다만 직원 이벤트가 계속 생기면 캐시가 자주 무효화되므로 실제 적중률을 확인해야 한다.

**우리 캐시에는 compact 조회 구분과 현재 접속 호스트·SSH 재정의 값도 반영해야 한다.** 최근 추가한 `connection` 정보는 요청 Host와 실시간 운영 설정에 따라 달라진다. 원본의 열쇠를 그대로 복사하면 앞 기기의 접속 주소나 설정 변경 전 값이 다른 응답에 남을 수 있다. 권한·복구 상태·cursor를 오래된 캐시로 판단하지 않는 경계도 검증해야 한다.

같은 커밋의 `LoopMonitor`는 느린 경로와 이벤트 루프 지연을 찾는 보조 도구로 유용하다. 이것을 추가하는 행위 자체가 성능 개선은 아니다.

### 3. 변화 없는 화면 자료의 참조를 보존한다

원본 [21cce52](https://github.com/yehsung/IAMCEO/commit/21cce52)는 같은 domain payload의 재대입을 막고 collection별로 관찰 값을 분리한다. 현재 원본의 [상태 반영](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/native/Sources/IAMCEO/State/AppStore+Sync.swift#L262)과 [목록별 갱신](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/native/Sources/IAMCEO/State/AppStore.swift#L477)에 그 원칙이 남아 있다.

우리 웹도 selector 기반 구독을 사용한다. 다만 [acceptSnapshot](https://github.com/sueelly/IAMCEO/blob/5fe3fb7376f6f9acd85159f694242c12afbf9e2d/web/src/lib/store.ts#L387)은 읽을 때마다 bootstrap·project 객체를 새로 만든다. 의미가 같은 목록의 참조를 유지하는 방식은 추가 개선 후보다. 네트워크 요청량을 줄이는 변경과는 구분해야 한다.

변경 여부를 매번 전체 JSON 문자열로 비교하면 그 비교 비용이 새 부담이 된다. 또한 member의 config revision만 보고 실행 상태 변화까지 무시해서는 안 된다. 대화 병합·전달 상태·새 필드가 실제로 갱신되는 회귀 검사가 필요하다. SwiftUI도 업데이트 빈도와 의존 범위에 따라 비용이 달라진다는 점은 [Apple 성능 지침](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)과 일치한다.

### 4. 네이티브 터미널은 작은 변경으로도 개선할 부분이 있다

원본 [395bd9a](https://github.com/yehsung/IAMCEO/commit/395bd9a)는 터미널 도입이 아니라 기존 터미널의 객체 유지·크기 변경·입력 전달을 다듬은 변경이다. 우리 네이티브에도 이미 WebSocket과 SwiftTerm이 있다. 원본은 `.id(outputGeneration)`으로 뷰를 다시 만들던 방식을 제거하고, 크기 변경 중 출력 연결을 유지하며, [입력을 8ms 동안 묶어 순서대로 전송](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/native/Sources/IAMCEO/Services/TerminalStreamClient.swift#L264)한다.

원본 검사에는 엔진 객체 식별자, 출력 handler·buffer 유지, 입력 순서를 확인하는 조건이 있다. 터미널 조작권·세션 세대·재연결 판정과 연결돼 있으므로 관련 검사를 함께 가져와야 한다. 이 조사에서는 실제 기기의 터미널 지연이나 FPS를 측정하지 않았다.

## 이미 있는 기능과 네이티브 추가 후보

- **웹의 숨긴 탭 정지와 이벤트 묶기는 이미 있다.** 현재 웹은 visibility/pagehide 때 동기화를 멈추고, 오로라 애니메이션도 hidden/reduced-motion 조건에서 정지한다. 동기화는 250ms 묶기, 한 번에 한 요청, 기본 최대 초당 2회로 제한한다. 이 기능을 네이티브만의 새 이점으로 세지 않았다.
- **계속 들어오는 이벤트에 새로고침 완료가 붙잡히는 문제는 네이티브 개선 후보다.** 원본 `b55d5cd`는 해당 읽기 pass가 끝나면 호출을 반환하는 waiter를 사용한다. 우리 웹은 pass별 완료 처리가 있지만 기존 네이티브는 전체 coordinator task를 기다린다.
- **느린 연결에 맞춘 요청 간격 조절은 실험할 만하다.** 원본 `AppStore+Sync.swift:370`은 이벤트 기반 읽기를 직전 소요시간의 두 배, 최대 5초까지 늦춘다. 사용자 직접 새로고침 등은 구분한다. 전송량과 서버 부담을 낮추는 대신 화면 갱신이 늦어질 수 있다.
- **프로젝트 재진입용 읽기 캐시는 네이티브에서 유용할 수 있다.** 원본 [ProjectStateCache](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/native/Sources/IAMCEO/State/ProjectStateCache.swift#L3)는 JSON 인코딩을 main queue 밖에서 수행하고 최대 4개·8MiB의 직렬화된 상태를 보관한다. 이 수치는 앱 전체 메모리 한도가 아니다. 재진입 시 디코딩과 최신 상태 검증 비용도 남는다.
- **가려진 Mac 사무실 창의 애니메이션 정지도 작은 네이티브 후보다.** 기존 앱은 비활성 창에서도 15/6fps로 움직이지만 원본은 자기 창이 key·visible인지를 확인해 정지한다. 활성 창의 사무실 애니메이션은 양쪽 모두 기본 30/12fps 계열이므로 원본이 전체적으로 덜 그린다고 단정할 수는 없다.
- 영속적인 last-seen·offline outbox 전체는 별도 기능이다. 서버 식별·전송 결과 불명·초안 복구·삭제 규칙까지 포함한다. 성능 수정에 묶어 통째로 도입하지 않는 편이 적합하다. 현재 웹에도 초안과 immutable send attempt의 기기 저장은 있다.

진행 중 네이티브 브랜치 `feat/agent-a-native-20261116`의 `0e31afd`도 읽기 전용으로 확인했다. 위 동기화·APIClient·TerminalStreamClient의 핵심 세 파일은 운영 소스와 같았다. 별도 진행 작업의 미커밋 변경은 조사 결과에 구현 완료로 합산하지 않았다.

## 현재 응답량과 호환 확인

2026-11-17 12:31:35 KST, 현재 운영 중인 같은 큰 프로젝트를 loopback에서 한 번씩 조회했다. 각 요청은 gzip을 허용했고, 전후 실제 build ID가 같은지 확인했다. 내용은 읽기 응답이며 메시지 전송·직원 실행·승인 응답은 하지 않았다.

| 현재 서버의 조회 방식 | JSON 원문 바이트 | gzip 전송 바이트 | 응답에 포함된 범위 |
|---|---:|---:|---|
| 기존 전체 sync | 7,918,567 | 1,325,240 | 최근 메시지 200개·자료 281개 |
| 현재 웹의 compact sync | 248,842 | 70,303 | 메시지는 별도 조회·자료 목록 20개 |
| 대화 첫 페이지 | 34,028 | 7,762 | 메시지 50개 |
| 자료 첫 페이지 | 17,206 | 4,976 | 자료 요약 20개 |

compact sync 하나의 전송량은 전체 sync보다 약 94.7% 작다. 대화·자료 상세와 후속 페이지 요청은 별도로 발생한다. 앞서 관찰한 7.9MB 전체 응답을 지금 웹이 그대로 반복 전송한다고 설명하면 현재 상태와 다르다. 이 표는 같은 서버의 서로 다른 조회 범위를 비교한 것이며, 네이티브와 웹의 같은 작업을 실측한 성능표는 아니다. loopback 응답 시간을 다른 기기의 Tailscale 체감 속도로 확대하지 않았다.

**최신 원본 앱의 sync 요청을 현재 서버에 그대로 보내면 400이 반환된다.** 원본 [APIClient](https://github.com/yehsung/IAMCEO/blob/43d1a8552b1b27a32d3a86f47cef2c7178f8057b/native/Sources/IAMCEO/Services/APIClient.swift#L206)는 lite 조회를 사용하고, 현재 서버는 `projectId,view`만 허용한다. 실제 `lite=1` GET의 400과 `view=compact` GET의 200을 확인했다. 최신 앱이 현재 서버에 그대로 호환된다고 볼 수 없다.

`lite`를 `compact`로 문자열만 바꾸는 것도 충분하지 않다. compact에서 빠진 메시지·자료를 네이티브가 별도의 history/file paging으로 채워야 한다. 원본의 lite는 자료 본문을 제거하는 projection이며, 우리 compact 페이지 계약을 대체하는 동일 기능이 아니다.

## 네이티브가 웹보다 나은 부분

| 사용 상황 | 현재 구현에서의 판단 |
|---|---|
| AI가 코드를 작성하거나 명령을 실행하는 속도 | 같은 맥미니·CLI·모델에서 이미 시작한 추론·명령 연산을 클라이언트 종류가 직접 빠르게 하지는 않는다. 입력 전달·화면 반영 지연은 달라질 수 있다. 서버 최적화는 양쪽 모두에 영향을 준다. |
| 터미널을 길게 보며 키·선택·ANSI/TUI를 다루는 작업 | 네이티브가 더 완성된 기능을 갖췄다. 현재 웹은 `/screen`의 전체 텍스트를 2초 주기로 읽고 ANSI를 제거해 표시하며, 네이티브는 실시간 VT 스트림을 렌더링한다. 입력 지연의 수치 우열은 미측정이다. |

| 기기 알림·사진/파일 입력·오프라인 재진입 | 원본 네이티브의 구현 범위가 더 넓다. APNs·기기 서명·서버 설정과 실제 기기 검증은 별도로 필요하다. 웹에서도 구현 가능한 영역과 현재 구현된 범위는 구분한다. |

원본 앱의 배포·구현 완료와 우리 환경에서 성능 우위를 확인한 것은 다른 상태다. 이번 조사에서는 원본 앱 설치·빌드, 실제 iPhone/외부 기기의 A/B 측정은 하지 않았다.

## 적용 순서 제안

1. 현재 웹의 compact·페이지 조회·압축을 유지한다.
2. 전달 상태의 일괄 조회와 요청 내 재사용을 먼저 작은 변경으로 옮기고, 동일 fixture에서 SQL 실행 수·p95와 전달 판정 동일성을 확인한다.
3. 변경 세대에 따른 sync 응답 재사용을 추가하되 주소 설정·권한·compact·프로젝트·cursor별 분리를 검사한다.
4. 바뀌지 않은 목록의 참조를 보존하고, 이벤트가 몰릴 때 React render 수·긴 프레임·현재 상태 갱신 누락을 비교한다.
5. 네이티브를 사용할 경우 API 호환을 먼저 맞춘 뒤 터미널 객체 유지, refresh waiter, 읽기 캐시, 가려진 창 정지를 선별한다.

이 순서는 조사에 따른 제안이며 구현 착수나 전체 원본 병합을 승인한 작업 목록이 아니다. 실제 이식 전후에는 같은 데이터·기기·Tailscale 경로에서 초기/재진입 시간, 요청 수·전송량, 이벤트 폭주 중 UI 지연, 숨긴 창 CPU, 터미널 출력 지연을 함께 측정해야 한다.
