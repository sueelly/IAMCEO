# 기존 지시의 독립 실행 복구 계획

> 실행 방식: 대표님이 지시한 네이티브 하위 에이전트 병렬 조사·시험과 이 세션의 통합 구현을 사용합니다.

목표: 이전 업무를 완료로 바꾸지 않고, 대표님이 명시적으로 허용한 독립 후속 지시의 원래 전달 ID를 기존 전송 경로에 넣습니다.

기준은 업무 `tk_w_SoxDmyweQG9B` 계약 r1입니다. 기존 읽기 전용 진단 업무와 분리합니다. 대표님의 최신 직접 지시는 독립 후속의 불필요한 순차 대기를 해제하되 승인·한도·조작권·소유 범위를 보존합니다.

## 설계

확정한 소스 재현 경계는 `pendingInputs → taskSequenceBlocker → hasWake=false`입니다. 과거 업무의 최종 완료 표시가 없으면 새 업무는 전송 시도 전에 제외됩니다. 네 직원 모두의 현재 운영 분기는 아직 확인하지 못했습니다.

네이티브 하위 에이전트의 `parallel` 설정을 업무 순서 예외 권한으로 사용하지 않습니다. 기본 순차 동작은 유지합니다. 대표 인증을 거친 명시적 복구 요청만 기존 전달 ID·업무·직원·대표 원문·세대·선행 업무를 묶어 허용합니다.

복구 요청은 기존 `workflow_assignment_receipts`의 JSON에 기록합니다. 새 입력을 만들거나 전달·수신·실행 상태를 꾸미지 않습니다. 같은 요청의 재시도는 같은 영수증을 읽으며 다시 전송하지 않습니다. 실제 전달은 기존 전달 함수가 수행합니다.

조작권·승인·불확실한 이전 입력·세션 작업·실행 중 상태·계정 제한·전역 동시 실행 제한은 기존 검사 그대로 적용합니다. 같은 부모 계통의 업무는 이 예외로 순서를 바꾸지 않습니다. 대표 원문이 바뀌거나 세대가 바뀌면 예외는 유효하지 않습니다.

## 파일과 검증

- [ ] `tests/delivery-independent-admission.test.ts`에서 기존 지시가 시도 0회로 남는 실패를 먼저 확인합니다. 명시적 허용 뒤 단 한 번 전달되는지 확인합니다.
- [ ] `server/independent-delivery.ts`와 전용 시험에서 출처·세대·업무·직원·기존 전달·순서 예외를 검증합니다. 서로 다른 프로젝트와 같은 부모 계통, 보호 중인 입력, 오래된 요청을 거절합니다.
- [ ] `shared/workflow.ts`, `server/store.ts`에 영수증 형식과 부작용 없는 조회만 더합니다. DB 판은 바꾸지 않습니다.
- [ ] `server/orchestrator.ts`에서 확인한 예외만 업무 순서 검사에서 허용합니다. 기존 안전 검사와 원래 전달 순서를 유지합니다.
- [ ] `server/http.ts`, `server/orchestrator-api.ts`에 대표 인증 경로만 연결합니다. 직원 도구에는 쓰기 권한을 추가하지 않습니다.
- [ ] 실제 격리 HTTP 요청, busy·lease·불확실 입력·정상 종료 후 재진입·동시 실행 제한·단 한 번 수신 회귀와 코드 검사를 실행합니다.
- [ ] 독립 검토 뒤 검증한 변경만 커밋하고 origin에 일반 업로드합니다. 원격 SHA를 대조합니다.
- [ ] 운영 바이너리의 동일성, 기존 ID의 실제 수신·실행, 적용에 필요한 조건을 구분해 인계합니다. 운영 서비스 변경과 직원 재송신은 실행하지 않습니다.

## 검토 초점

- 네이티브 병렬 설정만으로 업무 순서나 승인 범위를 넓히지 않습니다.
- 대표 원문 ID는 출처이며, 글 안의 ‘병렬’ 단어를 자동 승인으로 해석하지 않습니다.
- 기존 입력의 불확실성을 새 정상 전달로 바꾸지 않습니다.
- 같은 요청 재시도와 세대·원문 변경이 중복 전송을 만들지 않아야 합니다.
- 시험은 격리 저장소와 소켓만 사용합니다. 운영 DB·실행 기록을 직접 읽지 않으며 임시 폴더를 지우지 않습니다.
