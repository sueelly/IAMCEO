## 목적·제외·제약

## 접근 방법과 작성자의 선택

- task_trace에 매번 기록 읽기를 더하면 평소 조회 비용과 노출 범위가 커진다.
- 별도 exec_diagnose를 두면 요청한 실패 검사만 필요할 때 진단한다. 이 최소 변경을 작성자가 선택한다. 총괄이 위 두 방식 중 최소 변경을 맡긴 범위 안의 구현 판단이다.
- 원문 검색 도구나 새 성공 수집 경로는 금지 범위이므로 제외한다.

## 입력과 권한

같은 프로젝트의 정확한 업무에 붙은 실패 실행 검사(result=fail, behavior/typecheck/regression)만 받는다. 직원·계약 판·명령은 보고의 서버 기록에서 정한다. 임의 직원/명령/세션/경로 인자는 없다. 총괄은 같은 프로젝트, 직원은 자기 보고만 조회한다.
완료 관문이 거절해 보고 메시지로 남지 않은 시도는 직접 조회 대상으로 지정할 수 없다. 이미 있는 진행/막힘 보고의 실패 검사로 조회한다. 이는 공통 operation 요청 보관과 별개다. 비서 사례는 msg_xGtpAoZRLvIz의 check_index=3이다. 거절 당시 스냅숏이 없고 개선 후보가 검사 번호를 기록하지 않았다는 한계를 표시한다.

## 반환과 경계
