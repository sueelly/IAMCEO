# 외부 기기의 자료·대화 조회 개선

맥미니 밖에서 프로젝트를 열거나 갱신할 때 자료 본문 전체를 반복 전송하지 않고 필요한 목록과 본문만 받는다. 사용자가 보고한 7.9MB 응답과 7.5MB 자료 데이터는 구현 전 운영 데이터로 다시 측정한다.

## 범위와 결정

사용자가 자료의 비동기 최신순 조회, 무한 스크롤, 업무별 조회 최적화와 대화의 점진 조회를 실행 요청했다. 자료 20개와 대화 50개를 한 페이지로 쓰는 것은 구현자의 선택이다. 자료 목록은 본문을 제외하고, 선택한 자료만 상세 요청한다. 페이지 경계는 최신순 정렬 값과 ID를 포함하는 커서로 표현한다. 업무·종류 조건을 커서에 묶어 다른 조건에 재사용하지 못하게 한다.

기존 전체 응답에 압축만 적용하면 원문 전송과 해석 비용이 남는다. offset 페이지는 새 자료가 추가될 때 중복·누락이 생길 수 있다. 따라서 요약 목록과 커서 페이지를 사용하고 큰 조회 응답의 gzip 압축을 함께 적용한다. 기존 네이티브 클라이언트 계약은 보존하며 새 웹 클라이언트가 기능 지원을 확인한 뒤 가벼운 상태 응답을 요청한다. 이번 화면의 ‘네이티브 · Codex 체험’은 프로젝트 이름이며 네이티브 앱 전체를 재설계하지 않는다.

## 요구사항과 완료 조건

- R1. 웹 프로젝트 갱신은 자료 본문 전체와 별도의 최근 대화 200개를 다시 받지 않는다. A1 → R1. 큰 본문을 가진 45개 자료와 120개 대화 fixture에서 가벼운 상태 응답에 본문이 없고 대화는 페이지 API로 최대 50개만 받는지 검사한다.
- R2. 자료는 업무·종류 조건에 맞는 최신 20개부터 비동기로 조회하고 목록 하단에서 다음 페이지를 받는다. A2 → R2. 동일 정렬 값, 페이지 사이 추가·삭제, 조건 변경, 지연된 응답과 재시도에서 누락·중복·다른 조건의 자료 혼입이 없는지 검사한다. 종류 개수는 현재 업무 전체를 기준으로 표시한다.
- R3. 자료는 선택할 때 본문을 읽으며 목록 밖의 직접 링크도 열 수 있다. A3 → R3. 첫 목록에 없는 오래된 자료의 직접 링크와 다른 업무의 링크를 열고 프로젝트가 다른 자료는 섞이지 않는지 브라우저로 검사한다.
- R4. 업무별 자료와 대화 페이지는 조건·정렬에 맞는 인덱스를 사용한다. A4 → R4. 충분한 fixture에서 EXPLAIN QUERY PLAN으로 인덱스 탐색을 확인하고 전체 정렬을 위한 임시 B-tree가 없는지 확인한다.
- R5. 대화는 최신 50개부터 기존 과거 조회를 이어 쓰고 위로 더 읽을 때 보던 위치와 실시간 글을 보존한다. A5 → R5. 기존 커서·동기화·스크롤 회귀 검사와 브라우저의 추가 페이지 조회를 검증한다.
- R6. 압축을 지원하는 클라이언트에는 큰 JSON 조회 응답을 gzip으로 전송한다. A6 → R6. 압축 협상·압축 해제 내용 동일·gzip 거부·작은 응답·인증 경계를 검사하고 실제 원문 및 전송 바이트를 비교한다.
- R7. 변경은 검증·커밋·작업 브랜치 푸시 후 원격 SHA를 대조한다. A7 → R7. 해당 검사, 타입 검사, 빌드와 리뷰 결과를 남긴다. 운영 반영은 진행 중인 실행·대화·승인과 기존 Tailscale 경로를 보존할 수 있는 절차로 검증하며 실제 반영 여부를 별도로 보고한다.

인증·승인 자동 응답, 직원 실행 시작·중단, 무관한 프로젝트 수정은 범위에 포함하지 않는다. 실제 다른 기기의 속도는 그 기기에서 측정하지 않았다면 맥미니의 응답량 검증과 구분해 보고한다.
