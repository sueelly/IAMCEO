# 첫 접속 개선의 순차 반영

다른 기기의 Tailscale 웹 접속에서 첫 화면을 더 빨리 열고, 현재의 결재·대화·실행 정합성을 보존한다. 사용자는 서버 조회 재사용 개선과 비교한 뒤 적절한 개선을 순서대로 실제 반영하도록 요청했다.

현재 운영 소스는 `6471aa7`이다. 이 버전에는 요청 단위 알림 조회 일괄 처리, 250ms·32개·8MiB 한도의 compact 응답 재사용, 변경 없는 화면 객체 참조 보존, 직전 첫 화면 수정 `eaa12a7`, 스키마 v35 저장 최적화가 이미 함께 들어 있다. 같은 기능을 다시 만들지 않고 이 소스를 작업 브랜치로 가져왔다. 현재 워크트리는 `paginate-project-data`, 브랜치는 `fix-paginate-project-data`다.

## 선택과 범위

기존 전체 상태 계약을 유지하면서 운영용 화면 번들과 첫 접속의 불필요한 왕복을 먼저 줄인다. 홈 전용 새 상태 모델은 기존 업무 선택과 결재 버전 확인을 함께 이전해야 하므로 이 단계에서 부분 상태를 완전한 `ProjectState`로 가장하지 않는다. 변경분 전용 실시간 프로토콜도 이번 변경에 섞지 않는다. 이 선택은 구현자의 판단이며 새 조회 계약을 여러 개 동시에 바꾸는 위험을 줄인다.

초기 상태와 대화의 단순 병렬 요청은 채택하지 않는다. 대화를 먼저 받은 뒤 상태 커서가 앞으로 이동하면 초기 실시간 연결 사이의 글을 놓칠 수 있다. 대신 서버가 같은 동기 경계에서 최신 대화 페이지와 상태·커서를 한 응답에 담는 선택적 기능을 추가한다. 기존 페이지 API와 커서로 과거 조회·간격 복원을 계속한다.

- R1. 기존 서버 재사용·저장소·정합성 개선을 보존한다. A1 → R1: 현재 운영 소스에서 캐시 인증·직접 DB 변경·Host 분리·만료, 알림 SQL 수와 객체 공유 검사 19개를 통과한다.
- R2. 정식 앱 만들기는 운영용 React와 최소화한 화면 코드를 포함한다. A2 → R2: 실제 단일 실행 파일을 격리 홈에서 띄워 내장 JS의 gzip 전송량이 250KB 미만이며 기존 홈·인증·스타일이 동작하는지 확인한다. 로컬 `build`와 두 아키텍처 release 경로는 같은 옵션을 사용한다.
- R3. 첫 접속의 첨부 쿠키 발급과 기능 확인을 동시에 시작하고 `pageshow` 중복 시작을 합친다. A3 → R3: 쿠키를 보류해도 기능 확인이 시작되지만 화면 데이터 적용은 기존 인증 경계를 지키고, 같은 접속의 중복 쿠키 요청은 한 개다. 로그인 변경·숨김·로그아웃 후 늦은 응답을 버린다.
- R4. 지원하는 서버에서는 compact 상태와 최신 대화 50개를 같은 응답으로 받는다. A4 → R4: `snapshotHistory` 기능 협상, `history=50` 요청, 페이지 커서·실시간 겹침·404·잘못된 조건·캐시 변형 분리·기존 서버 fallback을 검사한다. 이 응답 이후의 글도 기존 실시간/간격 복원으로 보존한다.
- R5. 검증한 단계마다 커밋하고 작업 브랜치를 일반 푸시한다. A5 → R5: 관련 회귀·타입 검사·고정 SHA 빌드와 원격 SHA를 확인한다. 운영 반영 전 최신 제공 소스를 다시 대조하고 스키마 v35·인증·기존 직원 PID·승인·Tailscale 경로를 보존한다. 새 운영 백업이나 저장소 재압축은 수행하지 않는다.
- R6. 실제 효과를 동일 조건으로 비교한다. A6 → R6: 1Mbps·150ms·빈 브라우저 캐시에서 기존과 수정한 서비스의 첫 화면·자산량·첫 조회 요청 수를 각각 남긴다. 첫 단계의 목표는 약 3~4초이며 사용자 기기의 실제 측정과 구분한다. 도달하면 더 큰 홈 상태 계약 변경은 후속 대상으로 남긴다.

기존 전체 회귀의 실패는 기준 버전과 구분한다. 규칙 문서나 계획의 완료 표시를 실제 서비스 반영 영수증으로 사용하지 않는다.
