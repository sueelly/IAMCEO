# IAMCEO의 읽는 목적에 맞춘 제목과 상세

사용자는 결재함·보고·자료·업무 이름·현재 상황을 읽는 순간마다 필요한 정보를 알맞은 깊이로 제공하도록 요청했다. 앞선 맥락 보존 작업에 이어, 모든 필드에 같은 요약을 반복하는 대신 탐색·결정·검토·사용 목적을 구분한다.

## 화면과 글의 역할

| 위치 | 읽는 순간과 목적 | 제목·첫 부분 | 상세에서 확인할 내용 |
| --- | --- | --- | --- |
| 업무 이름·목록 | 여러 업무에서 다시 찾고 구별한다. | 대상과 달성할 목표를 안정된 이름으로 쓴다. | 범위·담당·단계·근거는 업무 상세와 보고에 둔다. |
| 결재함 | 무엇을 결정할지 이해하고 선택한다. | 대상과 결정할 질문을 쓴다. | 결정이 필요한 이유, 선택지별 결과, 비용·위험·미확인을 읽고 선택한다. |
| 업무 보고·대화 | 이전 상황과 달라진 결과를 확인한다. | 대상과 이번 결과를 쓴다. | 확인 범위·근거·남은 조건·다음 행동을 읽는다. |
| 자료 목록 | 필요한 결과물을 찾아 연다. | 대상과 결과물 종류를 이름으로 쓴다. | 요약은 용도·핵심 내용·중요한 사용 제한을 알려 준다. |
| 아티팩트·자료 본문 | 문서를 이해·비교·검토하거나 사용한다. | 문서의 목적에 맞는 결론이나 사용할 본문을 제공한다. | 기준·조건·출처·방법·실제 결과물을 목적에 맞게 구성한다. |
| 프로젝트의 지금 상황 | 프로젝트에 들어와 우선 확인할 일을 정한다. | 중요한 변화·병목·대표의 판단 대상을 먼저 쓴다. | 주요 업무의 현재 결과와 다음 행동을 연결한다. 과거 과정은 보고에 둔다. |
| 직원의 상태·다음 | 누가 무엇을 하는지와 이어질 행동을 확인한다. | 현재 행동의 대상을 쓴다. | 다음 주체·조건·행동을 구분한다. 실행 상태와 마지막 보고를 혼동하지 않는다. |

## 요구와 완료 조건

- R1. 기본·사용자 정의 직원에게 위치별 제목·요약·본문의 역할을 전달한다. A1 → R1: 실제 역할 렌더링과 도구 스키마에서 업무 이름·질문·변경 결과·결과물·프로젝트 요약의 목적을 구분하는지 확인한다.
- R2. 업무 이름은 제목 길이 때문에 중요한 목표가 저장 중 잘리지 않게 한다. A2 → R2: 대표가 정한 이름은 API의 기존 200자 범위에서 보존하고, 자동 임시 이름은 직원 task 도구의 기존 120자 범위에서 목적 문장을 보존한다. 기존 비밀값 가림은 유지한다.
- R3. 결정에 필요한 상세는 선택 버튼 전에 읽을 수 있고, 현재 상황의 조건은 자동으로 접히지 않는다. A3 → R3: PC·휴대폰에서 긴 결재 상세가 선택지보다 앞에 나타나고 홈 현재 상황의 마지막 조건까지 보이는지 검사한다. 네이티브 화면도 같은 순서를 적용하고 컴파일·기존 검사를 확인한다.
- R4. 이름·상태만 있는 제목에는 용도에 맞는 비차단 경고를 전달한다. A4 → R4: 업무·보고·결재·자료 도구에서 경고가 표시돼도 원문 저장과 승인 조건이 변하지 않는지 검사한다.
- R5. 작성 원칙과 실제 표시를 함께 검증한다. A5 → R5: 가상 업무로 자료의 제목·요약·본문, 보고의 제목·근거, 직원 상태·다음 행동, 업무 이름과 결재를 실제 화면에서 확인한다.

## 구현 판단과 경계

프롬프트만 보완하면 화면의 강제 접기와 저장 중 제목 절단은 남는다. 모든 내용을 한 형식의 구조 데이터로 다시 만들면 기존 기록의 변환과 새로운 작성 계약이 필요하다. 이번에는 기존 데이터 구조를 보존하면서 프롬프트·도구 설명·저장 길이·읽는 순서를 함께 정리한다. 이 선택은 구현 판단이며 사용자가 별도로 선택했다고 기록하지 않는다.

기존 결재 답변과 기록은 다시 쓰지 않는다. 짧은 탐색 목록과 상세 본문의 역할은 구분하며, 모든 목록에 긴 본문을 펼치지 않는다. 새 필수 필드·승인 동작·완료 판정·DB 이주는 추가하지 않는다. main 통합·운영 배포는 아직 승인된 것으로 간주하지 않는다.
