# 업무의 완료·현재·다음을 함께 보는 관리 화면

사용자는 직원별로 끝낸 일, 현재 해결할 일과 다음 일을 한눈에 비교하고, 업무의 맥락과 실행 제약을 보존하면서 담당자를 배정한다.

2026-11-18 설계 제안이다. 사용자는 설계와 조작 가능한 예시를 먼저 요청했다. 이 문서의 화면 구조와 배정 정책은 검토할 제안이며 제품 반영 완료를 뜻하지 않는다. 예시는 가상 데이터만 사용한다. 원래 터미널과 별개로 작업하며 기존 세션과 운영 데이터를 변경하지 않는다.

## 현재 확인한 구조

기준 소스는 `80d4d76`이다. `WorkFlow.tsx`는 직원별로 배정 기록을 가로로 나열한다. 직원마다 현재 업무의 가로 위치가 달라 비교가 어렵다. `server/workflow.ts`의 `!enrolled` 분기는 순서 관리 도입 전 기록을 ‘이전 업무’로 표시하며, 뒤쪽의 보완·검토 단계보다 먼저 실행된다. `pastAssignment`는 이러한 기록을 접을 수 있다. 이것은 완료 판정과 다르다. 이 설계는 운영 데이터에서 인용된 개별 업무의 현재 상태를 조사한 결과가 아니다.

배정 근거는 실제 수신 직원과 전달 기록이다. `Task.memberId`는 등록자이므로 담당자 칸으로 사용하지 않는다. 같은 업무가 여러 직원에게 배정될 수 있다. 서버는 실행 근거, 90초 관측 만료, 업무 단계, 전달 보류, 순서와 파생 관계를 계산한다.

`Orchestrator.assign`은 업무와 계약을 지시에 포함하고 전달 큐와 `pump`를 사용한다. 웹의 현재 업무 흐름에는 드래그 배정 API가 없다. 기존 메시지 전송을 단순 재호출해 배정을 흉내 내지 않는다. 신규 배정에는 중복 방지와 판 확인이 가능한 별도 쓰기 계약이 필요하다.

## 화면 구조의 선택지

| 구조 | 잘 보이는 것 | 한계 |
| --- | --- | --- |
| 단계별 칸반 | 단계별 업무량과 막힌 일 | 한 직원의 현재 업무와 다음 순서를 함께 비교하기 어렵다. |
| 자유로운 연결 지도 | 부모 업무와 파생 업무의 관계 | 업무가 늘면 선이 겹치며 전체 인력의 상태를 훑기 어렵다. |
| 직원별 완료·지금·다음 판과 연결 보기 | 담당자, 현재 위치, 대기 순서와 관련 업무 | 완료 이력은 요약하고 자세한 관계는 집중 보기에서 확인해야 한다. |

세 번째 구조를 추천한다. 사용자의 ‘한눈에 관리’ 목적과 기존 직원별 순서 모델에 맞는다. 이는 작성자의 제안이며 사용자 선택으로 기록하지 않는다.

## 기본 화면

- 직원 한 명을 한 행으로 두고 `최근 완료 / 지금 / 다음` 열의 위치를 고정한다. 모든 직원의 현재 상태를 같은 열에서 비교한다.
- 최근 완료에는 검증된 업무 완료만 표시한다. 카드의 결과 요약과 완료 시각을 제공한다. 이력 전체는 별도로 연다.
- 지금에는 실행 중인 일뿐 아니라 보완, 검토, 반영 대기와 막힌 일을 남긴다. 필요한 경우 막힌 이유와 다음 행동의 담당자를 카드에 표시한다. 턴 종료를 업무 완료로 바꾸지 않는다.
- 다음에는 실제 배정 순서대로 대기한 일을 표시한다. 시작 조건이 있으면 선행 업무를 표시한다. 예상 시간을 임의로 만들지 않는다.
- 미배정 대기열은 별도로 두고 ‘배정 가능’과 ‘요구사항 확인’을 구분한다. 직원의 대기 상태와 업무의 배정 가능 여부는 다른 정보다.
- 상단의 조치 필요·실행 중·다음·완료 수는 업무 ID 기준으로 중복을 제거한다. 여러 직원이 맡은 같은 업무는 행마다 보이더라도 전체 집계에서는 한 번 센다. 배정 건수는 별도 단위로 표시한다.
- 카드에는 제목, 판단에 필요한 상태, 결과 또는 다음 행동만 남긴다. 항상 보이는 안내문·입력 보호라는 추상 라벨·키보드 사용법은 두지 않는다. 상세에서 원인과 근거를 확인한다.
- 완료 근거가 없는 옛 기록은 `결과 확인 필요`로 남긴다. 기존 전달을 새로 실행 가능한 큐에 자동 등록하지 않는다. 해당 직원 행의 지금 열에서 접지 않고 보이며, 실제 현재 실행이 함께 있으면 그 아래 확인 항목으로 표시한다.

## 연결 지도와 우클릭

노드를 우클릭하면 선택한 노드와 직접 연결된 노드만 남긴다. 동일 업무 ID의 다른 직원 노드, 직접 선행·후행 순서, 부모·자식 관계를 포함한다. 관계가 없는 직원 행은 접는다. 터치와 키보드에는 카드의 더보기 메뉴에서 같은 ‘연결된 업무만 보기’를 제공한다.

첫 집중은 1단계 연결이다. 순서 간선을 끝까지 따라가서 직원의 모든 과거 업무가 다시 나타나지 않게 한다. `업무 묶음`을 선택하면 부모·파생 관계를 양방향으로 반복 탐색하되 순환을 방문 집합으로 막고, 그 묶음에 바로 붙은 순서 선행·후행만 추가한다. 업무 묶음 밖의 순서 체인을 재귀적으로 펼치지 않는다. 원래 배치와 작업 순서를 유지하며 ‘전체 보기’로 이전 필터·스크롤·선택을 복원한다.

연결 지도는 같은 데이터를 관계 중심으로 보여 준다. 순서는 실선 화살표, 파생은 점선으로 표시한다. 파생 관계를 실행 선행 조건으로 바꾸지 않는다. 예시에서 연결 지도는 직원·시간 순서의 배치를 유지하며 선만 함께 보여 준다. 기본 판에서는 시각적 혼잡을 줄이기 위해 선을 숨긴다.

## 드래그 배정과 인계

첫 구현 범위는 **미배정이며 실행이 승인된 업무를 직원의 다음 업무로 배정**하는 것이다. 드래그와 더보기의 ‘배정’은 같은 검토 화면을 연다. 이미 받은 업무의 담당 변경과 큐 순서 편집은 별도 확장이다. 이 범위에서는 실행 중인 일, 완료된 일, 이미 배정된 대기 업무의 이동을 제공하지 않는다.

1. 업무를 직원 행의 다음 칸에 놓는다. 업무 카드에 배정 미리보기를 띄우고 아직 서버 상태는 바꾸지 않는다.
2. 인계 화면에서 대상 직원, 큐 위치, 시작 조건, 원래 지시, 완료 조건, 현재까지의 결과, 참조 자료와 준수사항을 확인한다. 업무에 구현 실행 권한이 없으면 배정 버튼 대신 필요한 조건을 표시한다.
3. 사용자가 배정을 실행하면 서버가 프로젝트·업무·직원 범위와 현재 판을 다시 검사한다. 검토 후 계약·담당·상태·큐가 바뀌었으면 충돌을 알리고 새 검토를 요구한다.
4. 유효한 요청만 같은 업무 ID의 전달 큐와 배정 이력에 원자적으로 기록한다. 응답을 잃어도 동일 operation ID로 상태를 확인한다. 다른 ID로 자동 재전송하지 않는다.
5. 배정 성공과 실제 시작은 구분한다. 앞선 업무·승인·연결·수신 확인 문제로 기다리면 해당 이유가 다음 카드에 보인다. 실제 수신·실행 관측이 있어야 실행 중으로 표시한다.

인계 묶음은 원문 메시지 ID와 시각, 프로젝트·업무·부모 업무 ID, 확정 계약의 task ID·rev, 목표·범위·완료 조건·금지 사항, 실패 검사와 마지막 보완 보고, 권한이 확인된 자료·첨부 ID, 작업 브랜치·워크트리, 기존 승인과 선행 조건을 포함한다. 기존 확정 계약은 새 계약으로 덮어쓰지 않는다. 원문과 작성자의 요약을 구분한다. 자료를 너무 많이 담아야 하면 생략 항목과 조회 링크를 명시하고 필수 제한을 잘라내지 않는다. 비밀 값·다른 프로젝트 자료·CLI 인증 자료는 포함하지 않는다.

입력 보호가 걸린 업무에는 ‘이전 입력 수신 여부 확인 필요’처럼 해당 이유를 표시한다. 새 직원 배정으로 보호된 입력을 재생하거나 실행 소유권을 빼앗지 않는다. 승인 창의 답변, 반복 감시 해제, 자동 재시도 횟수·예산 상향은 이 화면의 배정 권한에 포함되지 않는다. `assign`의 대표 화면 경로가 일부 반복 감시 제한을 다르게 처리하므로, 신규 배정 API에서 서버 측 보호 검사를 명시적으로 적용한다.

## 상태와 집계 규칙

화면은 서버가 계산한 업무 결과·실행 상태·배정 상태를 구분해서 받는다. 완료는 업무 단계의 검증된 `done`이며 옛 기록 여부나 마지막 메시지의 ‘완료’ 단어로 판정하지 않는다. 검증된 완료와 미해결 제약이 동시에 나타나면 서버 계산을 수정하고 ‘상태 확인 필요’로 표시한다.

집계는 선택한 프로젝트 전체의 고유 업무 ID를 기준으로 한다. 담당자 복수, 집중 보기와 페이지 크기 때문에 전체 수가 달라지지 않는다. 필터 적용 시 ‘표시 N / 전체 M’은 별도로 제공한다. 실행 중·조치 필요가 겹치는 업무는 조치 필요를 대표 상태로 집계하되 카드 상세에는 실제 실행도 보존한다. 서버가 오래된 정보를 반환하거나 연결이 끊기면 실행 강조와 쓰기를 중지하고 마지막 확인 시각을 표시한다.

미배정과 배정된 업무는 모두 페이지 조회·서버 집계를 사용한다. 최신 50개 메시지나 접힌 최근 이력만으로 전체 건수·연결·인계 자료를 계산하지 않는다. 집중 범위가 페이지 밖을 가리키면 해당 노드를 추가 조회하고, 없는 노드를 조용히 누락하는 대신 누락된 연결을 표시한다.

## 요구사항과 완료 조건

| 요구사항 | 판정 가능한 완료 조건 |
| --- | --- |
| R1 [확정]. 사용자는 진행·완료·다음 업무를 함께 살핀다. | A1 → R1. 4명 이상의 직원과 상태가 다른 업무로 1440px 화면을 확인한다. 현재 업무가 같은 열에 놓이고 각 행의 완료 결과·현재 이유·다음 순서를 함께 읽을 수 있다. |
| R2 [제안]. 막힘과 미확인 옛 업무는 완료 이력으로 접히지 않는다. | A2 → R2. `historical=true`인 보완·막힘·완료 미확인 기록과 실제 완료 기록을 대조한다. 앞의 세 기록은 지금/확인 필요에 남고 실제 완료만 최근 완료에 들어간다. 큐 자동 등록은 0건이다. |
| R3 [확정]. 사용자는 드래그로 업무를 배정하며 맥락을 전달한다. | A3 → R3. 미배정 업무를 놓고 인계 원문·계약 판·자료·제약을 확인한다. 취소 시 쓰기가 0건이며 확정 시 같은 task ID의 배정이 1건만 생긴다. |
| R4 [확정]. 배정은 기존 실행·보호·승인 규칙을 지킨다. | A4 → R4. 미승인 후보, 수신 불확실, 중단 보호, 반복 감시, 연결 단절, 프로젝트 불일치, 계약 변경, 동시 배정과 응답 유실에서 우회 실행·중복 전달·기존 담당 덮어쓰기가 없다. |
| R5 [확정]. 노드 우클릭은 연결된 업무만 보여 준다. | A5 → R5. 순서·파생·동일 업무 복수 담당·무관 노드를 섞어 우클릭한다. 지정한 범위만 보이고 전체 보기에서 원래 화면으로 돌아온다. 터치 메뉴와 키보드에서도 같은 결과를 확인한다. |
| R6 [제안]. 업무 집계는 중복과 페이지 누락을 피한다. | A6 → R6. 같은 업무의 담당 2명과 50개를 넘는 기록을 사용한다. 서버 전체 고유 task 수와 집계가 일치하며 집중 보기로 전체 수가 바뀌지 않는다. |
| R7 [확정]. 예시 화면은 채팅 밖에서도 열고 읽을 수 있다. | A7 → R7. 네트워크를 차단한 `file://`에서 HTML의 배정·취소·연결 집중·복원·상세를 확인한다. Markdown에 같은 핵심 상태·정책을 남기고 두 파일의 절대 경로를 제공한다. |
| R8 [제안]. 좁은 화면과 보조 입력에서도 핵심 작업을 수행한다. | A8 → R8. 390px 화면은 직원별로 지금·다음·완료를 쌓고 본문이 가로로 넘치지 않는다. 드래그 없이 배정 메뉴를 쓰며 Escape로 상세를 닫은 뒤 원래 카드로 초점이 돌아온다. |

## 구현 경계와 순서

1. 서버 상태 분류·완료 이력 회귀를 먼저 고정하고, 직원별 기본 판과 집중 보기를 구현한다. 관련 파일은 `shared/workflow.ts`, `server/workflow.ts`, `web/src/components/WorkFlow.tsx`, `web/src/styles/workflow.css`다.
2. 서버가 인계 미리보기를 만들고 내용 digest와 workflow revision을 발급하는 읽기 경로, 이를 재검증하는 operation ID 기반 배정 쓰기를 추가한다. `shared/operations.ts`, `server/http.ts`, `server/orchestrator.ts`, 저장소 트랜잭션과 웹 API가 변경 대상이다. 보호 검사와 저장 원자성을 기존 서비스 경계에서 확인하고, 전달은 기존 큐를 사용한다.
3. 회귀 검사·타입 검사·격리 서버 브라우저 검사를 통과한 파일만 커밋하고 origin의 작업 브랜치에 일반 푸시한다. 운영 배정·직원 실행·main 병합·배포는 이 독립 세션의 설계 예시 작업에 포함하지 않는다.

이번 화면 설계는 원래 터미널이 조사하는 자동 후속 실행·완료 루프의 수정과 독립이다. 자동 업무 선택의 추천 알고리즘, 무제한 재시도, 예산 변경, 실행 중인 업무의 강제 이동은 포함하지 않는다. 원래 작업의 완료를 기다려 화면 예시를 만드는 것도 아니다.

기존 React·TypeScript·HTML/SVG와 서버 동기화를 유지하는 것은 작성자의 제안이다. 그래프 라이브러리 추가는 필요하지 않다. 서버 DTO 필드명, 인계 묶음의 저장 스키마, 페이지 크기와 검증 함수 분할은 구현자가 정한다. 단, 위의 원자성·판 확인·권한·자료 범위 조건은 유지한다.

미정 사항은 사용자에게 제안 화면을 보여 준 뒤 확인할 기본 화면 채택 여부다. 나머지 크기·간격·메뉴 위치는 예시 검토 결과에 따라 다듬는다.
